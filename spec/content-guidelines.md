# 教材作成ガイドライン

教材（動画・演習）を作るときの内容面のルールを定める。ファイル形式は `content-format.md` に従う。
AI で教材を作る場合も、このガイドラインを指示として与える。

## 1. 想定する学習者

- 他のプログラミング言語の経験がある人を対象とする。
- 変数・条件分岐・ループ・関数といった一般的な概念は知っている前提で、Rust の文法と Rust 固有の概念（所有権・借用・ライフタイム・トレイトなど）の説明に集中する。
- 他言語との違いが躓きの原因になりやすい箇所は、違いを明示して説明する。

## 2. カリキュラム

- 章立てと学習順は `content/chapters.json` に定める（作成者が別途用意する）。
- 1 レッスンはなるべく Rust の単独の要素のみを主要素とする（多くても 2 つ）。
- 各章の最後に、その章で学んだ内容を復習する章末復習レッスンを置く。

## 3. 未登場の要素を使わない

- レッスン（動画・演習・解説）には、そのレッスンの主要素と既習の要素以外を登場させない。
- 既習の要素と導入レッスンの定義は `content-format.md` §2 に従う。
- `secondary_elements` には既習の要素だけを書く（教材チェックツールで検証する）。
- コード中の構文が未登場でないことは、レビュー時にチェックリスト（§7）で確認する（教材チェックツールでは検証しない）。
- どうしても未学習の構文が必要な場合（例: 標準入力の読み込み）は、「今はおまじないとして使う。詳しくは第 N 章で学ぶ」と明記し、`starter/` の中に完成した形で用意する。

## 4. 動画

### 4.1 構成と長さ

- 構成は「表紙 → 導入 → 本編 → まとめ」を基本とする。
- 長さは 1〜5 分を目安とする。目安であり、超えてよい。
- 最初のシーンは表紙にする。表紙にはレッスン名（`lesson.json` の `title`）を出す（`content-format.md` §5.5）。
- 最後のシーンはまとめにする。まとめには、このレッスンで分かったことを書き、感想にしない。
- 演習の答えに直結する完成コードは動画に載せない。
- 動画だけでは伝えにくい背景知識は台本の `ai_note` に書いておくと、質疑応答の精度が上がる。

### 4.2 台本

- ナレーションは「です・ます」調とする。
- 1 文（`text`）は 60 字までを目安とする。目安であり、超えてよい。
- `say` は 140 字までとする。これは上限であり、超えられない（`content-format.md` §5.2）。
- `text` は、§4.3 の文章の決まり（和文と英数字の間の半角スペースなど）に従って書く。
- `say` には、VOICEPEAK に読ませる形を書く。
  - 読み間違えやすい語は、読みの対応表（`content/readings.json`。`content-format.md` §5.3）に従って、かなで書く（Rust → ラスト、値 → あたい）。
  - 変数名などの英字も、読みで書く（s1 → エスワン）。
  - 間を置きたいところに「、」を入れる。「、」の位置は `text` と違ってよい。
  - 対応表にない語を読み間違えたときは、`say` をかなで書き、その語を対応表に足す。

### 4.3 画面の文章

- 画面の見出しは、そのとき伝えていることを言い切る文にする（例: 「代入すると、所有権が移る」。「ムーブ」のような名詞だけの見出しにしない）。ただし、表紙の見出しはレッスン名、まとめの見出しは「このレッスンのまとめ」のような見出しでよい。
- 見出しは、ナレーションの進みに合わせて切り替えてよい。
- 画面の本文と callout の文は「です・ます」調とする。見出し・小見出し・箇条書き・表・図の中の語句は、言い切りの常体（「〜が移る」）か体言止めでもよい。
- 和文と英数字の間に半角スペースを入れる（「String を代入」「15 行まで」）。
- 表紙のサブタイトルと箇条書きの項目には句点を付けない。1 つの箇条書きの中では、項目の文末（常体・体言止めなど）をそろえる。
- callout の文に「注意:」「ポイント:」のような前置きを書かない（種類はアイコンと色で示される）。
- 表を載せるときは、表から何を読み取ってほしいのかを、ナレーションか、画面の文・callout で伝える。
- 文中でインラインコード（コードの書体）にするのはコード片だけとする。コード片は、記号・括弧・`::` を含むもの（`&s`、`clone()`、`String::from`、`"hello"`）と、キーワード（`let`、`mut`、`fn`）である。変数名・型名・クレート名だけ（s1、String、i32）はインラインコードにしない。見出しではインラインコードを使わない。表で型や式を並べる列は、そろえるためにすべてインラインコードにする。

### 4.4 コード

- 画面に出すコードとコンパイラの出力は、台本の `code_blocks` に書く（`content-format.md` §5.6）。
- 注目させたい字句はマーカー（`CodeBlock` の `marks`）で強調する。行全体に色を付けて強調しない。読み上げている行に目を向けさせるときは、ほかの行を淡くしてよい。
- 他の言語との違いを見せるときは、左右に並べる（左に他の言語、右に Rust）。
- コードブロックには行番号が表示される（`content-format.md` §5.6）。ナレーションと画面の文で、コードの行を「6 行目」のように行番号で指してよい。コード片（「`println!` の行」）や、マーカー・枠のラベル（「r の枠」）で指してもよい。マーカーや枠で指すときは、指している字句や範囲（行番号）を台本の `ai_note` に書く。
  - 行番号は、表示される番号（ファイルの行番号）で書く。
  - ファイルの途中から載せるときは `start_line` を書き、ファイルの行番号やコンパイラの出力の行番号とそろえる。`label` にファイル名を書く。関数の途中から載せてもよい。
  - Diff の行は変更後の行番号で指す。削除行には行番号がないので、コード片（「`let s2 = s1;` を消す」）で指す。
  - 行を差し込む動きの途中では、表示される行番号が `code_blocks` の行番号と違うことがある（`content-format.md` §5.6）。行番号で指すのは、両方が同じになるところだけにする。違うところでは、コード片で指す。
- Diff では、置き換える行は削除行を先に、追加行を後に書く。

### 4.5 エラー

- コンパイルエラーを説明するときは、コードブロックの中のエラーの箇所を波線（`CodeBlock` の `errors`）で示す。そのエラーをレッスンで初めて説明するところでは、実際のコンパイラの出力も、`language` が `text` のコードブロックで示す。同じエラーに再び触れるところでは、出力を省き、波線と言葉の説明だけでもよい。
- コンパイラの出力には、実際に rustc でコンパイルして得た出力を使う。説明に使わない行は省いてよい。載せる行は書き換えない。
- エラーをエラーコードだけで説明しない。ナレーション・画面の本文・callout・見出し・図・コードのコメント・画像の `alt` でエラーを指すときは、何が起きたのかを言葉で書く（例: 「ムーブ済みの値を使ったエラー」「借用している値が先に破棄されるエラー」）。エラーコードは、言葉の説明に括弧書きで添えるときだけ使う（例: 「ムーブ済みの値を使ったエラー（E0382）」）。コンパイラの出力の中のエラーコードは、そのままでよい。

### 4.6 図

- 所有権の移動・参照・メモリ配置など目に見えない仕組みは、図で示す。
- コード（文や式）は図（SVG）の中に書かず、コードブロックに書く。図の中に書くのは、変数名・型名・値と、`&s`・`'a` のような 1 語の短いラベルだけにする。図の説明は図の外の文なので、§4.3 に従ってコード片をインラインコードにして書いてよい。図とコードを 1 つの画面に並べるときは、左右に並べ、片方にコードブロック、もう片方に図を置く。
- 変数が生きている範囲・スコープは図にせず、コードブロックに枠（`CodeBlock` の `scopes`）を重ねて示す。
- 図の色は、色クラス（`content-format.md` §5.7）で指定する。

### 4.7 動きと画面の量

- 1 つの画面の上で、ナレーションの進みに合わせてコードと図を変えていく（所有者の印が動く、行を差し込む、読み上げている行以外を淡くする など）。
- 内容のある範囲へ寄せて、文字と図を大きく見せる。
- 寄せ方、文字の最小サイズ、動きの種類と速さ、1 画面に載せる量は、動画のデザインシステム（`screens.md` §10.1）の README「動画の原則」に従う。
- 合図（`content-format.md` §5.4）は言葉に合わせる。絵が動く位置を、そのことを読み上げる位置にそろえる。
- 台本や声の設定を変えて音声を作り直したら、合図が言葉に合っていることを確かめ直す。

## 5. 演習

### 5.1 問題

- ヒントやコード例は問題文に書かない（入出力例・呼び出し例は書く）。
- 主要素を正しく理解していないと解けない問題にする。少し考えないと解けない難しさを目安とする。
- 過去のレッスンで学んだ要素を取り入れる。
- 入力・出力の形式は、曖昧さがないように厳密に書く（区切り文字、末尾の改行、空の入力の扱いなど）。
- 初期コードには、問題の本質ではない部分（入力の読み込みなど）を用意しておく。
- 初期コードのままでは正解にならないこと（教材チェックツールで検証する）。

### 5.2 テストケース

- 3 件以上用意する。
- 境界のケース（空・0・1 件・最大値など）を含める。
- `stdout` 方式の最初のテストケースは、問題文の「例」と同じにする。

### 5.3 章末復習レッスン

- 動画はなく、演習のみとする。
- 通常のレッスンより難易度を上げ、その章の複数の要素を組み合わせる問題にする。
- `multi` レイアウト（複数ファイル）を使ってよい。

### 5.4 解説

- 模範解答だけでなく、なぜそう書くのかを説明する。
- 「よくある間違い」には、その要素の `related_errors` に対応するエラーを含める。

## 6. 教材チェックツール

`tools/` に教材チェックツールを用意し、教材を追加・変更したら実行する。CI でも実行する。

| チェック項目 | 内容 |
|---|---|
| 構成 | `chapters.json` の全レッスンのディレクトリと必要なファイルが存在する。章末復習レッスン以外は、`video/` に `script.json`・`index.tsx`・`durations.json` と、すべての文の音声ファイルがある |
| 定義 | `lesson.json` が `content-format.md` §4 の形式に合っている。要素 ID が要素マスタに存在する |
| 既習要素 | `secondary_elements` の各要素が、そのレッスンにとって既習の要素である |
| 要素マスタ | `deprecated` でない要素は、いずれかのレッスンの `primary_elements` に含まれている |
| 台本 | `script.json` が `content-format.md` §5.2 の形式に合っている（ID の重複がないこと、文の並び、`say` が 140 字以下であることを含む）。`code_blocks` が `content-format.md` §5.6 の行番号と Diff の決まりに合っている。`index.tsx` のシーンが台本の `scenes` と一致する |
| 音声 | すべての文に音声ファイルがあり、`durations.json` の `say`・`voice` が、台本の `say`・`content/voice.json` と同じである。台本にない文の音声ファイルと記録がない |
| lint | 動画のコードが `content-format.md` §5.8 に違反していない |
| 描画 | すべてのシーンをエラーなく描画できる。シーンごとに、最初のフレーム、各文の開始位置のフレーム、最後のフレームを描画する。台本にない文やほかのシーンの文を指す合図（`content-format.md` §5.4）と、制約に違反する `CodeBlock` の指定（`content-format.md` §5.6）は、ここでエラーになる |
| 表紙 | 最初のシーンが `LessonTitle` を 1 つ表示する（`content-format.md` §5.5） |
| 問題文・解説 | `content-format.md` §6.2・§6.3 の必須見出しがある |
| 模範解答 | 模範解答が判定ですべてのテストケースに通る（`exercise-runner.md` の判定処理を使う） |
| 初期コード | 初期コードが判定で正解にならない |
| テストケース | 3 件以上ある。`test` 方式では `case_labels` のキーが `judge_tests.rs` のテスト関数名と一致する |
| クレート | `dependencies` が許可クレートの一覧にある |

次の項目は警告とする。警告は結果に表示し、エラーにしない（CI を失敗にしない）。

| 警告の項目 | 内容 |
|---|---|
| 動画の長さ | 動画の長さ（`content-format.md` §5.4）が 1〜5 分の範囲にない |
| 文の長さ | `text` が 60 字を超える文がある |
| 読み | `say` に、読みの対応表（`content/readings.json`）の語がそのまま残っている |

## 7. レビューのチェックリスト

機械的に検証できない項目は、教材のレビュー時に確認する。

- [ ] 未登場の構文・関数・型を使っていない（§3）
- [ ] 画面の見出しが、そのとき伝えていることを言い切る文になっている（§4.3）
- [ ] ライト・ダークのどちらのテーマでも、動画の文字と図が読める
- [ ] 音声を聞いて、`say` の読み間違いと不自然な間がない（§4.2）
- [ ] 合図が言葉に合っている（§4.7）
- [ ] 寄せ方、文字の大きさ、動き、1 画面に載せる量が、動画のデザインシステムの「動画の原則」に従っている（§4.7）
- [ ] 再生位置を途中に移しても、その位置の絵が正しく表示される（`content-format.md` §5.5）
- [ ] 画面に出すコードを TSX に書き写していない（`content-format.md` §5.6）
- [ ] エラーをエラーコードだけで説明していない（§4.5）
- [ ] 文で指した行番号が、表示される行番号と合っている（§4.4）
- [ ] 図の中にコード（文や式）を書いていない（§4.6）
- [ ] 問題文にヒントやコード例が含まれていない
- [ ] 問題文だけで入出力の形式が一意に決まる
- [ ] 主要素を理解していないと解けない問題になっている
- [ ] 解説の「よくある間違い」が実際のエラーメッセージと一致している

## 8. 未決事項

- 章立て（`chapters.json`）と要素マスタ（`elements.json`）の内容は、作成者が別途用意する。
- 検索ワード（`lesson.json` の `tags`）に書く語の選び方（語の数、英語の表記や記号・エラーコードを含めるか など）。
