# 教材作成ガイドライン

教材（スライド・演習）を作るときの内容面のルールを定める。ファイル形式は `content-format.md` に従う。
AI で教材を作る場合も、このガイドラインを指示として与える。

## 1. 想定する学習者

- 他のプログラミング言語の経験がある人を対象とする。
- 変数・条件分岐・ループ・関数といった一般的な概念は知っている前提で、Rust の文法と Rust 固有の概念（所有権・借用・ライフタイム・トレイトなど）の説明に集中する。
- 他言語との違いが躓きの原因になりやすい箇所は、違いを明示して説明する。

## 2. カリキュラム

- 章立てと学習順は `content/chapters.json` に定める（作成者が別途用意する）。
- 1 レッスンはなるべく Rust の単独の要素のみを主要素とする（多くても 2 つ）。
- 各章の最後に、その章で学んだ内容を復習する章末復習レッスンを置く。

## 3. 未登場の要素を使わない

- レッスン（スライド・演習・解説）には、そのレッスンの主要素と既習の要素以外を登場させない。
- 既習の要素と導入レッスンの定義は `content-format.md` §2 に従う。
- `secondary_elements` には既習の要素だけを書く（教材チェックツールで検証する）。
- コード中の構文が未登場でないことは、レビュー時にチェックリスト（§7）で確認する（教材チェックツールでは検証しない）。
- どうしても未学習の構文が必要な場合（例: 標準入力の読み込み）は、「今はおまじないとして使う。詳しくは第 N 章で学ぶ」と明記し、`starter/` の中に完成した形で用意する。

## 4. スライド

### 4.1 構成

- 1 レッスンあたり 3〜8 枚を目安とする。
- 1 枚のスライドで伝えることは 1 つにする。`h1` は、そのことを言い切る文にする（例: 「代入すると、所有権が移る」。「ムーブ」のような名詞だけの見出しにしない）。ただし、表紙（`title`）の `h1` はレッスン名、まとめ（`summary`）の `h1` は「このレッスンのまとめ」のような見出しでよい。
- 1 枚に載せる量（文字数、コードの行数と 1 行の長さ、レイアウトごとの量）は、スライドのデザインシステム（`screens.md` §10.1）の README「レイアウトごとの容量」に従う。
- 最初のスライドは `title` レイアウトの表紙にする。`h1` は `lesson.json` の `title` と同じにする。
- 最後のスライドは `summary` レイアウトでまとめる。まとめには、このレッスンで分かったことを書き、感想にしない。
- 演習の答えに直結する完成コードはスライドに載せない。
- スライドだけでは伝えにくい背景知識は `aside.ai-note` に書いておくと、質疑応答の精度が上がる。

### 4.2 文章

- `p` と callout の文は「です・ます」調とする。`h1`・`h2`・`li`・表・図の中の語句は、言い切りの常体（「〜が移る」）か体言止めでもよい。
- 和文と英数字の間に半角スペースを入れる（「String を代入」「15 行まで」）。
- 表紙の `p`（サブタイトル）と箇条書きの項目には句点を付けない。1 つのリストの中では、項目の文末（常体・体言止めなど）をそろえる。
- callout の文に「注意:」「ポイント:」のような前置きを書かない（種類はアイコンと色で示される）。
- 表を載せるときは、表から何を読み取ってほしいのかを、表の前後の文か callout で書く。
- 文中で `code` で囲むのはコード片だけとする。コード片は、記号・括弧・`::` を含むもの（`&s`、`clone()`、`String::from`、`"hello"`）と、キーワード（`let`、`mut`、`fn`）である。変数名・型名・クレート名だけ（s1、String、i32）は囲まない。`h1` では `code` を使わない。表で型や式を並べる列は、そろえるためにすべて `code` で囲む。

### 4.3 コード

- 注目させたい字句は `span.mark` で強調する。行全体を強調しない。
- 他の言語との違いを見せるときは `two-column` で左右に並べる（左に他の言語、右に Rust）。
- コードブロックには行番号が表示される（`content-format.md` §5.4）。文でコードの行を「6 行目」のように行番号で指してよい。コード片（「`println!` の行」）や、`span.mark`・枠のラベル（「r の枠」）で指してもよい。
  - 行番号は、表示される番号（ファイルの行番号）で書く。
  - ファイルの途中から載せるときは `data-start-line` を書き、ファイルの行番号やコンパイラの出力の行番号とそろえる。`data-label` にファイル名を書く。関数の途中から載せてもよい。
  - Diff の行は変更後の行番号で指す。削除行には行番号がないので、コード片（「`let s2 = s1;` を消す」）で指す。
- Diff では、置き換える行は削除行を先に、追加行を後に書く。

### 4.4 エラー

- コンパイルエラーを説明するときは、コードブロックの中のエラーの箇所を `span.error` で示す。そのエラーをレッスンで初めて説明するスライドでは、実際のコンパイラの出力も `language-text` のコードブロックで示す。同じエラーに再び触れるスライドでは、出力を省き、波線と言葉の説明だけでもよい。
- エラーをエラーコードだけで説明しない。本文・callout・見出し・図・コードのコメント・画像の `alt` でエラーを指すときは、何が起きたのかを言葉で書く（例: 「ムーブ済みの値を使ったエラー」「借用している値が先に破棄されるエラー」）。エラーコードは、言葉の説明に括弧書きで添えるときだけ使う（例: 「ムーブ済みの値を使ったエラー（E0382）」）。コンパイラの出力の中のエラーコードは、そのままでよい。

### 4.5 図

- 所有権の移動・参照・メモリ配置など目に見えない仕組みは、図（`figure.diagram`）で示す。
- コード（文や式）は図（SVG）の中に書かず、コードブロックに書く。図の中に書くのは、変数名・型名・値と、`&s`・`'a` のような 1 語の短いラベルだけにする。図の説明（`figcaption`）は図の外の文なので、§4.2 に従ってコード片を `code` で囲んで書いてよい。図とコードを 1 枚に並べるときは `two-column` を使い、片方の列にコードブロック、もう片方の列に図を置く。
- 変数が生きている範囲・スコープは図にせず、コードブロックに `data-scopes` で枠を重ねて示す。

## 5. 演習

### 5.1 問題

- ヒントやコード例は問題文に書かない（入出力例・呼び出し例は書く）。
- 主要素を正しく理解していないと解けない問題にする。少し考えないと解けない難しさを目安とする。
- 過去のレッスンで学んだ要素を取り入れる。
- 入力・出力の形式は、曖昧さがないように厳密に書く（区切り文字、末尾の改行、空の入力の扱いなど）。
- 初期コードには、問題の本質ではない部分（入力の読み込みなど）を用意しておく。
- 初期コードのままでは正解にならないこと（教材チェックツールで検証する）。

### 5.2 テストケース

- 3 件以上用意する。
- 境界のケース（空・0・1 件・最大値など）を含める。
- `stdout` 方式の最初のテストケースは、問題文の「例」と同じにする。

### 5.3 章末復習レッスン

- スライドはなく、演習のみとする。
- 通常のレッスンより難易度を上げ、その章の複数の要素を組み合わせる問題にする。
- `multi` レイアウト（複数ファイル）を使ってよい。

### 5.4 解説

- 模範解答だけでなく、なぜそう書くのかを説明する。
- 「よくある間違い」には、その要素の `related_errors` に対応するエラーを含める。

## 6. 教材チェックツール

`tools/` に教材チェックツールを用意し、教材を追加・変更したら実行する。CI でも実行する。

| チェック項目 | 内容 |
|---|---|
| 構成 | `chapters.json` の全レッスンのディレクトリと必要なファイルが存在する。章末復習レッスン以外は `slides.html` がある |
| 定義 | `lesson.json` が `content-format.md` §4 の形式に合っている。要素 ID が要素マスタに存在する |
| 既習要素 | `secondary_elements` の各要素が、そのレッスンにとって既習の要素である |
| 要素マスタ | `deprecated` でない要素は、いずれかのレッスンの `primary_elements` に含まれている |
| スライド | `content-format.md` §5.3〜§5.6 に違反していない（コードブロックの属性の制約を含む）。各スライドに `h1` がある |
| 問題文・解説 | `content-format.md` §6.2・§6.3 の必須見出しがある |
| 模範解答 | 模範解答が判定ですべてのテストケースに通る（`exercise-runner.md` の判定処理を使う） |
| 初期コード | 初期コードが判定で正解にならない |
| テストケース | 3 件以上ある。`test` 方式では `case_labels` のキーが `judge_tests.rs` のテスト関数名と一致する |
| クレート | `dependencies` が許可クレートの一覧にある |

## 7. レビューのチェックリスト

機械的に検証できない項目は、教材のレビュー時に確認する。

- [ ] 未登場の構文・関数・型を使っていない（§3）
- [ ] 1 枚のスライドで 1 つのことだけを伝えている
- [ ] 図の色がテーマのクラスで指定され、ダークモードでも読める
- [ ] エラーをエラーコードだけで説明していない（§4.4）
- [ ] 文で指した行番号が、表示される行番号と合っている（§4.3）
- [ ] 図の中にコード（文や式）を書いていない（§4.5）
- [ ] 問題文にヒントやコード例が含まれていない
- [ ] 問題文だけで入出力の形式が一意に決まる
- [ ] 主要素を理解していないと解けない問題になっている
- [ ] 解説の「よくある間違い」が実際のエラーメッセージと一致している

## 8. 未決事項

- 章立て（`chapters.json`）と要素マスタ（`elements.json`）の内容は、作成者が別途用意する。
