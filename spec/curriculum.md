# カリキュラム 仕様書

章立てと学習順、各レッスンで主に扱う内容を定める。
教材の作成ルールは `content-guidelines.md`、アプリが読む章とレッスンの並びの形式は `content-format.md` §2 に定める。

## 1. 目的・スコープ

- 作成する章とレッスン、その学習順、各レッスンで主に扱う内容を定める。
- 章とレッスンの ID・タイトル、章の説明、学習順は、この仕様書を唯一の定義とする。`content/chapters.json` と各レッスン（章末復習レッスンを除く）の `lesson.json` の `title` は、これに合わせる（§6）。
- 各レッスンの主要素・副要素（要素 ID）は、レッスンを作るときに `lesson.json` に定める。この仕様書では「主に扱う内容」として範囲だけを示す。

## 2. 方針

- 1 レッスンの主要素の数と章末復習レッスンの置き方は `content-guidelines.md` §2 に従う。
- 想定する学習者（`content-guidelines.md` §1）に合わせ、Rust 固有でない内容（`while`、イテレータの汎用的なアダプタなど）はまとめて扱い、Rust 固有の内容（所有権・借用・パターン・ライフタイムなど）は細かく分ける。
- The Rust Programming Language（以下 TRPL）を、扱う内容の網羅の目安とする。章立て・順序・題材は独自に組み立て、TRPL の文章・コード・題材のプログラム（数当てゲーム、minigrep、Web サーバーなど）は使わない。

## 3. 章とレッスンの一覧

章の見出しは「章 ID + 章のタイトル」、見出しの下の文は章の説明（`chapters.json` の `description`）である。章の並びが章の学習順、表の並びが章の中の学習順である。
章末復習レッスンのタイトルはここでは定めず、表では「章末復習」と書く。

## 5. 演習の作り方の注意

レッスンごとに演習を作るときに、判定方式（`exercise-runner.md`）から来る制約で注意が必要な箇所。

| 箇所 | 制約 | 対応 |
| --- | --- | --- |
| ch01〜ch02 | 関数が未習なので `stdout` 方式しか使えない。標準入力の読み込みも未習 | 入力のない、出力が固定の演習にする。「コンパイルエラーになるコードを直す」「途中まで書かれたコードを完成させる」のように、主要素を使わないと解けない問題にする。テストケースの件数は §7 |
| ch03〜ch08 | 標準入力の読み込み（ch09-05）が未習 | `test` 方式（隠しテストが関数を呼ぶ）を中心にする。`stdout` 方式で入力が要る場合だけ、おまじない（`content-guidelines.md` §3）を使う |
| ch09-01 panic | `stdout` 方式では panic が `runtime_error`（`exercise-runner.md` §4.3）になり、「正しく panic する」ことを判定できない | `test` 方式の隠しテストで `#[should_panic]` を使う |
| ch09-06・ch19 の main から Err を返す演習 | 終了コード 0 以外は `runtime_error` になる | `fn run() -> Result<..>` を実装させ、`test` 方式で判定する |
| ch08-08〜ch08-10 HashMap・HashSet | 走査の順序が実行ごとに変わる | キーを指定して引く問題にする、またはキーを `Vec` に集めて `sort` してから出力させる（`collect` は ch15 なので `for` で `push`） |
| ch10-06 rand | 乱数の出力は `stdout` 方式で判定できない | `test` 方式で、値が範囲に入っていることや個数を検査する。`rand::random_range` を使えば、トレイト（ch12）を使わずに済む |
| ch10-05・ch10-06 | パッケージ名は `progrust_exercise` に固定で、`Cargo.toml` はアプリが生成し、学習者は編集できない（`exercise-runner.md` §3） | ライブラリは `use progrust_exercise::...` で使う。`[dependencies]` は動画で見せるだけにする |
| ch20・ch21 | 出力の順序が非決定的になりやすい | `join` の後にまとめて出力する、チャネルで集めてから並べ替える、待ち時間の差を十分に取る（1 ケースの制限時間内で） |
| ch11 | 学習者が書いたテストの判定方法が決まっていない | §7 |

## 7. 未決事項

- **ch11 テストの演習の判定方法**: 今の仕様では、実行（`exercise-runner.md` §4）は `cargo build` と実行だけを行い、提出の判定（`exercise-runner.md` §5.2）は学習者が書いたテストを含めない。学習者が自分で書いたテストを `cargo test` で実行できるようにする方針だが、次のことが決まっておらず、仕様書にもまだ反映していない。決まるまで ch11 の演習は作れない。
  - 画面での実行方法（テスト実行のボタンを別に置くか、実行ボタンの動作をレッスンで切り替えるか）
  - 判定方法（例: 学習者が書いた `#[test]` が N 件以上あり、すべて通ること。学習者のテストが実装の誤りを検出できるかまで判定するか）
  - 統合テスト（`tests/` ディレクトリ）を書けるようにするか。今はエディタから受け取るパスを `src/` 以下に限っている（`exercise-runner.md` §3）
  - ドキュメントテストを実行するか（`src/lib.rs` がある演習でのみ動く）
  - 決め方によっては、統合テスト（ch11-05）とドキュメントテスト（ch11-06）のレッスンを外す。
- **許可クレートの追加**: レッスンで使う外部クレートはすべて許可クレート（`exercise-runner.md` §2.1）に入れる方針だが、ch19・ch21 で使う次のクレートはまだ一覧になく、固定するバージョンも決まっていない。`tokio` を加えると、初回準備の時間とディスク使用量が増える。

  | クレート | 使う章 | 用途 |
  | --- | --- | --- |
  | `thiserror` | ch19-05 | 独自のエラー型の定義 |
  | `anyhow` | ch19-06 | アプリケーションのエラー処理 |
  | `tokio` | ch21 | 非同期ランタイム |
  | `futures` | ch21-03・ch21-07 | `join_all`、ストリーム |
  | `tokio-stream` | ch21-07 | ストリーム（紹介程度） |

- **Rust の最低バージョン**: ch07-08 の let チェーンは Rust 1.88 以降の機能で、今の最低バージョン（rustc 1.85 以上: `non-functional.md` §1、`architecture.md` §3.1）では使えない。最低バージョンをアプリのリリースごとにその時点の最新の stable に上げる方針だが、仕様書には未反映である。バージョンが足りないときの案内（`rustup update stable` を案内するか）も決まっていない。
- **ch01〜ch02 のテストケースの件数**: §5 のとおり出力が固定の演習になるため、テストケースを 1 件でよい例外にする方針だが、例外を章（ch01〜ch02）で決めるか、「関数が未習のレッスン」のような条件で決めるかが決まっておらず、`content-guidelines.md` §5.2・§6（3 件以上）には未反映である。
- **標準入力のおまじないの定型**: ch03〜ch08 で `stdout` 方式の演習に入力が要る場合に決める（ch01〜ch02 では使わない）。
