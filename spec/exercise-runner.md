# コード実行・判定 仕様書

演習のコードをビルド・実行し、正誤を判定する仕組みを定める。
判定方式とテストケースの形式は `content-format.md` §6.4 に従う。

## 1. 概要

- 学習者の環境にある `cargo` を使ってビルド・実行する（検出方法は `architecture.md` §3）。
- すべての演習は edition 2024、dev プロファイルでビルドする。
- 学習者による実行・提出は同時に 1 つだけ行う。処理中は実行ボタンと提出ボタンを無効にする。生成問題の検証は別のプロジェクト（`validate/`）で行い、学習者の実行と並行して行える。
- 学習者のコードはサンドボックスに入れず、学習者のユーザー権限で実行する（`non-functional.md` §4）。

## 2. 許可クレートと作業領域

### 2.1 許可クレート

演習で使える外部クレートはリポジトリの `runner/allowed-crates.toml` に定める。

```toml
[dependencies]
rand = "=0.9.1"
```

- 書式は `Cargo.toml` の `[dependencies]` と同じとし、バージョンは `=` で固定する。
- この一覧から生成した `runner/Cargo.lock` もリポジトリに置き、アプリに同梱する。
- クレートを追加・変更したら `Cargo.lock` を作り直す。

### 2.2 作業領域

```
{app_data_dir}/workspace/
├── prepared.json      # 初回準備の状態
├── warmup/            # 初回準備用のプロジェクト（全許可クレートに依存）
├── project/           # 実行・提出のたびに組み立てるプロジェクト
├── validate/          # 生成問題の検証用プロジェクト（exercise-generation.md §4.2）
├── target/            # 許可クレートを使う演習のビルド先（初回準備と共有）
└── target-std/        # 許可クレートを使わない演習のビルド先
```

- ビルド先は `CARGO_TARGET_DIR` で指定する。許可クレートを使う演習は初回準備でビルド済みの依存を再利用できる。
- 許可クレートを使わない演習は `target-std/` にビルドし、初回準備中でも待たずにビルドできる。
- クレートのダウンロード先（レジストリのキャッシュ）は学習者の環境の既定（`CARGO_HOME`）を使う。

### 2.3 初回準備

**実行する条件**（アプリ起動時に判定する）

- `prepared.json` がない
- `prepared.json` の `crates_hash`（`allowed-crates.toml` と `Cargo.lock` のハッシュ値）が同梱のものと異なる
- `prepared.json` の `status` が `failed`

**手順**

1. `warmup/` に、全許可クレートに依存する `Cargo.toml`、同梱の `Cargo.lock`、空の `src/main.rs` を作る。
2. `cargo build` と `cargo test --no-run` を実行する（ネットワークが必要）。ビルド先は `target/`。
3. 成功したら `prepared.json` に `status: ready` と `crates_hash`・`prepared_at` を書く。失敗したら `status: failed` と エラー内容を書き、次回起動時に再度実行する。

**準備中・失敗時の動作**

- 許可クレートを使わない演習は通常どおり実行・提出できる。
- 許可クレートを使う演習は、実行・提出ボタンを無効にし、「クレートを準備しています」「クレートの準備に失敗しました（ネットワーク接続を確認してください）」と表示する。失敗時は再試行ボタンを表示する。
- 準備の状態は `environment_updated` イベントで通知する。

## 3. プロジェクトの組み立て

実行・提出のたびに `project/` を空にしてから、以下を作る。

| ファイル | 内容 |
|---|---|
| `Cargo.toml` | パッケージ名 `progrust_exercise`、edition 2024。`[dependencies]` には演習の `dependencies` に挙げたクレートだけを `allowed-crates.toml` の指定のまま書く |
| `Cargo.lock` | 同梱の `Cargo.lock` をコピーする |
| `src/**` | エディタ上の全ファイル |

- エディタから受け取ったファイルパスは、`src/` 以下で拡張子が `.rs` の相対パスに限る。`..` を含むパスや絶対パスは拒否する。
- ビルドには `--offline` を付ける。依存が見つからないエラーになった場合は初回準備をやり直す（§2.3）。
- 環境変数 `RUST_BACKTRACE=0` を設定する。

## 4. 実行（run）

### 4.1 手順

1. `cargo build --offline --message-format=json-diagnostic-rendered-ansi` でビルドする。
2. ビルドに失敗したら、コンパイラの診断を表示して終了する（`compile_error`）。
3. 成功したら、生成された実行ファイルを `project/` を作業ディレクトリとして起動する。
4. 標準出力・標準エラー出力を `run_output` イベントで逐次送る。
5. 終了したら `run_finished` イベントで結果を送り、試行ログに `run` イベントを追記する（§7）。

- 演習には必ず `src/main.rs` があるものとする（`content-format.md` §6.1）。
- コンパイラの警告も表示する。cargo 自身の進捗メッセージ（`Compiling ...` など）は表示しない。

### 4.2 対話的な標準入力

- 実行中、コンソールの下部に入力欄を表示する。
- Enter で入力した 1 行に改行を付けてプログラムの標準入力に送り（`send_stdin`）、コンソールにも入力として区別できる色で表示する。
- 「入力終了」ボタン（または Ctrl+D）で標準入力を閉じる（`close_stdin`）。
- プログラムが終了したら入力欄を無効にする。

### 4.3 結果の状態

| 状態 | 条件 |
|---|---|
| `success` | 終了コード 0 で終了した |
| `compile_error` | ビルドに失敗した |
| `runtime_error` | 終了コードが 0 以外、またはシグナルで終了した（panic を含む）。出力量の上限を超えて停止した場合も含む |
| `timeout` | 制限時間を超えたため停止した |
| `stopped` | 学習者が停止ボタンを押した |

## 5. 提出（submit）

提出中はコンソールにビルドの診断と判定の進み具合だけを表示し、プログラムの出力は表示しない。

### 5.1 stdout 方式

1. §4.1 と同じ方法でビルドする。失敗したら `compile_error` で終了する。
2. テストケースごとに実行ファイルを起動し、`stdin` を書き込んで標準入力を閉じ、標準出力を受け取る。
3. 正規化した標準出力を `expected_stdout` と比較する。
4. 1 件失敗しても残りのテストケースはすべて実行する。

**正規化**: 改行コード（CRLF → LF）をそろえ、各行の末尾の空白と、末尾の空行を取り除く。期待値にも同じ正規化をかける。

### 5.2 test 方式

1. `judge_tests.rs` を `project/progrust_judge_tests.rs` に置く。
2. `judge.target` のファイルの末尾に以下を追加する。

   ```rust
   #[cfg(test)]
   #[path = "../progrust_judge_tests.rs"]
   mod progrust_judge;
   ```

3. `cargo test --offline --no-run --message-format=json-diagnostic-rendered-ansi` でビルドする。失敗したら `compile_error` で終了する。隠しテストの側でエラーが出た場合は、「問題文で指定された関数名・型・シグネチャを確認してください」と併せて表示する。
4. テスト実行ファイルを、引数 `progrust_judge::` で起動する（学習者自身が書いたテストは判定に含めない）。
5. 出力の `test progrust_judge::{関数名} ... ok|FAILED` を読み取り、テストケースごとの結果とする。失敗したテストの panic メッセージを詳細として取り出す。

### 5.3 判定結果

| 項目 | 内容 |
|---|---|
| `status` | `passed`（全テストケース通過）/ `wrong`（1 件以上失敗）/ `compile_error` |
| `passed` / `total` | 通過したテストケース数 / 全テストケース数 |
| `cases[]` | テストケースごとの `name`（表示名）・`status`（`pass` / `fail` / `timeout` / `runtime_error`）・`detail` |

`detail` の内容:

- stdout 方式の `fail`: 入力・期待する出力・実際の出力
- test 方式の `fail`: panic メッセージ（`assert_eq!` の左辺・右辺を含む）
- `timeout` / `runtime_error`: 標準エラー出力の先頭

画面には、通過数と失敗したテストケースの名前をすべて表示し、最初に失敗したテストケースの `detail` を表示する。

## 6. 制限値

| 項目 | 値 | 超えた場合 |
|---|---|---|
| ビルド時間 | 120 秒 | 中断し、`compile_error` としてタイムアウトの旨を表示 |
| 実行時間（run） | 60 秒 | 停止して `timeout` |
| 出力量（run） | 標準出力と標準エラー出力の合計 1 MB | 停止して `runtime_error`。上限で停止した旨を表示 |
| 1 テストケースの実行時間（stdout 方式） | 5 秒 | そのテストケースを `timeout` |
| テスト全体の実行時間（test 方式） | 10 秒 | 停止し、終わっていないテストケースを `timeout` |
| 1 テストケースの出力量（stdout 方式） | 64 KB | そのテストケースを `fail`（出力過多） |

## 7. 試行ログへの記録

実行・提出が終わるたびに、試行ログに `run` / `submit` イベントを追記する。スキーマは `learning-record-and-analysis.md` §3.2 に従う。

- `error_codes` は、ビルドの JSON 出力のうちレベルが `error` の診断の `code` から取り出す（重複除去・出現順）。
- `stdout` / `stderr` はそれぞれ先頭 20,000 文字までを保存する。`stderr` にはコンパイラの診断（ANSI エスケープを除去したもの）とプログラムの標準エラー出力を、この順に連結して保存する。
- `run` イベントの `stdin` には、学習者が入力した内容をそのまま連結して保存する。

## 8. 受け入れ条件

- 初回準備が終わった後は、ネットワークを切断した状態でも許可クレートを使う演習を実行・提出できる。
- 初回準備中でも、許可クレートを使わない演習はすぐに実行できる。
- `loop {}` を実行すると 60 秒で停止し、`timeout` になる。
- 無限に出力するプログラムを実行すると、1 MB で停止し、アプリが固まらない。
- 実行中に入力欄から入力した行を、プログラムが `stdin().read_line` で受け取れる。
- `stdout` 方式で、期待値と行末の空白だけが異なる出力は正解になる。
- `test` 方式で、学習者が自分で書いた `#[test]` が失敗していても、判定には影響しない。
- `test` 方式で判定した後も、エディタ上の学習者のコードは変更されない。
- `../` を含むファイルパスを送っても、`project/` の外にファイルが書かれない。
