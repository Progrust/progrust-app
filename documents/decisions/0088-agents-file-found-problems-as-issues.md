## 背景

ユーザーは次のように求めた。

- 「AIエージェントが作業中に不具合や問題点、課題（ソースコードやドキュメントなどなんでも）を見つけたときに、GitHubのIssueを起票できるようにしたいです。」
- 「Issueには原因の調査や具体的な改善案などは不要で、何が問題なのかが書かれていればOKです。」
- 「迷ったらIssueを追加してOKで、ユーザーへの確認は不要です。」
- 「作成されたIssueを対応するかどうかは、私が決めます。」
- 「このようなIssueを管理しやすくするために、Issueのラベルをいくつか作成しておいてください。」

Claude が理由を尋ねると、ユーザーは、起票したい理由として次の3つを選んだ（選択肢は Claude が示した）。

- 本来の作業を脱線させない: 見つけた問題をその場で直そうとすると、頼んだ作業から外れてしまう。
- 会話の中で流れて失われる: 作業中に AI が見つけた問題が、応答の中で触れられるだけで記録に残らず、忘れられてしまう。
- 対応の判断を自分がしたい: 問題を直すかどうか、いつ直すかは、ユーザーが一覧を見て決めたい。

原因の調査や改善案を書かなくてよい理由と、確認なしで起票してよい理由として、ユーザーは次の2つを選んだ。

- 起票の手間を小さくしたい: 調査や確認に時間を使うと本来の作業が遅れる。起票を気軽にして、見つけた問題を取りこぼさないことを優先する。
- 調査は対応するときでよい: 対応すると決めた Issue だけ、そのときに調べればよい。対応しない Issue の調査は無駄になる。

それまでの運用ルール（`conventions/`）は、`documents/` の中の文書の書き方だけを扱っていた（0080）。Issue の起票の決まりはソースコードなどの問題も扱うので、どこに置くかを決める必要があった。

## 決定

- AI エージェントは、作業中に見つけた問題を、原因の調査や改善案の検討をせずに、ユーザーに確認せずに GitHub の Issue に起票する。迷ったら起票する。対応するかどうかはユーザーが決める。決まりは [Issue の起票](../conventions/issues.md) に定め、`CLAUDE.md` からそこを指す。ユーザーの求めによる。
- 決まりは `conventions/` に置き、`Convention` の範囲を、`documents/` の中の文書の書き方と、AI エージェントの Issue の起票の決まりに広げる。0080 の「`Convention` は `documents/` の中の文書の書き方だけに使う」を、この範囲に変える。Claude が置き場所の案を示し、ユーザーがこの案を選んだ。
- 次の細部は Claude が決めた。ラベルはユーザーが作成を任せた。
  - 頼まれた作業の範囲の中の問題は起票せずに直し、範囲の外の問題と、範囲の中でも直さなかった問題を起票する。理由: 範囲の中の問題を直すことは頼まれた作業の一部で、範囲の外の問題を直すと本来の作業から外れる。直さなかった問題も起票しないと、会話の中で失われる。
  - 起票した問題は、ユーザーに頼まれるまで直さない。理由: 対応の判断はユーザーがする。
  - 起票する前に、閉じた Issue も含めて検索して重複を避ける。閉じた Issue があれば起票しない。理由: 1回の検索で済み、起票の手間をほとんど増やさない。閉じた Issue を検索から外すと、ユーザーが対応しないと決めて閉じた問題が、また起票される。
  - 応答の最後に、起票した Issue を書く。理由: ユーザーが確認しなくても、何が起票されたかを知ることができる。
  - ラベルは、AI エージェントが起票したことを示す `AI起票`、対応するかをまだ決めていないことを示す `未判断`、種類を示す `不具合`・`仕様`・`ドキュメント`・`改善` の6つにする。理由: `AI起票` で、ユーザーが管理する `技術検証`・`確認事項` の Issue と分けて一覧できる。`未判断` で、ユーザーが判断を済ませた Issue と分けられる。種類で、対応の判断に要る分野が分かる。

## 検討した他の案

- 案: `documents/` のルートに新しいディレクトリを作り、そこに置く
  - 採用しなかった理由: ルートを3つのディレクトリにする構成と、`type` の6つの語彙も変わり、変更が大きくなる。ユーザーが `conventions/` の範囲を広げる案を選んだ。
- 案: `CLAUDE.md` だけに書き、`documents/` には書かない
  - 採用しなかった理由: ユーザーが、ドキュメントに決まりを書くことを求めた。
- 案: Issue に原因の調査や改善案も書く、または起票の前にユーザーに確認する
  - 採用しなかった理由: ユーザーが挙げた理由（「背景」を参照）。

## 影響

- AI エージェントが起票した Issue は、`AI起票` と `未判断` で一覧できる。ユーザーは、対応すると決めた Issue から `未判断` を外し、対応しない Issue を閉じる。
- 起票の手間を小さくしたので、Issue の数は増え、対応しない Issue も混じる。その分は、ユーザーが閉じる。
- Issue には原因も改善案も書かれていないので、対応するときに調べ直す必要がある。
- 起票には `gh` が使える必要がある。使えないときは、起票しようとした内容を応答で伝える。
