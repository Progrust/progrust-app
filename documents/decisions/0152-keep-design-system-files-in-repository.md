## 背景

デザインシステム「Progrust」「Progrust Video」は、claude.ai の「Design System」の種類のアーティファクトで、リポジトリの外にあった（[ADR 0044](0044-design-system-as-source-of-visuals.md)、[ADR 0075](0075-video-design-system-progrust-video.md)）。ドキュメントを `documents/` に集約したときも、デザインシステムは扱わなかった（[ADR 0079](0079-manage-documents-as-okf-bundle.md)）。

Issue #67 の「背景」には、リポジトリの外にあることで起きていたこととして、次のことが挙がっている。

- Issue #20 の技術検証で、デザインシステムは `documents/` に無いので読んでいない、と記録された。
- Issue #60・#61・#62 の対応では、アーティファクトだけを直した。仕様の変更と同じコミットに入らなかった。
- Issue #61 の、いまは無い仕様のファイルへの参照（23 か所）は、`python3 tools/check-documents.py` では見つけられなかった。
- Claude Code の調査用のサブエージェント（Explore、Plan）と CI は、アーティファクトを読めない。
- 同じ値の写しを手で合わせている（「Progrust Video」が持つ「Progrust」の共通の値の写しと、画面デザイン「Progrust UIデザイン」の中の、2 つのデザインシステムの写し）。

2026-11-22、ユーザーは、デザインシステムと画面デザインをリポジトリに移すかどうかを Claude に相談した。Claude は Issue #67 の「提案した方針」を勧め、ユーザーの依頼で Issue #67 を起票した。

同じ日、Issue #67 の起票の後に、[ADR 0151](0151-copy-design-system-css-into-repository.md) を追加した。ADR 0151 は、デザインシステムがリポジトリの外にあることを前提に、CSS とアイコンを `src/design-system/` に写して使うと決めた。「写しをリポジトリで編集し、リポジトリの写しを正とする」案は採用しなかった。その理由は、値はデザインシステムを唯一の定義とすること（ADR 0044）と、ユーザーが見て確かめる場所もデザインシステムであることだった。

同じ日、ユーザーは Issue #67 の対応を頼み、「方針は提案通りで大丈夫です。」と示した。Claude は、移す理由をユーザーに尋ねた。選択肢は、Claude が Issue #67 の「背景」から言葉にした次の 3 つと、自由記入だった。

- 「変更を Git で管理したい」: デザインシステムの変更が、仕様の変更と同じコミットに入り、いつ・なぜ変えたかが Git の履歴に残るようにしたい
- 「AI と検査から読めるようにしたい」: Claude Code のサブエージェントや CI、ドキュメントの検査が、デザインシステムを読めるようにしたい
- 「手で合わせる写しを減らしたい」

ユーザーは「AI と検査から読めるようにしたい」「変更を Git で管理したい」の 2 つを選び、自由記入に「このアプリでしか使わないのでわざわざアーティファクト側にする理由もないため」と書いた。

同じ日、Issue #67 の「すること」の 1 のとおり、試し用のアーティファクトで次のことを確かめた。Claude のサブエージェントが実行し、Claude が、アーティファクトのファイルの一覧とページのスクリーンショットで確かめた。

- 「Progrust」の `project/` の下の 110 ファイルとアイコン 29 個を、手元のファイルから試し用のアーティファクトへ送ると、ファイルごとの sha256 とバイト数が全件一致した。ページの表示（表紙、README、色の表、部品のカード、アイコンの一覧）は、本物と同じだった。
- ページは、開いただけではファイルを書かない。`project/api/` と `project/manifest.json` は、本物にも試し用にも無い。
- `tokens.json` だけを変えて送ると、ページの表示は新しい値になるが、`tokens.css` のファイルは古いまま残る。ページは `tokens.css` を作り直さない。Design System の種類の説明では、ページがファイルを書くのは、人がページで保存したときだけである。
- 索引（`design-system.json`）に `"editing": "code"` を入れて送ると、ページは読み取り専用になる。値の入力欄と追加・削除のボタンが消え、上部に「読み取り専用」と、英語の 1 行「This design system is synced from code. To change it, edit the code, then run /design-sync in Claude Code.」が出る。この状態でも、Artifact ツールからの送信は通る。索引から外して送ると、編集できる状態に戻る。
- アイコンのアセットの id は、アーティファクトごとに別の値になる（中身からは決まらない）。
- `tokens.css` は、`tokens.json` から 1 バイトも違わずに作り直せる（2 つのデザインシステムの両方で確かめた）。

同じ日、本物の 2 つのアーティファクトへ、索引（`design-system.json`）だけを送った（ほかのファイルは同じ中身なので送っていない）。そのときに、次のことを確かめた。

- その会話でまだ読んでいないアーティファクトへの送信は、Artifact ツールに断られる。`path` を付けた read（索引だけを読む）のあとでも断られ、`url` だけの read をしてから送ると通った。`force` は使っていない。
- 公開ファイルは、read の `paths` に全部のパスを渡して 1 回で取得できた。アイコンは、`path` に id を渡して 1 つずつ取得し、`out_dir` の直下に `{id}.svg` の名前で保存された。
- 送った後に取得して比べると、リポジトリとの違いは、2 つのデザインシステムとも 0 件だった。ページは読み取り専用になり、表示は変わらなかった。ページは何もファイルを書いていない。
- 画面デザイン「Progrust UIデザイン」（種類は「Design」）の中の写し（`project/ds/` の下）は、ファイルを直接送って直すものではなかった。Design の種類の決まり（画面デザインのアーティファクトの `SKILL.md` と `artifact-type/reference/design-system-components.md`）では、`project/ds/` の下のファイルは、デザインシステムを入れる手順でだけ書く。その手順では、サーバーがデザインシステムのアーティファクトからファイルを写し、画面デザインの索引 `project/canvas.json` の `designSystems` の記録も置き換える。更新は、この手順をやり直す。

## 決定

- デザインシステム「Progrust」「Progrust Video」のファイルを、リポジトリの `design-system/progrust/`・`design-system/progrust-video/` に置き、リポジトリのファイルを正とする。アーティファクトは、リポジトリのファイルを送ったものとして残し、表示に使う（[デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md)「置き場所」「表示用のアーティファクト」）。
  - ユーザーが Issue #67 の方針を承認した。
  - 移す理由は、ユーザーが選んだ「AI と検査から読めるようにしたい」「変更を Git で管理したい」の 2 つ（Claude が言葉にした選択肢。「背景」を参照）と、ユーザーが自分の言葉で書いた「このアプリでしか使わないのでわざわざアーティファクト側にする理由もないため」である。
  - アーティファクトを残す理由（Claude の提案。Issue #67）: 部品の見本（`preview.html`）は、アーティファクトのページの中でしか表示できない。ユーザーが見て確かめる場所は、これまでどおりアーティファクトのページである。
- 置き場所は `documents/` の外にし、説明（`README.md`）・見本（`preview.html`）・CSS を分けずに、アーティファクトの `project/` の下と同じ形のまま置く（Claude の提案。Issue #67）。
  - 理由: `documents/` は `README.md` を置けず、すべての `.md` に frontmatter、`.md` のあるディレクトリに `index.md`、英小文字・数字・ハイフンだけの名前を求める（[ドキュメントの検査](../conventions/checks.md)）。デザインシステムのファイルは、`README.md` や `components/AppHeader/README.md` のように、Design System の種類が形を決めている。
- 「値はデザインシステムを唯一の定義とし、仕様書には書かない」（ADR 0044）と、2 つのデザインシステムを分けること・画面と共通の値は「Progrust」を正とすること（ADR 0075）は変えない。変わるのは、デザインシステムの置き場所と、どちらを正とするかだけである。
- ADR 0151 が「写しをリポジトリで編集し、リポジトリの写しを正とする」案を採用しなかった理由（値の定義を 1 か所に保つこと、ユーザーが見て確かめる場所はデザインシステムであること）は、この形でも保たれる。リポジトリに置くのは写しではなくデザインシステムそのもので、値の定義は 1 か所のままである。ユーザーが見て確かめる場所も、リポジトリから送ったアーティファクトのページのままである。
- アーティファクトのページは読み取り専用にする（索引に `"editing": "code"`）。ページでは編集しない（Claude の判断）。
  - 理由: ページで編集すると、リポジトリのファイルと食い違い、次にリポジトリから送ったときに消える。決まりだけでなく、ページの側で編集できなくしておく。試しで、読み取り専用にしても表示が変わらず、外せば戻せることを確かめた。
- `tokens.css` は、リポジトリで `tokens.json` から作る（手で書かない）。作る道具と、食い違いを見つける検査を `tools/design-system.py` に持ち、検査を CI でも実行する（Claude の判断。[デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md)「検査」、[テストの方針](../spec/non-functional/testing.md)「CI」）。
  - 理由: ページは `tokens.css` を作り直さないことを、試しで確かめた。アプリは `tokens.css` を読み込むので、`tokens.json` と食い違うと、アプリの見た目とアーティファクトの表示が食い違う。
- デザインシステムを変えるときは、リポジトリのファイルを直してから、アーティファクトへ送り、送った後に、リポジトリとアーティファクトの中身が同じことを確かめる。画面デザイン「Progrust UIデザイン」が中に持つ写し（`project/ds/progrust/`・`project/ds/progrust-video/` の `tokens.css`・`tokens.json`・`components/bundle.css`）も、デザインシステムを変えたら取り直し、確かめる対象に含める（Claude の判断。[デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md)「変更の手順」）。
  - 理由（画面デザインの中の写し）: 各画面のレイアウトは、実装するまで画面デザインを正とする（[ADR 0150](0150-screen-layouts-follow-ui-design-until-implemented.md)）。その見た目は中の写しで決まるので、写しが古いと、ユーザーが見て確かめるものが古くなる。
  - 画面デザインの中の写しは、直接送って直さず、画面デザインの側の、デザインシステムを入れる手順をやり直して取り直す。理由: Design の種類の決まりでは、`project/ds/` の下のファイルは、その手順でだけ書く（「背景」を参照）。
- 画面デザイン「Progrust UIデザイン」は、アーティファクトのままにする。この判断では移さない（Issue #67 の方針のとおり）。

## 検討した他の案

- 案: デザインシステムのファイルを `documents/` の中に置く
  - 採用しなかった理由: `documents/` の検査の決まりと、Design System の種類が決める形が合わない（「決定」を参照）
- 案: 説明（README）だけを `documents/` に移す
  - 採用しなかった理由: 見本と一緒に確認・編集できなくなる（ADR 0044 が値を仕様書に書かない理由）。Issue #67 では、AI が読むものを絞るという理由（ADR 0047・0075）も崩れると説明した。この理由を書いているのは [ADR 0047](0047-separate-slide-design-system.md) で（スライドのデザインシステムを画面のものと分けた理由）、ADR 0075 は 0047 の判断を引き継いでいる
- 案: アーティファクトを正のままにして、リポジトリには写しだけを置く（ADR 0151 の形。Issue #67 の「うまくいかなかった場合」の案でもある）
  - 採用しなかった理由: ユーザーが挙げた理由（Git で変更を管理する、AI と検査から読めるようにする）を満たさない。写しは README を含まず、変更もアーティファクトの側で行うことになる。試しで、リポジトリから送る形が成り立つことを確かめたので、この案に下がる必要がなかった
- 案: アーティファクトのページを編集できるままにして、ページで編集しないことを決まりだけで守る
  - 採用しなかった理由: 「決定」の、ページを読み取り専用にする理由を参照

## 影響

- デザインシステムの変更が、仕様の変更と同じコミットに入る。
- Claude Code のサブエージェントと CI が、デザインシステムを読める。
- デザインシステムを変えるたびに、アーティファクトへ送る作業と、中身が同じことを確かめる作業が要る。送り忘れると、アーティファクトの表示が古いままになる。
- 索引（`design-system.json`）は、アイコンの記録に、表示用のアーティファクトのアセットの id を持つ。id はアーティファクトごとに別なので、別のアーティファクトへ送るときは、id の書き換えが要る。
- ページの上部に出る英語の 1 行は `/design-sync` という仕組みを案内するが、このプロジェクトはその仕組みを使わず、Artifact ツールで送る。
- デザインシステムがリポジトリの外にあることを前提にした ADR 0151（CSS とアイコンを `src/design-system/` に写して使う）の扱いは、[ADR 0153](0153-load-design-system-css-directly-from-repository.md) で決めた（ADR 0151 を置き換えた）。
- ADR 0044 の「影響」の「デザインシステムはリポジトリの外（Claude のアーティファクト）にある」と、ADR 0079 の「影響」の「デザインシステムは今回扱っていない」は、この判断で変わった。
- ドキュメントの検査（`python3 tools/check-documents.py`）は `design-system/` を見ない。デザインシステムの README から仕様への参照が古くなっても、ドキュメントの検査では見つからないままである。Issue #67 の「背景」に挙げた、Issue #61 の古い参照を検査で見つけられなかったことは、この判断だけでは解消しない。
