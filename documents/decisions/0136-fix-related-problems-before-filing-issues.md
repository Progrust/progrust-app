## 背景

[ADR 0088](0088-agents-file-found-problems-as-issues.md) は、AI エージェントが作業中に見つけた問題を、原因の調査や改善案の検討をせずに、確認せずに起票するとし、迷ったら起票するとした。起票するのは「頼まれた作業の範囲の外の問題」と「範囲の中でも直さなかった問題」で、範囲の中の問題は起票せずに直すとした。何が範囲の中に当たるかは、定めていなかった。[ADR 0130](0130-triage-undecided-issues-by-skill.md) は、スキル `triage-issues` を作ったときに、起票の決まりは変えないとした。

2026-11-22 の Issue #54 の対応（[ADR 0135](0135-show-cargo-stderr-with-quiet-build.md)）では、直している途中で Issue #55・#56・#57 の3件が起票された。3件の「場所」は、どれも #54 で変えた仕様と同じ機能（`spec/exercise-runner/`）の文書を含む。#56 と #57 の本文は、#54 の対応で足した小見出し「ビルドの出力の表示」を前提にしている。

ユーザーは次のように求めた。

- 「課題や問題を見つけたときに、その課題が現在対応している作業内容と関係する課題の場合、Issueを起票する前にその場ですぐに対応できないかどうかを検討させたいです。」
- 「対応できそうであればその場で対応し、Issueは作成しないでよいです。」
- 「見つけた課題が現在対応している作業とは全く関係がないものだったり、関係はあるが対処に大きな変更を伴うようなものであればIssueを作成します。」
- 「現状は何でもかんでも気になったものをIssueとして作ってしまっている状態で、1つのIssueを片付けるときに新しいIssueが2〜3つくらい出てくるので終わりません。」
- 「実際に作られたIssueが現在対応中のものと関係する課題であるにもかかわらず、その場で解決しようとせずIssueを作成して先延ばしにしてしまっている状況を改善するのが目的です。」

## 決定

- 見つけた問題が、いましている作業と関係するときは、起票する前に、その作業の中で直せるかどうかを確かめる。直せるときは直し、起票しない。いましている作業と関係しない問題と、関係するが直すのに大きな変更が要る問題は、起票する。ユーザーの求めによる。決まりは [Issue の起票](../conventions/issues.md)「起票する問題」に定め、`CLAUDE.md` の「Issue の起票」も合わせる。
  - ADR 0088 の「頼まれた作業の範囲の中の問題は起票せずに直し、範囲の外の問題と、範囲の中でも直さなかった問題を起票する」を、これに変える。
  - ADR 0088 の「原因の調査や改善案の検討をせずに、ユーザーに確認せずに GitHub の Issue に起票する。迷ったら起票する」を、いましている作業と関係する問題については、起票する前に直せるかどうかを確かめる、に変える。関係しない問題は、これまでどおり、調査をせずに起票する。ユーザーに確認しないことは変えない。
  - ADR 0130 の「起票の決まり（迷ったら起票する）は変えない」を、変える。ADR 0130 が「起票を絞る」案を採用しなかった理由は、見つけた問題が会話の中で流れて失われることと、見逃した問題が誰にも伝わらないことだった。この変更で起票しなくなるのは、その作業の中で直した問題だけで、直した問題は応答の最後に書く（下の細部）。直さなかった問題は、これまでどおり起票するので、見つけた問題は失われない。
  - ADR 0088 でユーザーが起票の理由に選んだ「本来の作業を脱線させない」は、いましている作業と関係しない問題と、直すのに大きな変更が要る問題に当てはめる。関係する問題をその作業の中で直すことは、ユーザーが求めた。
- 次の細部は Claude が決めた。
  - 「いましている作業と関係する」を、次のどれかに当てはまることとする。作業で変えるファイルにあるか、作業の対象と同じ機能にある。作業でした変更と食い違うか、作業でした変更によって生じた。作業で扱っている問題と原因が同じである。理由: ADR 0088 の「頼まれた作業の範囲」は、何が範囲の中かを定めていなかったので、#55〜#57 のように、同じ機能の仕様にある問題も起票されていた。基準を書かないと、「関係する」も同じように狭く読まれる。
  - 「大きな変更」は、仕分けの「対応するが、この仕分けでは直さない」と同じもの（機能の実装、技術検証、複数の機能にまたがる仕様の書き換えなど）とする。理由: 起票と仕分けで、別の目安を持たない。
  - 関係する問題でも、直すかどうかや直し方にユーザーの判断が要るものは、直さずに起票する。基準は、仕分けの「ユーザーに回す Issue」のうち、「AI エージェントが、仕分けを迷った」以外のものと同じにする。理由: ADR 0088 のときから、範囲の中でもユーザーの判断が要る問題は起票していて、ユーザーはこの扱いを変えることを求めていない。作業の途中でユーザーに尋ねると、頼まれた作業が止まる。ADR の理由を推測で書かない決まり（`CLAUDE.md`）にも合う。
  - 直せるかどうかを確かめるための調査（問題の場所と関連する ADR を読むこと）はする。Issue に書くための原因の調査や改善案の検討は、これまでどおりしない。理由: 読まなければ、直せるかどうかも、大きな変更が要るかどうかも分からない。ADR 0088 が調査をしないとしたのは、起票の手間を小さくするためで、直すことには当てはまらない。
  - 迷ったときの扱いを、迷いの種類ごとに分ける。問題かどうかを迷ったら、問題として扱う。関係するかどうかを迷ったら、関係するとして、直せるかどうかを確かめる。大きな変更が要るかどうかを迷ったら、直し始め、大きな変更が要ると分かったら、その問題のためにした編集だけを元に戻して起票する。ユーザーの判断が要るかどうかを迷ったら、起票する。理由: 「迷ったら起票する」のままにすると、関係する問題が、迷ったとして起票され、先延ばしが変わらない。関係するとして確かめても、大きな変更が要る問題は起票するので、頼まれた作業から大きくは外れない。ユーザーの判断が要るかどうかの迷いだけは、起票の側に倒す。AI エージェントが決めると、ユーザーが判断したかったことを、知らないうちに決めてしまう（ADR 0130 が、仕分けで迷った Issue をユーザーに回すとした理由と同じ）。
  - 関係する問題を直そうとして直せなかったときは、その問題のためにした編集だけを元に戻して起票する。理由: ADR 0088 のときから、範囲の中でも直せなかった問題は起票している。直さなかった問題を、会話の中で失わない。
  - 起票せずに直した問題は、応答の最後に、何が問題だったかと、どう直したかを書く。仕分けでは、直している Issue のコメントと報告に書く。理由: Issue が残らないので、ユーザーが、何が見つかり何が直されたかを知る手段が、ほかに無い。ADR 0088 の「会話の中で流れて失われる」を防ぐ。
  - 関係する問題を直さずに起票するときは、直さなかった理由を Issue の「問題」に書く。理由: 関係する問題の起票が、先延ばしでないことを、ユーザーと、後で仕分ける AI エージェントが確かめられる。
  - 仕分けで Issue を直している途中に見つけた問題にも、同じ決まりを当てはめる。「いましている作業」は、直している Issue の対応とする。理由: ユーザーが挙げたのは、Issue を片付けるときに新しい Issue が出てくることである。
  - 起票せずに直すときは、同じ問題の Issue があるかどうかの検索を求めない。理由: 検索は、重複した起票を避けるためのものである。直す前に毎回検索すると、作業の中で直すことの手間が増える。

## 検討した他の案

- 案: いましている作業と関係しない問題も、小さければその場で直す
  - 採用しなかった理由: ユーザーが、全く関係がない問題は Issue を作成するとした。関係しない問題を直すと、頼まれた作業から外れる（ADR 0088 の「本来の作業を脱線させない」）
- 案: 関係する問題のうち、ユーザーの判断が要るものは、起票せずに、その場でユーザーに尋ねる
  - 採用しなかった理由: 「決定」に書いたとおり、頼まれた作業が止まる。起票しておけば、ユーザーがスキル `triage-issues` を呼んだときに、まとめて尋ねられる（ADR 0130）
- 案: 起票の決まりは変えず、溜まった Issue を、仕分けでまとめて直す
  - 採用しなかった理由: ユーザーが、関係する問題を起票して先延ばしにすることを改めたいと求めた。仕分けで直している途中にも起票されるので、Issue を1つ片付けるたびに新しい Issue が出て、終わらない（「背景」を参照）
- 案: 「関係する」の基準を書かず、AI エージェントがその都度決める
  - 採用しなかった理由: 「決定」に書いたとおり、基準が無いと狭く読まれる

## 影響

- いましている作業と関係する問題は、その作業の中で直されるので、起票される Issue が減る。
- 1回の作業の変更が、頼まれたものより大きくなることがある。ユーザーは、応答の最後に書かれた「起票せずに直した問題」を読んで、変更を確かめる。
- 対応するかどうかをユーザーが決めないまま、直される問題が生じる。ADR 0088 でユーザーが起票の理由に選んだ「対応の判断を自分がしたい」は、起票された問題にだけ当てはまるようになる。ユーザーの判断が要る問題は、これまでどおり起票される。
- 関係するかどうかと、大きな変更が要るかどうかは、AI エージェントが読んで決めるので、決め方に幅がある。
- 直し始めてから大きな変更が要ると分かったときは、編集を元に戻す手間がかかる。
- 起票せずに直すときは Issue を検索しないので、既に開いている Issue と同じ問題を直すことがある。その Issue は、次の仕分けで「解消している」として閉じられる。ユーザーが対応しないと決めて閉じた Issue と同じ問題を、気づかずに直すこともある。
- `CLAUDE.md` の「Issue の起票」と、スキル（`.claude/skills/triage-issues/SKILL.md`）の、直している途中で見つけた問題の扱いと報告の項目も、この決まりに合わせて直した。どちらも `documents/` の外にあり、検査の対象にならない。
