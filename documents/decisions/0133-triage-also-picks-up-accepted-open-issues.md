- 日付: 2026-11-22
- 関連仕様: [Issue の起票](../conventions/issues.md)「未判断の Issue の仕分け」
- 置き換え: なし

## 背景

[ADR 0130](0130-triage-undecided-issues-by-skill.md) は、ユーザーがスキル `triage-issues` を呼んだときに、`AI起票` と `未判断` の両方が付いた Issue を仕分けるとした。直すのに大きな変更が要る Issue は、直さずに `未判断` を外し、開いたままにする（「対応するが、この仕分けでは直さない」）。

`未判断` を外した Issue は、スキルの対象から外れる。そのため、ユーザーが番号を指定して頼むまで、誰も手を付けない。Issue #51 は、2026-11-21 の仕分けで「対応するが、この仕分けでは直さない」になり、開いたままだった。直すのに要る変更は、2026-11-22 の Issue #52 の対応（[ADR 0132](0132-no-allcrates-dependency-without-crates.md)）で済み、#51 は解消していた。それでも、スキルを呼んだだけでは見つからなかった。ユーザーが「Issue #51 がなんで途中で止まっているのかわかりますか？」と尋ねて、初めて分かった。

ユーザーは「`/triage-issues` で拾うのは「保留」以外に変えられますか？」と尋ねた。Claude は、変える理由と、拾った Issue の扱いを尋ねた。ユーザーは次のように選んだ。

- 理由: 「止まったままを防ぎたい」。Claude が示した説明は次のとおり。「#51 のように「対応するが直さない」にした Issue が、誰にも拾われずに止まったままになるのを防ぎたい」。
- 拾った Issue の扱い: 「小さくなっていれば直す」。Claude が推奨した案である。Claude が示した説明は次のとおり。「他の作業で解消していたら閉じ、その場で直せるようになっていたら直す。まだ大きいものは開いたまま報告の一覧に挙げ、どれを進めるかはあなたが選ぶ。仕分けの時間と変更の量が大きくなりすぎない」。

## 決定

- スキル `triage-issues` が仕分ける Issue を、開いている `AI起票` の Issue のうち `保留` が付いていないもの全部にする。`未判断` の Issue と、対応すると決めて開いたままの Issue（`未判断` も `保留` も付いていないもの）が対象になる（[Issue の起票](../conventions/issues.md)「未判断の Issue の仕分け」）。ADR 0130 の「開いている Issue のうち `AI起票` と `未判断` の両方が付いたものを仕分ける」を、これに変える。ユーザーの求めによる。
- 対応すると決めた Issue は、解消していれば閉じ、その場で直せるようになっていれば直して閉じ、まだ大きな変更が要るものは開いたまま報告に挙げる。どれを進めるかはユーザーが選ぶ。ユーザーが選んだ（「背景」を参照）。
- 次の細部は Claude が決めた。
  - 対応すると決めた Issue では、対応するかどうかを決め直さない。保留にすることも、対応しないで閉じることもしない。理由: 対応すると決めたのは、ユーザーか、前の仕分けである。拾うたびに決め直すと、ユーザーが対応すると決めた Issue を、知らないうちに閉じてしまうことがある。この変更の目的は、止まったままを防ぐことで、決め直すことではない。
  - 開いたまま残す Issue には、コメントを書かず、ラベルも変えない。理由: 仕分けのたびに同じコメントが溜まり、Issue が読みにくくなる。開いたまま残したことは、応答の報告で伝わる。
  - `保留` の Issue は、対象にしない。理由: ユーザーが「保留」以外と求めた。保留の Issue には、対応するきっかけを書いてあり、きっかけが来たときの扱いは [Issue の起票](../conventions/issues.md)「保留の Issue」が定めている。
  - 運用ルールの見出し「未判断の Issue の仕分け」は、名前を変えない。理由: ADR 0130 などの本文が、この見出しを参照している。

## 検討した他の案

- 案: 対応すると決めた Issue も、拾ったときには大きな変更（技術検証や大きな書き換え）まで行う
  - 採用しなかった理由: ユーザーが「小さくなっていれば直す」を選んだ。1 回の仕分けが長くなり、ユーザーが確かめる変更も大きくなる（ADR 0130 が、大きな変更を仕分けの中で行わないとした理由と同じ）
- 案: 拾うが、解消しているかを確かめて閉じるだけにし、直すのはユーザーが番号を指定して頼んだときだけにする
  - 採用しなかった理由: ユーザーが「小さくなっていれば直す」を選んだ
- 案: 対象を変えず、対応すると決めた Issue は、ユーザーが番号を指定して頼むことにする
  - 採用しなかった理由: Issue #51 のように、解消していても気づかれないまま残る。ユーザーが、止まったままを防ぎたいと求めた

## 影響

- 対応すると決めた Issue が、仕分けのたびに見直される。他の作業で解消したり直せるようになったりした Issue が、止まったまま残らない。
- 開いたまま残した Issue は、仕分けのたびに報告に挙がる。件数が多いと、報告が長くなる。
- 仕分けのたびに、対応すると決めた Issue も調べるので、1 回の仕分けに時間がかかるようになる。
