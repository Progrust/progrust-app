## 背景

コードエディタの部品（Issue #166）を作るにあたり、次のことが実装で決めることとして残っていた。

- Monaco Editor を、不要な言語・機能を外した入口で読み込むか（[ADR 0111](0111-bundle-monaco-and-set-csp.md) で、仕様に書かず実装で決めるとした）。技術検証では、既定の入口（`editor.main`）から全言語の定義、css・html・json・typescript の言語機能、LSP を除いた自前の入口で動き、既定の入口より軽かった（[Monaco Editor を Tauri の中で使えるかの技術検証](../verification/issue-21-monaco-in-tauri.md)）。
- Rust の構文強調の色分け。Monaco の Rust の定義は、字句をキーワード・型のキーワード・文字列・コメント・数値などに分けるが、関数とマクロを分けず（`println!` などの一部のマクロはキーワードになる）、`String` のような大文字で始まる型も分けない。デザインシステムは、エディタの色に `code-macro`・`code-function`・`code-type` を定め、Monaco Editor のテーマもこのトークンから作るとしている（`design-system/progrust/README.md`「コード」）。画面デザインのエディタも、関数・マクロ・型を色分けしている。
- エディタの配色の作り方。Monaco のテーマは色の値（16 進）で登録する必要があり、CSS 変数をそのまま使えない。色の値はデザインシステムを唯一の定義とする（[画面の見た目とテーマ](../spec/screens/appearance.md)「デザインシステム」）。

## 決定

以下は、どれも Claude の技術的な判断である。

- Monaco Editor は、既定の入口から、全言語の定義、言語機能（css・html・json・typescript）、LSP のクライアントだけを除いた自前の入口（`src/editor/monaco.ts`）で読み込む。編集機能（contrib）は、既定の入口と同じものを同じ順に読み込む。自前の入口の一覧が既定の入口の一覧と合っていることを、自動テストで確かめる。
  - 理由: 言語は Rust だけを使い、補完・LSP は使わない（[ADR 0004](0004-monaco-without-completion.md)）ので、他の言語と LSP を読み込む意味がない。編集機能を選んで外すと、技術検証で動いた組み合わせから離れ、どの機能を外してよいかの確認が要る。版を上げたときの一覧の確認の手間は、自動テストが既定の入口との違いを知らせることで小さくする。
- 補完は、エディタの設定（`quickSuggestions` などを切る）で出さないようにする。補完の編集機能そのものは外さない。
  - 理由: 上と同じく、編集機能は既定の入口と同じにそろえる。
- Rust は、Monaco の Rust の登録（`languages/definitions/rust/register`）を使わず、自分で登録する。字句の定義は、Monaco の Rust の定義に、マクロ（`名前!`）・関数（名前の後に `(` か `::<` が続く）・型（大文字で始まる名前）を分ける規則を先頭に足したものにする（`src/editor/rustLanguage.ts`）。分け方は、動画のコードの色分け（[ADR 0188](0188-write-rust-highlighter-by-hand.md)）とそろえる。
  - 理由: デザインシステムのエディタの色のうち、マクロ・関数・型の色を使えるようにするためである。Monaco の Rust の登録は、字句の定義を後から読み込んで設定するので、先に設定した定義を上書きする。
- エディタの配色は、アプリの実行時に、読み込んだデザインシステムの CSS から、ライト・ダークそれぞれの CSS 変数の値を読んで作り、Monaco に 2 つのテーマとして登録する。アプリのテーマが変わったら、ルート要素の `data-theme` の変化を見て、エディタのテーマを切り替える。
  - 理由: 色の値をコードに写すと、デザインシステムの値を変えたときに食い違う。CSS から読めば、デザインシステムが唯一の定義のままになる。
- Monaco の既定のテーマの字句の色は引き継がない。区分の無い字句（数値、演算子、名前など）は、文字の色（`ink`）にする。
  - 理由: デザインシステムに無い色をエディタに出さない。
- 演習画面のショートカットを Monaco に登録するのに、`addCommand` ではなく `addAction`（キーを指定したアクション）を使う。[ADR 0111](0111-bundle-monaco-and-set-csp.md) の「決定」の「演習画面のショートカットは、Monaco の `addCommand` で登録して Monaco の既定を上書きする」を、この点で変える。既定を上書きすること、エディタの外ではキャプチャの keydown でも受けることは変えない。
  - 理由: Monaco 0.57 のソースでは、`addCommand` で登録したキーは、どのエディタにフォーカスがあっても効き、登録を外せない。演習画面には、編集するエディタのほかに、読み取り専用のエディタ（前回の正解コード、提出したコードなど）が並ぶことがあり、登録が重なる。`addAction` で登録したキーは、登録したエディタにフォーカスがあるときだけ効き、外せる。どちらも、キーの割り当ては同じ仕組み（Monaco の動的なキーの割り当て）で行われる。

## 検討した他の案

- 案: 既定の入口（`monaco-editor` をそのまま import する）を使う
  - 採用しなかった理由: 約 80 の言語の定義と LSP を読み込み、言語を Rust だけにできない。技術検証で、自前の入口のほうが軽いことを確かめている
- 案: 編集機能も、使うものだけを選んで読み込む
  - 採用しなかった理由: 技術検証で動いた組み合わせから離れ、外した機能に頼る機能が無いかの確認が要る
- 案: Monaco の Rust の定義をそのまま使う
  - 採用しなかった理由: デザインシステムのマクロ・関数の色が使われず、`String` などの型も色分けされず、画面デザインと違う見た目になる
- 案: 動画の色分けの自作の走査（`src/video/highlight.ts`）を、Monaco の字句の分け方として使う
  - 採用しなかった理由: 走査はコード全体を一度に分ける作りで、Monaco が行ごとに字句を分ける仕組み（複数行のコメントの続きなど、行の間の状態を持つ）に合わない
- 案: 配色の色の値を、デザインシステムから写してコードに書く
  - 採用しなかった理由: デザインシステムの値を変えたときに食い違う
- 案: ショートカットを、ADR 0111 のとおり `addCommand` で登録する
  - 採用しなかった理由: 上の理由のとおり、エディタが複数あるときに登録が重なり、外せない

## 影響

- Monaco の版を上げて既定の入口の一覧が変わると、自動テストが失敗する。そのときは、自前の入口の一覧を合わせる（[ADR 0111](0111-bundle-monaco-and-set-csp.md) の「影響」の確認とあわせて行う）。
- Rust の字句の分け方は、Monaco の Rust の定義に頼る。版を上げて Monaco の定義が変わると、色分けが変わることがある。
- 字句の分け方は文法を完全には解釈しない。関数・型の区分は、名前の形と後ろの文字だけで決める。
- エディタの配色に使う CSS 変数（`src/editor/editorTheme.ts`）の名前を、デザインシステムで変えたり消したりすると、その色は Monaco の既定の色になる。
- 技術検証で、Monaco の既定（Cmd+Enter での行の挿入など）を上書きすることと、読み取り専用でも効くことを確かめたのは `addCommand` である。`addAction` は、動いたことだけを確かめている。キーボードショートカットのタスクで、`addAction` でも既定を上書きし、読み取り専用でも効くことを、実際のキーで確かめる。
