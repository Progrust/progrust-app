## 背景

これまでの仕様は、学習者のプログラムの出力を `run_output` イベントで「逐次送る」とだけ書き、止め方、実行の終わりの判定、ビルド中の停止を定めていなかった。

Issue #16 の技術検証で、学習者のプログラムを子プロセスとして起動し、出力の受け取り、標準入力、停止、出力量の上限を試した（[学習者のプログラムの子プロセスとしての扱いの技術検証](../verification/issue-16-learner-process.md)）。

- 新しいプロセスグループで起動してグループ全体に SIGKILL を送ると、スレッド、`Command` や `fork()` で作った子、`cargo run` 経由のプログラム、ビルド中の cargo と rustc まで止まり、孤児もゾンビも残らなかった。学習者のプログラムが `setsid()` などで別のグループに移した子は残った。端末で Ctrl+C を押したときも同じく残った。
- 親子関係をたどって止める方法を足すと、グループから抜けた子の多くは止められたが、二重 fork した孫は止められなかった。
- 学習者のプログラムが終わった後も、同じグループの子が残って動き続けることがある。抜けた子がパイプを持ったままだと、パイプの終わり（EOF）が来ない。
- 1 行ごとに 1 イベントで送ると、行数の多い出力で画面が 0.2〜1 秒以上止まり、1 MB に達するまで 13 秒かかった。16〜50ms ごとにまとめて送ると、1 MB が 1〜16 イベントになり、受け取るだけなら画面は止まらなかった。
- 画面への送信が遅いとき、停止の後にたまった出力を送り切ると、`run_finished` が 7 秒以上遅れ、制限時間も効かなくなった。たまった出力を捨てると、100ms 以内に終わった。
- stdout と stderr は別々のパイプなので、書いた順と違う順で届いた。1 つのパイプにまとめれば順序は保てるが、stdout と stderr を区別できなくなる。

Claude は、上の結果から推奨の構成を示した。ユーザーは、「私は細かい技術的な話はわからないので、あなたの推奨通りで進めて大丈夫です」と示し、判断を Claude に任せた。以下の理由は Claude が書いた。

## 決定

- ビルドの cargo と学習者のプログラムを、新しいプロセスグループで起動し、停止ボタン・実行時間の制限・出力量の上限では、グループ全体に SIGKILL を送る。別のグループやセッションに移した子は止めない（[コードの実行（run）](../spec/exercise-runner/run.md)「停止」）。
  - 理由: 端末で `cargo run` して Ctrl+C を押したときと同じ範囲を止める。学習者のコードは、学習者が自分のターミナルで動かすのと同等に扱う（[ADR 0014](0014-run-learner-code-without-sandbox.md)）。親子関係をたどる方法を足しても二重 fork は止められず、実装が増えるわりに完全にならない。
- 学習者のプログラムが終わったら、同じグループに残ったプロセスを止め、その後の出力は 300ms だけ待って実行を終える。EOF は待たない。
  - 理由: 残った子を止めないと、次の実行と並行して動き、パイプも持ち続ける。グループから抜けた子がパイプを持っていると EOF が来ず、実行が終わらない。
- 停止ボタンと実行時間の制限で止めた後は、まだ送っていない出力を捨てる。
  - 理由: 送り切ると、画面への送信が遅いときに停止の結果が数秒遅れ、制限時間も効かなくなる。
- 出力は 16〜50ms ごとにまとめて 1 つの `run_output` で送り、1 つのイベントに stdout / stderr / system の断片を順に入れる。改行で終わらない出力も待たずに送る（[コードの実行（run）](../spec/exercise-runner/run.md)「出力の送り方」）。
  - 理由: 1 行ごとのイベントでは、行数の多い出力で画面が固まる。改行を待つと、flush したプロンプトや改行のない出力が届かない。
- stdout と stderr は別々のパイプのままにし、前後関係が書いた順と違うことがあると仕様に書く。
  - 理由: 画面で stderr を区別して表示できることを優先する。
- 出力量の上限では、上限までの出力だけを表示し、上限で切れた UTF-8 の文字と、上限を超えた後に受け取った分は表示しない（[実行・判定の制限値](../spec/exercise-runner/limits.md)）。
  - 理由: 上限を超えたことは読み取りの時点で分かるが、パイプには最大 64KB 程度が残っている。切れた文字を表示すると、置換文字が出る。
- ビルド中も停止ボタンで止め、結果を `stopped` とする（[演習画面](../spec/screens/exercise-screen.md)）。
  - 理由: 検証で、ビルド中に止めても cargo と rustc がまとめて止まり、次のビルドも成功した。

## 検討した他の案

- 案: プロセスグループへの SIGKILL に加えて、親子関係をたどって子孫を止める
  - 採用しなかった理由: 二重 fork した孫は止められず、完全にならない。端末と違う動きになる
- 案: 学習者のプログラムが終わった後、同じグループに残った子を止めない（端末と同じ）
  - 採用しなかった理由: 残った子が次の実行と並行して動き、パイプを持ち続けて実行が終わらなくなる
- 案: stdout と stderr を 1 つのパイプにまとめる
  - 採用しなかった理由: 順序は保てるが、stdout と stderr を区別して表示できなくなる
- 案: 1 行ごと、または `read()` 1 回ごとに 1 イベントで送る
  - 採用しなかった理由: 行数の多い出力で画面が固まり、学習者のプログラムも待たされる
- 案: 停止の後も、たまった出力を送り切る
  - 採用しなかった理由: 停止の結果が数秒遅れ、制限時間が効かなくなることがある

## 影響

- 学習者のプログラムが別のプロセスグループに移した子は、実行が終わった後も残る。
- stdout と stderr を交互に書くプログラムでは、コンソールの表示の順序が端末と違うことがある。
- `print!` の後に flush しない出力や `BufWriter` の出力は、学習者のプログラムの中にたまり、すぐには表示されない。これは Rust の標準ライブラリの性質で、端末でも同じである（[ADR 0104](0104-teach-flush-after-print.md)）。
- macOS で、二重 fork した孫を止める仕組みは確かめていない。
