## 背景

`test` 方式の判定では、テスト実行ファイルを `--list progrust_judge::` で起動して隠しテストの名前を得て、名前ごとに別のプロセスで実行する（[ADR 0101](0101-run-each-hidden-test-in-own-process.md)）。ADR 0101 は、隠しテストが 1 件も無いとき（`--list` が 0 件のとき）の扱いを、確かめていないとして残していた。

判定結果は、すべてのテストケースが `pass` のときに `passed` になる（[コードの提出（submit）](../spec/exercise-runner/submit.md)「判定結果」）。テストケースが 0 件のまま判定結果を組み立てると、何も確かめずに `passed`（0 / 0）になり、レッスンが完了になる。実装計画の M2 で、`test` 方式の隠しテストの判定の部品を作るときに決める必要があった。

この判断は、Claude が技術的な判断として決めた。

## 決定

- `--list` の起動が終了コード 0 で終わらなかったときと、隠しテストの名前が 1 件も得られなかったときは、テストケースを実行せずに、アプリの側の失敗（[実行のコマンドとイベント](../spec/architecture/commands/run.md)「イベント」の `run_finished` の `error`）として終える（[コードの提出（submit）](../spec/exercise-runner/submit.md)「test 方式」）。
  - 理由: どちらも、学習者のコードではなく、教材（隠しテストの無い `judge_tests.rs`）かアプリの誤りで起きる。`--list` はテストを実行せずに名前を出すだけなので、学習者のコードで失敗することは無い。判定しないまま正解にすると、誤りに気付けず、レッスンが誤って完了になる。

## 検討した他の案

- 案: 0 件のまま判定結果を組み立てる（`passed`、0 / 0）
  - 採用しなかった理由: 何も確かめずに正解になり、レッスンが完了になる
- 案: `wrong`（0 / 0）にする
  - 採用しなかった理由: 学習者のコードに誤りが無くても不正解になり、学習者には直しようがない。試行ログにも、学習者の誤りとして記録される

## 影響

- 隠しテストの無い教材は、提出のたびにアプリの側の失敗になる。演習の作成ルールでは、テストケースを 1 件以上用意する（[演習の作成ルール](../spec/content-guidelines/exercise.md)「テストケース」）ので、ルールどおりに作った教材では起きない。
