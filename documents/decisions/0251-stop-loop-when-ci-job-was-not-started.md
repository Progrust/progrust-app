## 背景

2026-11-25 に、GitHub Actions のジョブが「The job was not started because recent account payments have failed or your spending limit needs to be increased.」の注釈付きで、ステップを 1 つも実行せずに失敗するようになった。実装のループは、チェックが失敗したことだけを見て、コードの失敗として直しの回を回した。ジョブが開始されていないので、失敗したジョブの出力も無く、直す側への指摘は、チェックの名前とリンクだけだった。タスク #239 と #241 は、直しの回を 4 回ずつ回し、どの回もファイルが変わらずに失敗して、行き詰まりになった（Issue #264）。コードを直しても通らない、全部のタスクに共通する CI の基盤の問題だった。

前の仕分け（2026-11-25）で、Claude が対応すると決めた。変えるファイルが保護するパスなので、ユーザーのいる会話（2026-11-26 の仕分け）で直した。

## 決定

以下は、どれも Claude の技術的な判断である。

- 失敗した CI のチェックのジョブが、ステップを 1 つも実行せずに終わったときは、ジョブが開始されなかったとして、直しに回さずに止まる。仕組みの失敗と同じく、タスクにラベルを付けず、作業を捨て、pull request は開いたままにする。決まりは [実装のループ](../conventions/implementation-loop.md)「止まるとき」に定める。
  - 理由: コードを直しても通らないので、直しの回は利用枠の無駄になり、タスクを行き詰まりにすると、原因を取り除いた後に、ユーザーが 1 件ずつ `行き詰まり` を外す必要がある。仕組みの失敗にすれば、原因を取り除いてループを始め直すだけで、タスクはまた選ばれる。
- 見分けるのは、注釈の文言ではなく、ジョブの形（`gh run view --json jobs` のジョブが `completed` で、ステップの一覧が空であること）で行う。
  - 理由: 文言は GitHub の都合で変わり、支払い以外の理由（利用上限など）でも、ジョブは開始されないことがある。ジョブが始まれば、最初に「Set up job」のステップが記録されるので、ステップが空なら、ワークフローの中身は何も動いていない。
- 結論（`failure` か `cancelled` か）は問わない。
  - 理由: どちらでも、ステップが 1 つも動いていなければ、直す側に渡せる失敗の中身が無い。
- 止まる理由には、そのジョブの失敗の注釈（`gh api` で読む check run の annotations）の文を出す。
  - 理由: ユーザーが、ループの出力だけで、支払いや利用上限などの原因を知り、取り除ける。
- ジョブの一覧が読めないとき（`gh` の失敗など）は、見分けずに、これまでどおり CI の失敗として直しに回す。
  - 理由: 読めないことを理由に止めると、一時的な失敗でループが止まりやすくなる。直しに回しても、次の回の CI でまた見分けられる。

## 検討した他の案

- 案: 注釈の文言（`The job was not started` など）で見分ける。
  - 採用しなかった理由: 上の理由。文言が変わると見分けられなくなる。
- 案: 見分けたタスクに `行き詰まり` を付け、ループは次のタスクへ進む。
  - 採用しなかった理由: CI の基盤の問題は、どのタスクでも同じように起きるので、次のタスクも同じように失敗する。タスクの数だけ `行き詰まり` が付き、ユーザーが外す手間が増える。

## 影響

- CI のジョブが開始されないときは、最初のタスクの CI でループが止まり、ほかのタスクに `行き詰まり` が付かない。
- 止まったタスクは、次のループで最初から実装し直す。実装・チェック・レビュー・push の分の時間と利用枠は、やり直しになる。
- CI を待つたびに、失敗したチェックがあると、`gh run view` を run ごとに 1 回呼ぶ。見分けたジョブには、`gh api` を 1 回呼ぶ。
