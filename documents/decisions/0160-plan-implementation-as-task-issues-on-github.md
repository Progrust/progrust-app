## 背景

仕様と実装前の技術検証が済み、アプリの実装を始める段階になった。リポジトリには、アプリのコード（`src/`・`src-tauri/`）も `package.json` も CI も、まだ無い。実装をどの単位で、どの順に、どう進めるかの決まりは無かった。

ユーザーは、実装するときの仕組みやルール、実装計画の作り方を決めたいと示し、次のように求めた。

- 「なるべく人間の介入を挟まないようにループして実装を行えるような仕組みが欲しい。」
- 「なるべくコスパよく作りたい。haiku、sonnet、opusを組み合わせて難易度ごとに実施するモデルを切り替える。」
- 「レビューを仕組みに組み込む」
- 「上記のことを前提として実装計画を組む」
- 「実装に必要なClaudeスキルなどが必要であれば用意する」
- 「実装中に見つかったIssueは直せるものは実装中のループの中で片付けたい。」

あわせて「GitHubの機能も使って良い」と示した。

Claude が理由を尋ねると、ユーザーは、人の介入を減らしたい理由として次の 2 つを選んだ（選択肢は Claude が示した）。

- つきっきりになれない: 仕事中や寝ている間など、自分が見ていない時間にも実装を進めたい。
- 判断の負担を減らしたい: 技術的な細かい確認に、そのつど答えるのが負担になる。

Claude は、次の案を示した。計画と進み具合を GitHub の Issue に置き、1 タスクを 1 Issue・1 pull request にする。まとまりはマイルストーンで表す。先に未決事項を決める。機能を縦に薄く切る。細かく切るのは次のマイルストーンの分だけにする。最初のマイルストーンを土台にする。Claude は、あわせて、ユーザーに決めてほしいことを 4 つ挙げ、どれにも推奨を付けた（[ADR 0161](0161-run-implementation-loop-locally-and-park-human-work.md)、[ADR 0163](0163-loop-merges-pull-requests-by-itself.md)、[ADR 0164](0164-loop-triages-issues-between-tasks.md)、[ADR 0165](0165-implementation-plan-excludes-content.md)）。ユーザーは「「決めていただきたいこと」はすべて推奨通りでよいです。」と答えた。案のほかの部分には、変更を求めなかった。

関係する決まりと事実は、次のとおり。

- Issue の一覧のための Issue は作らない（[ADR 0121](0121-no-tracking-issues-use-labels.md)）。Issue をまたぐ説明は、各 Issue の本文か `documents/` に書く。
- 各受け入れ条件をどの区分で確かめるかは、機能を実装するときに決める（[ADR 0149](0149-testing-policy.md)）。
- 各機能の未決事項（`open-questions.md`）は、2026-11-22 に数えて 12 の機能に 43 件ある。非機能要件の「一般公開をする場合に決めること」「一般公開した後に決めること」の 9 件は、数に入れていない。
- 運用ルール（`conventions/`）と type `Convention` は、`documents/` の中の文書の書き方と、AI エージェントの Issue の起票の決まりだけを扱っていた（[ADR 0080](0080-use-minimal-okf-frontmatter.md)、[ADR 0088](0088-agents-file-found-problems-as-issues.md)）。
- 一時作業用ディレクトリは、文書や実装から参照できない（`CLAUDE.md`）。

## 決定

- 実装は、実装計画のタスクごとに進める。実装計画は、人の介入をなるべく挟まないループ（ADR 0161）、難易度ごとのモデルの切り替えとレビュー（[ADR 0162](0162-pick-model-by-difficulty-and-review-in-separate-session.md)）を前提にして組む。ユーザーの求めによる。決まりは [実装計画とタスクの Issue](../conventions/implementation-plan.md) に定める。
- 次の内容は、Claude が案として示し、ユーザーは変更を求めなかった（「背景」を参照）。理由は Claude が挙げた。
  - 実装を、1 タスクを 1 つの Issue にして、1 つの pull request でマージする単位に分ける。計画と進み具合は、GitHub の Issue・ラベル・マイルストーンで持ち、リポジトリのファイルには書かない。理由: 状態が会話の中に無いので、どのモデルの会話でも、いつ止まっても、続きから進められる。進み具合をファイルに書くと、進むたびにコミットが要り、Issue の状態との 2 重管理になる。
  - タスクを作る前に、そのマイルストーンの実装に要る未決事項を決める。理由: 未決事項は、実装の途中でユーザーの判断を待って止まる原因になる。先にまとめて尋ねれば、ユーザーが答える回数が減る。
  - マイルストーンを、作者がアプリを操作して確かめられる区切りにし、層ごとには切らない。理由: 早い段階から、作者がアプリを触って確かめられる。
  - マイルストーンは最後のものまで作り、タスクの Issue は次に進めるマイルストーンの分だけ作る。理由: 実装すると分かることがあり、先のタスクを細かく作っても、作り直しになる。
  - 最初のマイルストーンを `M0 土台` にし、そのタスクは `ループ対象外` にして、ユーザーのいる会話で進める。理由: ループは、機械のチェック（`npm run check`）と CI が無いと、確かめてマージすることができない。
- 次の細部は Claude が決めた。
  - まとまりを、GitHub のマイルストーンで表す。理由: マイルストーンは、ラベルと同じく Issue に付く属性で、一覧のための Issue ではない。ADR 0121 が避けた 2 重管理にならない。ADR 0121 が「置く場所がなくなる」とした、項目をどの順で進めるかの説明は、各 Issue の「前提」と、マイルストーンの番号と説明に書く。
  - タスクの Issue の本文の形を決め、「前提」の行と見出しの名前を固定する。理由: ループが、前提と、人が確かめることの有無を、機械で読む。
  - タスクの Issue に書く確かめ方の区分は、案とし、区分は実装するときに決める。理由: ADR 0149 の「機能を実装するときに決める」を変えない。計画のときに案があれば、実装する側が区分を決めやすく、人が確かめることを計画のときに拾える。
  - モデルの名前ではなく、難易度をラベルにする。理由: 難易度とモデルの対応を変えても、Issue のラベルを付け直さずに済む。
  - タスクの Issue に `AI起票` と `未判断` を付けない。理由: スキル `triage-issues` は `AI起票` の Issue を仕分けるので、付けると、計画のタスクが仕分けの対象になる。
  - 計画を作るのは、ユーザーがスキル `plan-implementation` を呼んだときとし、決まりを運用ルールに、進め方をスキルに書く。理由: [ADR 0130](0130-triage-undecided-issues-by-skill.md) がスキル `triage-issues` で取った分け方と同じにする。未決事項をユーザーに尋ねるので、ユーザーがいるときに行う必要がある。
  - 実装の進め方の決まりを `conventions/` に置き、type `Convention` の範囲を、実装の進め方の決まりに広げる。ADR 0088 の「`Convention` の範囲を、`documents/` の中の文書の書き方と、AI エージェントの Issue の起票の決まりに広げる」を、実装の進め方の決まりも含める、に変える。ADR 0080 の type の範囲も同じに変える。理由: 実装の進め方は、AI エージェントの作業の決まりで、プロダクトの仕様ではない。Issue の起票の決まりと同じ場所にあれば、`CLAUDE.md` から 1 つのディレクトリを指せる。新しい type は作らない（ADR 0080）。

## 検討した他の案

- 案: 計画とタスクの一覧を、`documents/` の文書に書く
  - 採用しなかった理由: 進むたびに文書を書き換えてコミットすることになり、Issue の状態との 2 重管理になる。仕様は現時点の事実を書く場所で、進み具合を書く場所ではない
- 案: 一覧のための Issue（チェックリスト）で進み具合を追う
  - 採用しなかった理由: ADR 0121 で、ユーザーの求めによって作らないと決めている
- 案: GitHub Projects で管理する
  - 採用しなかった理由: ラベルとマイルストーンで、順序と進み具合を表せる。2026-11-22 に確かめたところ、いまの `gh` のログインには Projects を操作する権限（`project`）が無く、足すにはユーザーの操作が要る
- 案: 全部のタスクの Issue を、最初に作る
  - 採用しなかった理由: 先のタスクは、実装で分かったことで作り直しになる。Issue の数も多くなる
- 案: 層ごとに切る（バックエンドを全部作ってから、画面を作る）
  - 採用しなかった理由: 作者が触って確かめられるのが、最後になる
- 案: 未決事項を、実装の途中で 1 件ずつ決める
  - 採用しなかった理由: ユーザーの判断が要る事項で、そのつどタスクが止まる

## 影響

- 実装の状況は、GitHub の Issue とマイルストーンを見れば分かる。リポジトリのファイルだけを読んでも、どこまで進んだかは分からない。
- タスクの Issue の質が、実装の質を決める。計画を作るときに、仕様を読んで Issue を書く手間がかかる。
- マイルストーンの区切りごとに、ユーザーがスキル `plan-implementation` を呼ぶ必要がある。
- タスクの Issue の本文の形を変えると、ループのスクリプトも直す必要がある。
- `Convention` の文書が、文書の書き方、Issue の起票、実装の進め方の 3 つを扱うようになる。
