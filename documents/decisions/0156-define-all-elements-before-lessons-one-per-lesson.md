## 背景

要素マスタ（`content/elements.json`）の内容は、教材作成ガイドラインの未決事項（「作成者が別途用意する」）のままだった。形式は決まっていたが、例は 1 件だけで、分類の名前の一覧も、要素をどの細かさで分けるかの基準も無かった（Issue #64）。

要素の数と分け方には、すでに次の決まりが効いている。

- 要素 ID は、公開したら変更も削除もできない（[ADR 0006](0006-element-ids-are-permanent.md)）。
- どの要素も、いずれかのレッスンの主要素でなければならない。既習の要素は、導入レッスンから求める（[ADR 0007](0007-derive-introduced-lesson.md)）。
- 主要素は 1 レッスンに 2 件までで、動画のみのレッスンは要素を持たない（[ADR 0120](0120-video-only-lessons-have-no-elements-or-attempt-sessions.md)）。
- 演習のあるレッスンは 142 件ある。分析のジョブが制限時間に収まることは、142 要素で確かめた（[AI の応答時間と出力の安定性の技術検証](../verification/issue-11-ai-timing.md)）。

ユーザーは 2026-11-22 に、レッスンを 1 本ずつ作りながら要素を足すのではなく、要素 ID をすべて事前に決める方針を示した。Claude が理由を尋ね、ユーザーは「実装時に判断が残るものをある程度潰しておきたいため」と答えた。

Claude は、分け方の基準、分類の一覧、全レッスンぶんの 145 件の要素を推奨案として示し、ユーザーは推奨案のとおりにすると答えた。

## 決定

- 要素マスタの要素を、レッスンを作る前にすべて決める（[要素の分け方と要素 ID の付け方](../spec/content-guidelines/elements.md)）。ユーザーの方針による。
  - 理由: 実装時に判断が残るものを、ある程度潰しておきたいため（ユーザーの言葉）。
- 演習のあるレッスン 1 つにつき要素を 1 つ置くことを基本とし、別々に使える 2 つの内容を扱い、そのどちらも単独でよく使うか単独で躓きやすいレッスンだけ、2 つに分ける（同「要素の分け方」）。Claude が提案し、ユーザーが採用した。理由は Claude が書いた。
  - 理由: 上の決まりから、要素は 142 件より少なくできない。1 つの要素を複数のレッスンにまたがらせると、最初のレッスンを終えた時点で、後のレッスンの内容まで既習になってしまう。
  - 理由: 細かく分けるほど、演習の回数が 1 回だけで「データ不足」になる要素が増え、問題生成の設定画面に並ぶ要素も増える。145 件なら、検証で確かめた規模とほぼ同じである。
- 2 つに分けるレッスンは、次の 3 つにした。
  - ch06-03（構造体更新記法、部分的なムーブ）。理由: 部分的なムーブは、構造体更新記法を使わなくても起きる所有権の躓きである。
  - ch07-01（列挙型、match による分岐）。理由: `match` は、列挙型以外の値（数値、タプル、`Option`）にも使う。
  - ch15-04（collect、消費アダプタ）。理由: `collect` は、その後のほとんどの演習に出る。1 つにまとめると、`sum`・`fold` などの習熟が `collect` の記録に埋もれる。
- 次の細部は Claude が決めた。
  - 要素 ID の分類を、Rust の機能のまとまりで付け、章の番号を入れない（同「要素 ID」）。理由: レッスンを別の章に移しても、変えられない要素 ID をそのまま使える。
  - 仕様の例に出ていた 7 つの要素 ID（`ownership.move`・`fn.basic`・`string.basic`・`vec.basic`・`borrow.mutable`・`borrow.rules`・`string.concat`）を、そのまま使える名前にした。理由: 例を書き換えずに済む。
  - `chapter` を、「その要素を主に扱う章」から、章とレッスンの一覧で最初にその要素を主要素とするレッスンが属する章に変える（[要素マスタの形式（elements.json）](../spec/content-format/elements-json.md)）。理由: 問題生成の設定画面は `chapter` で要素を章ごとに並べるので、要素が、学んだ章に並ぶ。「主に扱う章」は、分類が複数の章にまたがる要素で決め方が曖昧だった。機械的に検査できる（[教材チェックツール](../spec/content-guidelines/check-tool.md)「要素と一覧」）。
    - ADR 0007 は、学習順から求められる値（導入レッスン）を要素マスタに持たせると、値がずれる可能性が残り、レッスンの順序を変えるたびに要素マスタも直すことになる、として退けた。`chapter` も学習順から求められる値だが、ADR 0007 が残したフィールドで、今回は新しいフィールドを足していない。レッスンを別の章に移したときに要素マスタも直す手間は、これまでの「主に扱う章」でも同じにあった。今回の検査で、直し忘れが見つかるようになる。
  - `related_errors` には、必要な最低バージョンの rustc でコンパイルして、実際に出ることを確かめたコードだけを書く。理由: 記憶で挙げた候補を rustc 1.100.0 でコンパイルすると、別のコードが出たものが 3 件（「型が見つからない」は E0412 ではなく E0425 で出る、など）、エラーにならなかったものが 1 件あった。
  - E0308・E0277・E0599・E0425 のように多くの場面で出るコードは、その誤解が要素の中心である場合だけ書く。理由: `related_errors` は、試行ログのエラーコードから躓いた要素の候補を出すのに使う。多くの要素に同じコードを書くと、候補が絞れない。
  - `name`・`description`・`related_errors` は、後から変えてよいものとする。理由: 変えられないと決めているのは要素 ID だけで（ADR 0006）、これらは、レッスンを作ってみて分かったことで直したい。

## 検討した他の案

- 案: レッスンを 1 本ずつ作りながら、要素を足す
  - 採用しなかった理由: 実装時に、要素の分け方と名前の判断が残る（ユーザーの方針）
- 案: 「A と B」を扱うレッスンを、広く 2 つの要素に分ける（ch04-05 の clone と Copy、ch08-10 の HashSet と BTreeMap、ch14-04 の関数ポインタとクロージャを返す関数、ch22-04 の型エイリアスと never 型など）
  - 採用しなかった理由: どれも、片方だけでは演習の対象にしにくいか、躓き方が変わらない。分けると、データ不足の要素と、設定画面に並ぶ要素が増える
- 案: 複数のレッスンを 1 つの要素にまとめる
  - 採用しなかった理由: 上の「決定」の理由のとおり、既習の判定がレッスンの単位でできなくなる。どのレッスンにも主要素が要るので、要素の数も減らない
- 案: 分類を章と 1 対 1 にする（章の ID を分類にする、など）
  - 採用しなかった理由: レッスンを別の章に移すと、要素 ID が内容と合わなくなる

## 影響

- 教材作成ガイドラインの未決事項から、要素マスタの用意が無くなった。
- 分け方を見直したくなっても、既存の要素 ID は変えられない。新しい要素を足し、古い要素に `deprecated` を付ける（ADR 0006）。
- カリキュラムにレッスンを足すときは、要素も足す。
- `related_errors` が空の要素が 40 件ある。これらは、エラーコードからの候補には出ない。
- `test.integration`・`error.anyhow`・`async.stream` の `related_errors` は、外部クレートや複数のクレートが要るので、コンパイルして確かめていない。`rustc --explain` でコードの意味を確かめただけである。
