## 背景

AI エージェントが作業中に見つけた問題は、その作業と関係していて直せるものはその場で直し（[ADR 0136](0136-fix-related-problems-before-filing-issues.md)）、それ以外は Issue に起票する。起票した問題について、これまでの決まりは次のとおりだった。

- 起票した問題は、ユーザーに頼まれるまで直さない（[ADR 0088](0088-agents-file-found-problems-as-issues.md)）。ユーザーが挙げた理由は、本来の作業を脱線させないことと、対応の判断を自分がしたいことだった。
- 仕分けるのは、ユーザーがスキル `triage-issues` を呼んだときだけにする（[ADR 0130](0130-triage-undecided-issues-by-skill.md)）。Claude が挙げた理由は、作業中に AI エージェントが自分から仕分けると頼まれた作業から外れることと、ユーザーが知らないうちに Issue が閉じられることだった。
- スキルが仕分けるのは、開いている `AI起票` の Issue のうち、`保留` が付いていないもの全部である（[ADR 0133](0133-triage-also-picks-up-accepted-open-issues.md)）。
- スキルで直した変更は、コミットしない（ADR 0130）。

ユーザーは、実装の仕組みについて「実装中に見つかったIssueは直せるものは実装中のループの中で片付けたい。」と求めた。Claude が理由を尋ねると、ユーザーは、選択肢（Claude が示した）をすべて選んだ。

- Issue をためたくない: 実装中は起票が増えるので、後でまとめて仕分けると量が多くなる。
- 呼ぶ手間をなくしたい: 自分で `/triage-issues` を呼ばなくても、ループが片付けてほしい。
- 問題の上に積みたくない: 直っていない問題を残したまま、次の実装を重ねたくない。

Claude は、ユーザーに決めてほしいこととして、次のように尋ねた。「タスクの切れ目で、`AI起票` の Issue を自動で仕分けて直してよいか。推奨は「よい」です。」あわせて、ループの起動を仕分けの依頼とみなし、タスクの途中ではなく切れ目で行えば脱線を防げること、判断を今までどおり Issue のコメントに残すことを示した。ユーザーは「「決めていただきたいこと」はすべて推奨通りでよいです。」と答えた。

ループは、ユーザーのいないところで動き、機械のチェック・レビュー・CI を通った pull request を自分でマージする（[ADR 0161](0161-run-implementation-loop-locally-and-park-human-work.md)、[ADR 0163](0163-loop-merges-pull-requests-by-itself.md)）。

## 決定

- 実装のループは、始めたときと、タスクの切れ目に、開いている `AI起票` の Issue を仕分け、直すと決めたものを直す。ユーザーの求めと選択による（「背景」を参照）。決まりは [実装のループ](../conventions/implementation-loop.md)「Issue の仕分け」に定め、[Issue の起票](../conventions/issues.md) と `CLAUDE.md` も合わせる。
  - ADR 0088 の「起票した問題は、ユーザーに頼まれるまで直さない」を、ユーザーに頼まれたときと、実装のループの中で直す、に変える。
  - ADR 0130 の「仕分けるのは、ユーザーがスキルを呼んだときだけにする」を、ユーザーがスキルを呼んだときと、実装のループのタスクの切れ目に仕分ける、に変える。ADR 0130 がこの決まりの理由にした 2 つのうち、頼まれた作業から外れることは、タスクの途中ではなく切れ目で仕分けることで防ぐ。ユーザーが知らないうちに Issue が閉じられることは、ユーザーがループを始めたことを仕分けの依頼とし、判断を Issue のコメントに残すことで、ユーザーが後から確かめて変えられるようにする。
  - ADR 0133 の「仕分ける Issue を、開いている `AI起票` の Issue のうち `保留` が付いていないもの全部にする」を、`保留` も `実装タスク` も付いていないもの、に変える。
- 次の細部は Claude が決めた。
  - ループの仕分けでは、ユーザーに尋ねない。ユーザーの判断が要る Issue は、`未判断` のまま残す。理由: ループにはユーザーがいない。残した Issue は、ユーザーがスキル `triage-issues` を呼んだときに尋ねられる。
  - ループの仕分けでは、ファイルを変えない。「直す」に仕分けた Issue は、`実装タスク` と難易度のラベルを付けて、ループのタスクにする。理由: 直した変更を、ほかのタスクと同じ道（機械のチェック、レビュー、pull request、CI、マージ）に通せる。ユーザーが挙げた「人が差分を見ないから」レビューが要るという理由（[ADR 0162](0162-pick-model-by-difficulty-and-review-in-separate-session.md)）は、Issue を直した変更にも当てはまる。仕分けの中で直すと、その変更だけ、別の進め方が要る。
  - タスクにした `AI起票` の Issue を、実装計画のタスクより先に選ぶ。理由: ユーザーが挙げた「問題の上に積みたくない」に合わせる。
  - `実装タスク` の付いた Issue を、スキル `triage-issues` の対象から外す。理由: ループが直すと決めた Issue を、スキルがもう一度仕分けて、その場で直してしまうことを防ぐ。
  - 「直す」に仕分けるのは、ループの中で直せる Issue だけにする。保護するパスを変える必要がある Issue は、「対応するが、この仕分けでは直さない」にする。理由: ループは、保護するパスを変えない（ADR 0161）。
  - タスクにするときのコメントの 1 行目を `ループで直すと決めた（YYYY-MM-DD、Claude の判断）。` とし、どう直すかを続けて書く。マージした後は、ループが `直したので閉じる（YYYY-MM-DD、Claude の判断）。` で始まるコメントを書く。理由: それまでの仕分けのコメント（ADR 0130）と同じ形にし、誰の判断かを同じ場所で読めるようにする。実装する側は、仕分けたときの会話を見られないので、直し方をコメントから読む。
  - 開いているタスクが「前提」で待っている Issue は、ループでは仕分けない。理由: その Issue は、実装する側が、ユーザーの判断を求めて起票したものである（[ADR 0161](0161-run-implementation-loop-locally-and-park-human-work.md)）。ループが閉じたりタスクにしたりすると、ユーザーが決めないまま、待っていたタスクが進んでしまう。
  - 同じ実行の中で一度仕分けた Issue は、その実行では仕分け直さない。理由: `未判断` のまま残した Issue を、タスクの切れ目のたびに読み直して、トークンを使うことを防ぐ。
- ユーザーがスキル `triage-issues` を呼んだときの仕分け（ユーザーに尋ねること、その場で直すこと、直した変更をコミットしないこと）は、変えない。

## 検討した他の案

- 案: ループでは仕分けず、マイルストーンの区切りに、ユーザーがスキル `triage-issues` を呼ぶ
  - 採用しなかった理由: ユーザーが挙げた 3 つの理由（「背景」を参照）のどれにも合わない
- 案: ループの仕分けの中で、その場で直す
  - 採用しなかった理由: 「決定」に書いたとおり、直した変更が、レビューと CI を通らない
- 案: タスクの途中で見つけた問題を、関係しないものも含めて、その場で直す
  - 採用しなかった理由: タスクの差分に関係のない変更が混じり、レビューと取り消しがしにくくなる。関係する問題は、ADR 0136 のとおり、その場で直している
- 案: ユーザーの判断が要る Issue が出たら、ループを止めて尋ねる
  - 採用しなかった理由: 人の判断が要ることでは、ループを止めない（ADR 0161）

## 影響

- ユーザーが `/triage-issues` を呼ばなくても、`AI起票` の Issue が、ループの中で仕分けられ、直せるものは直される。
- ユーザーのいないところで、AI エージェントが、Issue を保留にしたり、対応しないと決めて閉じたりする。判断は Issue のコメントに残るので、ユーザーは後から確かめて、変えられる（ADR 0130「影響」と同じ）。
- `未判断` のまま残った Issue は、ユーザーが `/triage-issues` を呼ぶまで残る。タスクがその判断を待っているときは、そのタスクも進まない（ADR 0161）。
- 小さな問題 1 件にも、実装・レビュー・pull request・CI が 1 回ずつ要る。その分、トークンと CI の時間を使う。
- 仕分けの決まりが、[Issue の起票](../conventions/issues.md) と [実装のループ](../conventions/implementation-loop.md) の 2 つの文書にまたがる。ループの文書には、違う点だけを書く。
