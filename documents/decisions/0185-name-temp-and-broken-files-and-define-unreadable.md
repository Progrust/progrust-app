## 背景

[データの保存場所](../spec/architecture/data-locations.md)「書き込みの規則」は、一時ファイルに書いてからリネームすることと、読み込めないファイルを `.broken-{日時}` を付けて退避することを定めていた。一時ファイルの置き場所と名前、`{日時}` の書き方、どのような場合を「読み込めない」とするかは、決まっていなかった。Issue #82 で読み書きの部品を作るときに、決める必要があった。

## 決定

細部を [データの保存場所](../spec/architecture/data-locations.md)「書き込みの規則」に定めた。Claude が決めた。

- 一時ファイルを、書き込むファイルと同じディレクトリに置く。理由: リネームが一度に入れ替わるのは、同じファイルシステムの中だけである。
- 一時ファイルの名前を `.` で始め、`.tmp` で終える。理由: `drafts/` などで `.json` のファイルを並べる処理に、一時ファイルが混ざらない。
- 一時ファイルの名前にプロセス ID を入れる。理由: 同じプロセスの中の書き込みは直列化するので、名前は 1 つで足りる。アプリが 2 つ起動したときも、互いの一時ファイルを書き換えない。
- `{日時}` を `YYYYMMDDTHHMMSS` の形にする。理由: ほかのファイル名（`generation_id`、試行ログの `session_id`、分析ファイルの履歴）と同じ形にした。
- `{日時}` を現地時刻にする。理由: 学習者が Finder で退避したファイルを見たときに、手元の時計と合う。
- 同じ秒に退避が重なったときは `-2`、`-3`… を付ける。理由: リネームは、同じ名前のファイルを黙って上書きする。前に退避したファイルを失わないようにする。
- 読み込めない場合を、内容の誤り（JSON として読めない、形に合わない、`schema_version` が無い、読める版でない）に限る。理由: 退避して作り直しても、内容の誤りは直る。権限が無いなどの読み込みの失敗は、作り直しても直らない。そのうえ、読めるはずのデータを退避してしまう。
- `schema_version` が、アプリが読める版でないときも退避する。理由: 新しい版のアプリが書いたファイルを、古い形として読んで書き戻すと、知らない項目が消える。退避すれば、元のファイルは残る。
- ファイルが無いときは、ファイルを作らずに初期状態を返す。理由: 読むだけの操作で、学習者データのディレクトリにファイルを作らない。ファイルは、次に書き込むときに作る。

## 検討した他の案

- 案: 一時ファイルを OS の一時ディレクトリに置く
  - 採用しなかった理由: 学習者データと別のファイルシステムになることがあり、そのときリネームが一度に入れ替わらない
- 案: `{日時}` を UTC にする
  - 採用しなかった理由: 学習者が見る手元の時計とずれ、いつ退避したのかが分かりにくい
- 案: 読み込みに失敗したときも、退避して作り直す
  - 採用しなかった理由: 失敗が一時的なものでも、読めるはずのデータを退避してしまう

## 影響

- 書き込みの途中でプロセスが止まると、一時ファイルが残ることがある。残った一時ファイルは、同じプロセス ID の書き込みで上書きされる。ほかのプロセス ID のものは残る。
- 古い `schema_version` を変換する処理（[データの互換性](../spec/non-functional/data-compatibility.md)）を作るときは、読み込みで、変換を退避より先に行う。
