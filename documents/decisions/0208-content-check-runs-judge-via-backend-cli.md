## 背景

教材チェックツールの「模範解答」「初期コード」は、[コード実行・判定](../spec/exercise-runner/index.md) の判定処理を使うと定めていた。教材チェックツールは Node.js で動く TypeScript のツール（`tools/`）で、判定処理はバックエンドの Rust のコードにある。ツールから判定処理をどう使うかが決まっていなかった。実装計画の M2 で、教材チェックツールの演習の検査を作るために決める必要があった。

## 決定

Claude が決めた（[教材チェックツール](../spec/content-guidelines/check-tool.md)）。

- バックエンドのクレート（`src-tauri/`）に、判定だけを行うコマンドラインのプログラムを置く（`src-tauri/src/bin/`）。教材チェックツールは、これを `cargo run`（`--locked`）で起動し、レッスンのディレクトリと、判定するファイル（`solution/` か `starter/`）を渡して、判定結果を JSON で受け取る。
  - 理由: アプリと同じコードで判定するので、教材チェックツールで通った模範解答は、アプリでも通る。判定を TypeScript で書き直すと、2 つの実装の食い違いが起きうる。同じクレートに置けば、依存とロックファイル（`src-tauri/Cargo.lock`）も 1 つで済む。
- 判定の作業領域は、アプリの学習者データ（`{app_data_dir}`）ではなく、`src-tauri/target/` の下の教材チェックツール専用のディレクトリにする。ビルド先の分け方はアプリの作業領域と同じにする。
  - 理由: 開発者の実際の学習者データを読み書きしない（[テストの方針](../spec/non-functional/testing.md) のバックエンドのテストと同じ考え方）。`src-tauri/target/` は git の対象外で、CI のキャッシュにも入るので、ビルドの結果を使い回せる。

## 検討した他の案

- 案: 判定処理を TypeScript で書き直し、教材チェックツールの中で動かす
  - 採用しなかった理由: アプリの判定と食い違いうる。判定の仕様を変えるたびに 2 か所を直す必要がある
- 案: 判定処理を別のクレートに分け、アプリと判定のプログラムの両方から使う
  - 採用しなかった理由: いまはリポジトリの構成を変えるほどの理由が無い。判定のプログラムに Tauri の実行時が要らないようにすれば、同じクレートでも足りる

## 影響

- 判定のロジックは、Tauri の実行時に頼らずに呼べるようにする（[テストの方針](../spec/non-functional/testing.md)「自動テストで確かめるもの」と同じ）。
- `src-tauri/` に実行ファイルが 2 つになるので、`tauri dev`・`tauri build` が起動するのはアプリの実行ファイルであることを、`Cargo.toml` で指定する。
- 教材チェックツールの実行（CI と実装のループの機械のチェック）で、実物の `cargo` が要る。
- 許可クレートを使う演習の判定には、作業領域の初回準備（ネットワークが要る）が要る。許可クレートを使う演習の検査のしかたは、初回準備を作るときに決める。
