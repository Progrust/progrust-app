## 背景

ユーザーは、実装の仕組みについて、次のように求めた（[ADR 0160](0160-plan-implementation-as-task-issues-on-github.md)「背景」）。

- 「なるべくコスパよく作りたい。haiku、sonnet、opusを組み合わせて難易度ごとに実施するモデルを切り替える。」
- 「レビューを仕組みに組み込む」

Claude が理由を尋ねると、ユーザーは、選択肢（Claude が示した）をすべて選んだ。

- モデルを使い分ける理由
  - 利用枠を長持ちさせたい: 上位モデルだけで回すと、サブスクリプションの利用枠をすぐ使い切り、ループが止まる。
  - 追加の料金を払いたくない: 今のプランの範囲で作りきりたい。
  - 簡単な作業に上位は無駄: 定型の作業まで上位モデルにさせるのは、もったいない。
- レビューを組み込む理由
  - 人が差分を見ないから: 無人で進めるので、自分の代わりに品質を確かめる手段が要る。
  - 安いモデルの誤りを拾う: Haiku や Sonnet に実装させる分、誤りを別のモデルに見つけさせたい。
  - 仕様とのずれを防ぐ: 仕様、受け入れ条件、ADR から外れた実装が積み重なるのを防ぎたい。

ループは、ユーザーの承認を待たずにマージする（[ADR 0163](0163-loop-merges-pull-requests-by-itself.md)）。Claude Code では、`claude` を呼ぶたびに、モデルを指定できる。

## 決定

- タスクの難易度ごとに、実装するモデルを切り替える。レビューを、ループの中に組み込む。ユーザーの求めによる。決まりは [実装のループ](../conventions/implementation-loop.md)「モデル」と [実装のレビュー](../conventions/implementation-review.md) に定める。
- 次の内容は、Claude が案として示し、ユーザーは変更を求めなかった。理由は Claude が挙げた。
  - 難易度を小・中・大の 3 つにし、実装を、小は Haiku、中は Sonnet、大は Opus にする。難易度は、計画を作るときに、タスクごとに決める。理由: ユーザーが挙げた 3 つのモデルに、1 つずつ当てる。実装を始めてから難易度を見積もると、見積もりにもトークンを使う。
  - レビューは、実装したのとは別の会話のモデルにさせ、差分と仕様・受け入れ条件・ADR だけを読ませる。実装した側の説明は渡さない。理由: 実装した会話は、自分の判断を正しいものとして見直しがちである。説明を渡すと、レビューする側が、その説明に沿って読んでしまう。
  - 機械のチェック（lint、整形の確認、自動テスト、文書の検査）を、レビューの前に実行する。理由: 機械で分かる誤りに、レビューのトークンを使わない。
  - 直しは、実装したモデルで 2 回まで、それでも通らなければ 1 段上のモデルで 1 回とし、それでも通らないタスクは行き詰まりとして脇に置く。理由: 回数を限らないと、通らないタスクでトークンを使い続ける。安いモデルで通らないタスクは、難易度の見積もりが低かったことがある。
  - チェックを通すために、テスト・lint の規則・仕様・受け入れ条件を弱めることを禁じる。理由: 通すことが目的になると、確かめる側を変えて通すことができてしまう。
  - 実装計画は、Opus の会話で作る。理由: 安いモデルで実装できるかどうかは、タスクの Issue の書き方で決まる。
- 次の細部は Claude が決めた。
  - レビューのモデルを、小と中は Sonnet、大は Opus にする。理由: 実装したモデルと同じか、それより上のモデルが見る。小のタスクを Haiku がレビューすると、ユーザーが挙げた「安いモデルの誤りを拾う」にならない。
  - 引き上げたモデルは、新しい会話で直す。同じモデルでの直しは、実装した会話を続ける。理由: 引き上げるのは、行き詰まった考え方から離れるためである。同じモデルでの直しは、読み直しを省いたほうが、トークンを使わない。
  - 大のタスクには、引き上げるモデルを置かない。理由: ユーザーが挙げたモデルの中では、Opus がいちばん上である。
  - 指摘の重さを `must` と `note` に分け、`must` が無ければ合格にする。好みや書き方の違いは `must` にしない。理由: 直さなくてよい指摘でタスクが行き詰まることを防ぐ。
  - レビューする側は、ファイルを変えない。理由: 直した結果を、誰もレビューしないことになる。
  - Issue の仕分けは、Sonnet で行う。理由: 仕分けは、迷ったらユーザーに回す決まりで、直すと決めた Issue は、ループのタスクとしてレビューを通る（[ADR 0164](0164-loop-triages-issues-between-tasks.md)）。
  - 難易度とモデルの対応は、運用ルールの表に定め、スクリプトの先頭の表を、それに合わせる。

## 検討した他の案

- 案: すべてのタスクを Opus で実装する
  - 採用しなかった理由: ユーザーが挙げた理由（「背景」を参照）。利用枠をすぐ使い切る
- 案: すべてのタスクを Sonnet で実装する
  - 採用しなかった理由: ユーザーが、難易度ごとにモデルを切り替えることを求めた。難しいタスクで直しが増え、かえってトークンを使うことがある
- 案: 実装した会話に、自分でレビューさせる
  - 採用しなかった理由: 「決定」に書いたとおり、自分の判断を正しいものとして見直しがちである
- 案: 直しの回数を限らない
  - 採用しなかった理由: 通らないタスクで、トークンを使い続ける
- 案: レビューを、マージした後に行う
  - 採用しなかった理由: 誤りの上に、次のタスクが積み重なる

## 影響

- 小と中のタスクでは、安いモデルが実装するので、直しの回が増えることがある。直しの回数と行き詰まりの件数が多いときは、難易度の決め方か、モデルの対応を見直す。
- レビューの分だけ、1 タスクに使うトークンが増える。
- レビューするのもモデルなので、誤りを見逃すことがある。人が操作して確かめることは、マイルストーンの区切りに残る（[ADR 0161](0161-run-implementation-loop-locally-and-park-human-work.md)）。
- 行き詰まりのタスクは、ユーザーが対応を決める必要がある。
- モデルの名前（Haiku・Sonnet・Opus）が指すモデルは、Claude Code の版で変わる。対応を見直すときは、運用ルールの表とスクリプトの表を、同じ変更で直す。
