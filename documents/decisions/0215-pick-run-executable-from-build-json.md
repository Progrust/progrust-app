## 背景

実行の手順は、ビルドに成功したら「生成された実行ファイル」を起動すると書いていた（[コードの実行（run）](../spec/exercise-runner/run.md)「手順」）。エディタから受け取るファイルパスは `src/` 以下の `.rs` ならよい（[実行・提出時のプロジェクトの組み立て](../spec/exercise-runner/project-assembly.md)）ので、学習者が `src/bin/` にファイルを置くと、`cargo build` は `src/main.rs` の実行ファイルのほかにも実行ファイルを作る。どれを起動するかが書かれていなかった。実装計画の M2 で、ビルドの部品（Issue #158）を作るために決める必要があった。

`cargo run` は、実行ファイルが複数あり、どれを動かすかの指定が無いと、エラーで終わる。

Claude が決めた。以下の理由は Claude が書いた。

## 決定

- 実行で起動する実行ファイルは、ビルドの標準出力の JSON のうち、`src/main.rs` を根に持つ、テスト用でない bin の成果物の `executable` とする。見つからないときは、アプリの側の失敗として終える（[コードの実行（run）](../spec/exercise-runner/run.md)「手順」の 3）。
  - 理由: 演習には必ず `src/main.rs` がある（[演習のファイル形式](../spec/content-format/exercise.md)「ファイル」）ので、演習の作者が意図したプログラムは `src/main.rs` のものである。cargo は成果物ごとに根のファイルのパスとテスト用かどうかを JSON で出すので、ファイル名や並び順から推し量らずに決められる。`test` 方式の判定で、テスト実行ファイルを同じ JSON から決めるのと同じ方法になる（[ADR 0205](0205-pick-hidden-test-executable-from-build-json.md)）。

## 検討した他の案

- 案: 実行ファイルが複数あるときは、`cargo run` と同じく、実行をエラーにする
  - 採用しなかった理由: 演習で使うのは `src/main.rs` なので、`src/bin/` のファイルがあるだけで実行できなくなる理由が無い
- 案: `target/debug/` の実行ファイルを、パッケージ名（`progrust_exercise`）で探す
  - 採用しなかった理由: ビルド先の中の置き場所は cargo の版で変わりうる。古いビルドの実行ファイルも残る

## 影響

- 学習者が `src/bin/` に置いたファイルは、コンパイルはされる（コンパイルエラーは表示される）が、実行はされない。
- 実行ファイルが見つからないのは、cargo の出力の形が変わったときなど、アプリの側の問題のときだけである。
