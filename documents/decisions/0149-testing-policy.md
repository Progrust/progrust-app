## 背景

各機能には受け入れ条件（`acceptance.md`）があるが、それを自動テストで確かめるのか、人が手で確かめるのかの方針が無かった。テストの道具も決まっていなかった。

受け入れ条件の中には、AI の出力に左右されるものがある。たとえば、質疑応答で完成コードが返らないこと（[質疑応答の受け入れ条件](../spec/qa-chat/acceptance.md)）、学習記録のアプリ管理フィールドが AI の出力に関係なく試行ログから計算した値になること、AI の出力が検証に失敗したときにファイルが変わらないこと（[学習記録・分析の受け入れ条件](../spec/learning-record-and-analysis/acceptance.md)）である。これらの確かめ方が決まっていなかった。`settings.json` の `tool_paths` には、`claude` と `cargo` の実行ファイルのパスを指定できる（[設定画面と settings.json](../spec/screens/settings-screen.md)）。アプリが `claude` に渡す環境変数は 6 つに限っている（[ADR 0124](0124-pass-only-six-env-vars-to-claude.md)）。

教材チェックツールは CI でも実行すると定めてある（[教材チェックツール](../spec/content-guidelines/check-tool.md)、[ADR 0095](0095-render-check-all-lessons-in-ci.md)）。教材チェックツールの描画のチェックは、GitHub Actions の ubuntu-latest で動くことを確かめてある（[動画の描画チェックを CI で実行できるかの技術検証](../verification/issue-7-render-check-in-ci.md)）。アプリ本体のテストを CI でどうするかは定めが無かった。リポジトリは private である（[署名なしの macOS アプリの自動更新の技術検証](../verification/issue-19-updater-unsigned-macos.md)「環境」）。GitHub の資料（2026-11-22 に確かめた）では、private のリポジトリで GitHub が用意する runner の料金は、Linux（2 コア）が 1 分あたり 0.006 米ドル、macOS が 1 分あたり 0.062 米ドルで、GitHub Free の無料の枠は月に 12 米ドル分である（Linux なら約 2,000 分、macOS なら約 190 分にあたる）。

アプリは個人開発で、対応環境は作者の Mac だけ（[ADR 0090](0090-support-only-authors-mac-until-completion.md)）、配布もしない（[ADR 0091](0091-no-distribution-or-auto-update-until-publication.md)）。

画面を自動で操作するテスト（E2E）について、Tauri の公式の資料（2026-11-22 に確かめた）は、`tauri-driver` を直接使う方法は macOS に対応していないこと（macOS には WKWebView の WebDriver が無い）と、WebdriverIO の `@wdio/tauri-service` はアプリの中に WebDriver のサーバーを組み込んで macOS にも対応することを書いている。このプロジェクトでは、どちらも試していない。技術検証では、画面の操作を自動化する代わりに、ページ自身が計測して Tauri のコマンドで JSON に書き出す方法を使った（[レッスンごとの動画の遅延読み込みの技術検証](../verification/issue-4-lazy-load-lesson-video.md)「環境」）。

ユーザーは、アプリの操作感に関わらない技術的に詳細な部分の判断を Claude に任せている。実装を始める前の調査で、Claude はテストの方針を Claude が決めて仕様に書くことを提案し、ユーザーは提案のとおりでよいと示した。方針の内容は Claude が決めた。以下の理由は Claude が書いた。

## 決定

[テストの方針](../spec/non-functional/testing.md) を新しく定める。主な判断と理由は次のとおり。

- バックエンドのロジック（判定、集計、検証、ファイルの読み書き、ジョブキュー、外部ツールの起動）は、`cargo test` の自動テストで確かめることを基本にする。テストは一時ディレクトリを使い、ウィンドウを開かずに実行できるようにする。
  - 理由: アプリの正しさの多くは、バックエンドが決める（[フロントエンドとバックエンドの役割分担](../spec/architecture/responsibilities.md)）。ロジックの誤りは、画面を触るより、テストで入力と出力を決めて確かめるほうが確実で、何度でも繰り返せる。実際の `{app_data_dir}` を使うと、作者の学習者データを壊すおそれがある。
- 学習者のプログラムのビルドと実行を確かめるテストは、実物の `cargo` を使う。
  - 理由: 判定やプロセスの扱いは、cargo と rustc の実際の出力と動きに依存する。実物の `cargo` は、作者の Mac にも CI にもあり、結果が決まっている。
- フロントエンドの自動テストには Vitest を使う。
  - 理由: Vite の設定をそのまま使えるので、設定が 1 組で済む。
- AI の出力を受けた後のアプリの動作は、決まった出力を返す偽の `claude` を使う自動テストで確かめる。偽の `claude` が返す出力は、実行ファイルのパスか、隣に置いたファイルで決める。
  - 理由: 実物の `claude` の出力は毎回変わるので、自動テストの結果が決まらない。アプリの検証・計算・書き込みが正しいかは、AI の出力を決めてしまえば、確実に確かめられる。アプリは `claude` に決めた 6 つの環境変数しか渡さないので、環境変数で出力を切り替えると、偽の `claude` に届かない。
- 実物の `claude` を呼ぶ確認は自動テストに入れず、作者がアプリを操作して確かめる。
  - 理由: 回答の中身が条件を満たすかは、AI の出力の揺れがあり、自動で白黒を付けにくい。呼ぶたびに作者のサブスクリプションの利用枠を使い、時間もかかる。CI には、作者のログインを置かない。
- 画面の見た目と操作感、動画の再生、日本語の入力、本番ビルドでしか確かめられない条件（CSP、性能の目安）は、人が操作して確かめる。見た目と操作感は、作者が実装された画面を見て確かめる。
  - 理由: 見た目と操作感は、作者が判断することである。動画の再生と日本語の入力は、技術検証でも人が見て聞いて確かめた。CSP は本番ビルドで確かめる（[ADR 0140](0140-check-csp-in-production-build.md)）。
- 画面を自動で操作するテスト（E2E）は行わない。
  - 理由: macOS の WKWebView を自動で操作する方法は限られ、使えそうな `@wdio/tauri-service` も、このプロジェクトでは試していない。取り入れるには技術検証が要り、テストを保つ手間もかかる。作者だけが使う個人のアプリで、画面は作者が見て確かめるので、その費用に見合わない。ロジックはバックエンドとフロントエンドの自動テストで確かめる。
- 各受け入れ条件をどの区分で確かめるかは、各 `acceptance.md` に書き込まず、機能を実装するときに決める。
  - 理由: 条件の数が多く、いま全部に区分を付けても、実装の形が決まるまでは確かでない。
- コミットする前に `npm run check`（lint、整形の確認、自動テスト）を実行する。AI エージェントがコミットするときも同じにする。
  - 理由: 対応環境は作者の Mac で、そこで実行するのがいちばん確かな確認になる。
- CI では、push と pull request のたびに、`npm run check` と教材チェックツールを GitHub Actions の ubuntu-latest で実行する。macOS に固有の動作を確かめるテストは、CI では実行しない。CI では本番ビルドを作らない。
  - 理由: 教材チェックツールは ubuntu-latest で動くことを確かめてあり、同じ実行環境にそろえられる。private のリポジトリでは、macOS の runner の料金は Linux の約 10 倍で、無料の枠で使えるのは月に約 190 分になる。Tauri のアプリのビルドとテストを push のたびに macOS で実行すると、すぐに枠を使い切る見込みである。CI の役目は、コミット前の確認の実行し忘れと、ロックファイルのとおりに入れた依存で通ることの確かめにとどめる。対応環境で動くことは、作者の Mac でのコミット前の確認と、人の確認で確かめる。Linux で本番ビルドを作っても、対応環境のアプリの確かめにならない。
- 作者の Mac では通り、CI の実行環境でだけ失敗するビルドやテストがあるときは、アプリのコードを Linux に合わせて直さず、そのテストを macOS のときだけ実行するか、CI で実行するものから外す。
  - 理由: 開発では macOS の他のバージョンと他の OS を考慮しない（ADR 0090）。CI の実行環境は、変更を自動で確かめるための場所で、対応環境ではない。Linux で動かすためにアプリを直すと、ADR 0090 の前提に反して、他の OS のための作業が増える。

## 検討した他の案

- 案: E2E を必須にし、WebdriverIO の `@wdio/tauri-service` で画面を自動で操作する
  - 採用しなかった理由: このプロジェクトで確かめておらず、取り入れるには技術検証が要る。作者が画面を見て確かめるので、費用に見合わない
- 案: 実物の `claude` を呼ぶテストを自動テストに入れる
  - 採用しなかった理由: 出力が毎回変わり、結果が決まらない。利用枠と時間を使う。CI に作者のログインを置けない
- 案: すべての受け入れ条件を、人がアプリを操作して確かめる
  - 採用しなかった理由: ロジックの誤りを、変更のたびに確かめられない。AI エージェントが実装を変えたときに、壊したことに気づけない
- 案: CI を macOS の runner で実行する
  - 採用しなかった理由: private のリポジトリでは料金が Linux の約 10 倍で、無料の枠をすぐに使い切る見込みである。対応環境で動くことは作者の Mac で確かめる
- 案: アプリ本体のテストを CI で実行しない
  - 採用しなかった理由: コミット前の確認を実行し忘れたときに気づけない

## 影響

- AI エージェントが実装を進めるときは、受け入れ条件のうち自動テストで確かめられるものにテストを書き、コミット前に `npm run check` を通す。
- 偽の `claude` を作り、[claude -p の呼び出しの共通ルール](../spec/claude-integration/invocation.md) の出力形式に合わせて保つ手間が要る。Claude Code の出力の形が変わったら、偽の `claude` の出力も直す。偽の `claude` で通っても、実物の `claude` で動くことにはならないので、人の確認が残る。
- E2E を行わないので、画面のつながり（画面遷移、ボタンを押した後の表示）の誤りは、人が操作して見つける。画面の誤りが多く見つかるようになったら、E2E を技術検証してから見直す（新しい ADR にする）。
- CI の実行環境は Linux で、対応環境ではない。CI が通っても、作者の Mac で動くことの確かめにはならない。Tauri が Linux でのビルドに要るライブラリを、CI で入れる手間が要る。バックエンドを ubuntu-latest でビルドしてテストすることは、このプロジェクトではまだ試していない。Linux でだけ失敗するものが多く、CI から外すものが増えるようなら、CI でバックエンドを扱うかを見直す（新しい ADR にする）。
- macOS の runner を使わない判断は、2026-11-22 の料金と、private のリポジトリであることに基づく。リポジトリを公開する、料金が変わるなど、条件が変わったら見直してよい。
