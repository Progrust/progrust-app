## 背景

初回準備で全許可クレートに依存するプロジェクトをビルドし、そのビルド結果を全演習で共有する（[ADR 0011](0011-prepare-crates-on-first-launch.md)）。演習のプロジェクトには、演習の `dependencies` に挙げたクレートだけを書く。

Issue #12 の技術検証で、許可クレートを 10 個に増やした想定の一覧で試すと、演習が許可クレートの一部だけに依存するときに、依存の一部を作り直した（[許可クレートのビルド結果の共有の技術検証](../verification/issue-12-reuse-prepared-crates.md)）。

- 原因は、cargo が依存の feature を、ビルドするプロジェクトの依存の集合ごとに決めることである。初回準備と演習で feature の組み合わせが違うと、同じクレートでも別のビルド結果になる。
- 作り直しは組み合わせごとの初回だけで、1〜8 秒だった。オフラインでも失敗はしない。
- 今の一覧（rand だけ）では起きない。
- 全許可クレートに依存する空のライブラリを作り、初回準備と演習の両方がそれに path 依存すると（検証の案 b）、すべての組み合わせで、build と test の両方の作り直しが 0 になった。演習から `use` できるクレートは、演習に直接書いたものだけのままだった。
- 同梱の `Cargo.lock` が演習と一致しなくても、cargo はエラーにせずに書き換える。`--locked` を付けると失敗する。
- 仕様の初回準備の手順の「空の `src/main.rs`」では、`main` 関数が無いのでビルドが必ず失敗する（Issue #33）。

検証の後、Claude は案 b を推奨した。ユーザーは「私は細かい技術的な話はわからないので、あなたの推奨通りで進めて大丈夫です」と示し、判断と理由を Claude に任せた。以下の理由は Claude が書いた。

## 決定

- 全許可クレートに依存する空のライブラリ `allcrates/`（パッケージ名 `progrust_allowed_crates`）を作業領域に置き、初回準備の `warmup/` と、実行・提出の `project/`、生成問題の検証の `validate/` が、どれもこれに path 依存する（[許可クレートと作業領域](../spec/exercise-runner/crates-and-workspace.md)「作業領域」、[実行・提出時のプロジェクトの組み立て](../spec/exercise-runner/project-assembly.md)）。
  - 理由: どの演習のビルドでも、許可クレートの feature の組み合わせが初回準備と同じになり、ADR 0011 の「ビルド結果を全演習で共有する」が、許可クレートが増えても成り立つ。検証で作り直しが 0 になった。演習から使えるクレートは演習の `dependencies` のまま変わらない。
- 同梱の `Cargo.lock` は、このライブラリをルートのパッケージにして生成する（[許可クレートと作業領域](../spec/exercise-runner/crates-and-workspace.md)「許可クレート」）。
  - 理由: 検証では、lock のルートとライブラリの名前が同じ状態で試した。名前が違う場合は確かめていない。
- 初回準備と演習のビルドに `--locked` と `--frozen` を付けない、と仕様に書く。
  - 理由: 同梱の lock はルートの名前も entry も演習と一致しないので、付けると必ず失敗する。後から付け足されないように明記する。
- 初回準備の `warmup/` の `src/main.rs` は `fn main() {}` にする。
  - 理由: 空のファイルではビルドが失敗し、初回準備が毎回 `failed` になる。

## 検討した他の案

- 案: 演習の `Cargo.toml` に、毎回すべての許可クレートを書く（検証の案 a）
  - 採用しなかった理由: 演習の `dependencies` に無いクレートも `use` できてしまい、レッスンが使うクレートを指定する意味（[ADR 0010](0010-allow-listed-crates.md)）が変わる
- 案: 組み合わせごとの初回だけ数秒遅いのを受け入れる（検証の案 d）
  - 採用しなかった理由: 生成問題の組み合わせは事前に分からず、どの演習で遅くなるかが読めない。組み合わせが増えるほど `target/` も大きくなる。案 b なら、追加の手間はライブラリ 1 つと path 依存の 1 行だけである
- 案: cargo の workspace で初回準備と演習をまとめる（検証の案 c）
  - 採用しなかった理由: stable の cargo では feature がそろわず、作り直しが残る

## 影響

- 作業領域に `allcrates/` が増える。初回準備の時間とディスク使用量は、仕様どおりの組み立てと変わらない（検証で確かめた）。
- `progrust_allowed_crates` というクレート名が、演習のプロジェクトの依存に入る。中身が空なので、演習のコードからは何も使えない。
- 同梱の `Cargo.lock` を作り直すときは、ルートのパッケージを `progrust_allowed_crates` にする必要がある。
