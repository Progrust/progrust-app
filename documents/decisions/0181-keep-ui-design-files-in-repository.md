## 背景

各画面のレイアウトは、実装するまでは画面デザイン「Progrust UIデザイン」に従う（[ADR 0150](0150-screen-layouts-follow-ui-design-until-implemented.md)）。画面デザインは claude.ai のアーティファクトで、[ADR 0152](0152-keep-design-system-files-in-repository.md) は、デザインシステムをリポジトリに移したときに「画面デザイン「Progrust UIデザイン」は、アーティファクトのままにする。この判断では移さない」と決めていた。

Issue #113 は、次のことを挙げていた。実装のループが呼ぶ `claude` に許可しているのは `.claude/loop-settings.json` の操作だけで、アーティファクトを読む操作は含まれない。そのため、ループで実装する画面のタスクは、画面デザインを読めない。画面デザインには、デザインシステムの部品の README・`preview.html` に無い、画面ごとの部品の組み合わせと、画面の配置の CSS（`project/styles/app.css` の `pgx-*`）がある。M1 の計画では、計画を作る会話で画面デザインを読み、画面のタスク（#93〜#96、#104）の「作るもの」に配置の要点を書いたが、CSS の値までは書いていない。

2026-11-23、ユーザーは、Issue #113 について「ルールの中でもアーティファクトを見れるようにしたい」と Claude に相談した。Claude は、次の 2 つの方法を示し、方法 2 を勧めた。

- 方法 1: ループの `claude` に、アーティファクトを読む操作（Artifact ツール）を許可する
- 方法 2: 画面デザインの中身をリポジトリに置く。リポジトリのファイルを正にする（a）か、アーティファクトを正のままにしてリポジトリには読むための写しを置く（b）かは、ユーザーに尋ねた

ユーザーは「方法2の(a)で、理由はループで画面デザインを読ませたいから、変えるならデザインシステムと同じやり方に揃えたいからです。」と示した。

同じ日、Claude は画面デザインのアーティファクトを読み、次のことを確かめた。

- アーティファクトの `project/` の下で、画面デザインそのもののファイルは、索引 `canvas.json`、`.dc.html` のファイル 34 個、`styles/app.css` の 36 ファイルだった。残りは、デザインシステムの写し（`project/ds/` の下）だった。
- `.dc.html` は、アセット（`/_blob/…`）を参照していない。参照しているのは、種類が配る `support.js`、`ds/` の下の写し、`styles/app.css`、ほかの `.dc.html` と、書体の外部の URL だけだった。
- 36 ファイルを取得してリポジトリに置き、sha256 がアーティファクトのファイルの一覧と一致することを確かめた。
- 種類「Design」の説明（`SKILL.md`、`artifact-type/reference/` の `format.md`・`view-state.md`・`design-system-components.md`）には、デザインシステムの `"editing": "code"` のような、ページを読み取り専用にする指定が無い。ページは、見る人が手で編集でき、手で編集した後の送信は断られる、と説明されている。

## 決定

- 画面デザインのファイルを、リポジトリの `design-system/ui-design/` に置き、リポジトリのファイルを正とする。アーティファクトは、リポジトリのファイルを送ったものとして残し、表示に使う（[画面デザインのファイルと変更の手順](../spec/screens/ui-design-files.md)「置き場所」「表示用のアーティファクト」）。
  - 理由: ユーザーが方法 2 の (a) を選んだ。理由は、ユーザーの言葉で「ループで画面デザインを読ませたいから、変えるならデザインシステムと同じやり方に揃えたいから」である。
  - ADR 0152 の「決定」の「画面デザイン「Progrust UIデザイン」は、アーティファクトのままにする。この判断では移さない」を、この判断で変えた。
- 置き場所は `design-system/` の下にし、アーティファクトの `project/` の下と同じ形のまま置く（Claude の判断）。
  - 理由: デザインシステムと同じ道具（`tools/design-system.py`）と同じ手順で扱える。`design-system/` は lint と整形の対象から外してあり（[ADR 0153](0153-load-design-system-css-directly-from-repository.md)）、`.dc.html` が整形で変わらない。形を変えないので、取得したファイルと送るファイルをそのまま比べられる。
- 画面デザインの中のデザインシステムの写し（`project/ds/` の下）は、リポジトリに置かない（Claude の判断）。
  - 理由: 写しの元は、リポジトリの `design-system/progrust/`・`design-system/progrust-video/` にある。写しは、種類「Design」の決まりでは、デザインシステムを入れる手順でだけ書く（ADR 0152 の「背景」）。
- ページでは編集しない。読み取り専用にする指定が無いので、決まりとして守り、送る前に、アーティファクトの中身がリポジトリと同じことを確かめる（Claude の判断。[画面デザインのファイルと変更の手順](../spec/screens/ui-design-files.md)「変更の手順」）。
  - 理由: ページで編集すると、リポジトリのファイルと食い違い、次にリポジトリから送ったときに消える（ADR 0152 がデザインシステムのページを読み取り専用にした理由と同じ）。デザインシステムと違い、ページの側で編集できなくすることはできない。
- デザインシステムを変えて画面デザインの中の写しを取り直すときに送る索引を、アーティファクトから取得したものではなく、リポジトリの `canvas.json` にする（Claude の判断。[デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md)「変更の手順」の 8）。
  - 理由: 取り直しの手順は、索引の `designSystems` の記録を書き換える。リポジトリの `canvas.json` を直さないと、次に画面デザインを送ったときに、記録が古い値に戻る。
- `tools/design-system.py` で、画面デザインも検査し（`check`）、送る引数を出し（`files ui-design`）、取得したファイルと比べる（`compare ui-design`）（Claude の判断。[画面デザインのファイルと変更の手順](../spec/screens/ui-design-files.md)「検査」）。名前を省いた `check` が画面デザインも検査するので、CI と実装のループの機械のチェックでも検査される。
- 画面を作るタスクの計画・実装・レビューでは、リポジトリの画面デザインのファイルを読む。計画では、タスクの「読む仕様」に画面デザインのファイルのパスを書き、配置や CSS の値を書き写さない（Claude の判断。[実装計画とタスクの Issue](../conventions/implementation-plan.md)「タスクの Issue」、[タスクの実装](../conventions/implementation-task.md)「作るとき」、[実装のレビュー](../conventions/implementation-review.md)「観点」）。
  - 理由: Issue #113 の問題は、ループの中で画面デザインを読めないことだった。ファイルを置くだけでは、タスクがそのファイルを読むことにならない。
- `styles/app.css` は、配置を読むためのものとし、アプリの画面の CSS にそのまま写さない（Claude の判断。[画面デザインのファイルと変更の手順](../spec/screens/ui-design-files.md)「読み方」）。
  - 理由: `styles/app.css` には、アプリの画面の CSS の書き方（[ADR 0177](0177-load-both-design-systems-and-write-app-css-with-classes.md)）に合わない規則と、画面デザインの中でだけ使う規則がある。

## 検討した他の案

- 案: 方法 1。ループの `claude` に、アーティファクトを読む操作を許可する
  - 採用しなかった理由: ユーザーが方法 2 を選んだ。Claude は、勧めない理由として次のことを挙げたが、どれも試して確かめたことではなく、見込みである。許可は道具ごとで、読む操作だけに絞れない見込みが高く、送信と削除もできるようになる。`claude -p` で動くループからアーティファクトにつながるかは、試していない。許可を足しても、サブエージェント（Explore・Plan）と CI は読めない（ADR 0152 の「背景」）。
- 案: 方法 2 の (b)。アーティファクトを正のままにして、リポジトリには読むための写しを置く
  - 採用しなかった理由: ユーザーが (a) を選んだ。理由は「変えるならデザインシステムと同じやり方に揃えたいから」である。
- 案: 画面デザインを、`design-system/` の外（リポジトリ直下の `ui-design/` など）に置く
  - 採用しなかった理由: デザインシステムと同じ道具と手順で扱えなくなり、lint と整形の対象から外す設定も別に要る（「決定」を参照）。

## 影響

- 実装のループ、Claude Code のサブエージェント、CI が、画面デザインを読める。ループの権限（`.claude/loop-settings.json`）は変えていない。ファイルを読む操作は、もともと許可している。
- 画面デザインの変更が、仕様の変更と同じコミットに入る。
- 画面デザインを変えるたびに、送る前の確認と、アーティファクトへ送る作業と、送った後の確認が要る。
- ページで編集されても、ページの側では防げない。送る前の確認か、送信が断られることで見つかる。
- リポジトリの `.dc.html` は、それだけでは表示できない（`support.js` と、`ds/` の下の写しが無い）。画面デザインを見るのは、これまでどおり表示用のアーティファクトのページである。
- 画面を実装した後は、その画面については実装を正とすること（ADR 0150）は変えない。実装した画面と、リポジトリの画面デザインのファイルは、食い違っていくことがある。
- 画面のタスク（#93〜#96、#104）の「読む仕様」に、画面デザインのファイルのパスを足した。
