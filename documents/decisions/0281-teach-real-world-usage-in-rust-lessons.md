## 背景

教材の作成ルールには、文法を正しく教える決まりはあったが、実務でどう使われるかを伝える決まりはなかった。

ユーザーは、教材に、実務での使われ方や近年のコミュニティの考え（こういう書き方はやらないほうがいい、実務ではこういう使われ方が多い、など）も交えることにした。演習も、できるだけ実務的な、そこで解いた内容が実際に活用できる問題にしたいと示した。

C の章をどうするかについて、Claude は、C の章は C を使えるようになるためではなく、Rust を深く理解するために学ぶので（[ADR 0262](0262-teach-c-chapters-before-rust.md)）、この決まりを Rust のレッスンだけに当てはめることを提案した。ユーザーはこれを承認した。

## 決定

- Rust のレッスン（動画・演習・解説）と生成問題で、実務での使われ方を伝える（[実務での書き方を伝える](../spec/content-guidelines/practice.md)）。C の章には当てはめない。
- Rust の演習は、実務で出会う題材にし、解説で実務のどんな場面で使われるかに触れる（[演習の作成ルール](../spec/content-guidelines/exercise.md)「問題」「解説」）。
- 「実務では」「コミュニティでは」と言える根拠を、決めた資料（TRPL、標準ライブラリのドキュメント、Rust API Guidelines、Clippy の既定の警告、rustfmt の既定の書式）に限り、動画では根拠を `ai_note` に書く。以下の理由は Claude が書いた。
  - 理由: 教材は AI でも作る。根拠を決めないと、確かめようのない「実務では〜」が教材に入る。`ai_note` に書けば、レビューで確かめられ、質疑応答の AI も根拠を示して答えられる。
- 意見が分かれる書き方は、分かれていることを伝え、一方を正解のように言わない。古い書き方は教材のコードに使わない。
- 模範解答と動画のコードを rustfmt の既定の書式にし、Clippy の既定の警告が出ないようにする。これはレビューで確かめ、教材チェックツールでは検証しない。
  - 理由: 教材のコードそのものが、実務での書き方の見本になるからである。
- 実務での書き方が未学習の要素を使うときは、コードを載せずに言葉で触れ、学ぶレッスンを伝える（[未登場の要素を使わない](../spec/content-guidelines/no-unseen-elements.md) の決まりを保つ）。
- 生成問題の入力に、実務での書き方の決まりを加える（[演習問題生成で AI に渡す入力](../spec/exercise-generation/ai-input.md)）。Claude が提案し、ユーザーが承認した。
  - 理由: 生成問題も Rust の演習で、レッスンの演習と同じ決まりで作るからである。

## 検討した他の案

- 案: C の章にも当てはめる
  - 採用しなかった理由: C の章の目的は、C を使えるようになることではなく、Rust を深く理解することである
- 案: 「実務では」と言う根拠を決めず、作者の判断に任せる
  - 採用しなかった理由: AI が作る教材に、根拠のない一般化が入っても気づけない

## 影響

- 教材の作者は、実務での使われ方を、決めた資料で確かめる手間が増える。
- 使える要素が少ない最初の章では、題材が小さくなる。
