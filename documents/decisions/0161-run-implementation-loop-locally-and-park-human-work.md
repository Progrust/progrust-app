## 背景

ユーザーは「なるべく人間の介入を挟まないようにループして実装を行えるような仕組みが欲しい。」と求めた。理由として、つきっきりになれないこと（自分が見ていない時間にも実装を進めたい）と、判断の負担を減らしたいこと（技術的な細かい確認に、そのつど答えるのが負担になる）を選んだ（[ADR 0160](0160-plan-implementation-as-task-issues-on-github.md)「背景」）。

実装には、人が要ることが残る。画面の見た目、動画の再生、実物の `claude` を使う確認、本番ビルドでの確認は、人が操作して確かめると定めてある（[テストの方針](../spec/non-functional/testing.md)、[ADR 0149](0149-testing-policy.md)）。アプリの操作感や方針に関わる判断と、理由がユーザーにしか分からない判断は、ユーザーに回す（[Issue の起票](../conventions/issues.md)「ユーザーに回す Issue」）。

Claude は、ループの 1 周の流れ（タスクを選ぶ、実装する、機械のチェック、レビュー、直し、pull request、マージ、Issue の仕分け）と、人が要ることでは止まらずにラベルを付けて脇に置く案を示した。あわせて、ユーザーが見るタイミングを尋ね、「マイルストーンの区切りでまとめて見る」を推奨した。ユーザーは「「決めていただきたいこと」はすべて推奨通りでよいです。」と答えた。

実行する場所について、ADR 0149 は、CI を GitHub Actions の ubuntu-latest で実行し、CI には作者のログインを置かず、CI の実行環境は対応環境ではないとしている。対応環境は作者の Mac だけである（[ADR 0090](0090-support-only-authors-mac-until-completion.md)）。

Claude Code について、2026-11-22 に公式の資料で確かめたことは、次のとおり。

- `claude -p` は、スクリプトから繰り返し呼べる。権限のモード `dontAsk` は、確認が要る操作を拒否する。`bypassPermissions` は、隔離したコンテナや仮想マシンだけで使うものとされている。
- 1 つの会話の中で繰り返す `/loop` は、開いたままの会話が要る。自分で間隔を決める形のループは、会話を再開しても復元されない。
- GitHub Actions の `anthropics/claude-code-action` は、サブスクリプションのトークン（`claude setup-token`）でも動く。クラウドの定期実行は、リポジトリを新しく取得した環境で動く。
- `--bare` は、将来、`-p` の既定になると予告されている。`--bare` は、claude.ai のログインを読まない。

同じ日に、使い捨てのリポジトリで Claude Code 2.1.329 を呼んで確かめたことは、次のとおり。

- claude.ai のログインのまま、`claude -p --permission-mode dontAsk --settings （ファイル） --output-format json` が動いた。結果は 1 つの JSON で、`is_error`・`result`・`session_id`・`permission_denials` を持つ。
- 許可していないコマンドとファイルの書き込みは、待たずに拒否された。`--settings` のファイルの `deny` に書いたパスには、書き込めなかった。
- 信頼の確認をしていない使い捨てのディレクトリでは、プロジェクトの `.claude/settings.json` の許可が無視された。`--settings` で渡した許可は効いた。このリポジトリから作った作業ツリーでは、許可を無視するという警告は出なかった。
- `--resume` に `session_id` を渡すと、`-p` でも、前の会話を続けられた。
- `/スキル名 引数` を `-p` に渡すと、`disable-model-invocation: true` のスキルも動いた。
- `--json-schema` を渡すと、結果の `structured_output` に、決めた形の値が入った。

2026-11-22 に GitHub の API で確かめたところ、このリポジトリ（GitHub Free の private）では、ブランチ保護が使えない。

## 決定

- 人が操作して確かめることと、ユーザーの判断が要ることでは、ループを止めない。ループは、それらを脇に置いて次のタスクへ進み、ユーザーは、マイルストーンの区切りにまとめて見る。ユーザーが選んだ（「背景」を参照）。決まりは [実装のループ](../conventions/implementation-loop.md)「判断待ち」「人の確認」「マイルストーンの区切り」に定める。
- 次の内容は、Claude が案として示し、ユーザーは変更を求めなかった。理由は Claude が挙げた。
  - ループは、作者の Mac で回す。理由: ADR 0149 のとおり、対応環境で確かめられるのは作者の Mac だけで、CI には作者のログインを置かない。GitHub Actions で `claude` を動かすことはできるが、Linux の実行環境になり、private のリポジトリの無料の枠を使い、ログインのトークンを GitHub に置くことになる。
  - 決まった手順（タスクを選ぶ、ブランチを作る、チェックを実行する、マージする）は、スクリプトが行い、`claude` は、考える部分（実装、レビュー、仕分け）だけに呼ぶ。理由: 決まった手順にトークンを使わない。
  - `claude` は、作業の単位（タスクの実装、レビュー、仕分け）ごとに、新しい会話で呼ぶ。同じタスクを同じモデルで直すときだけ、実装した会話を続ける（[ADR 0162](0162-pick-model-by-difficulty-and-review-in-separate-session.md)）。理由: 会話が長くなって前のタスクの内容を持ち越すことがなく、使うトークンが増えない。進み具合は GitHub にあるので、タスクをまたいで会話を持ち越す必要がない。
- 次の細部は Claude が決めた。
  - ループを回すものを、スクリプト `tools/implement-loop.py` にする。標準ライブラリだけの Python にする。理由: 既にある検査の道具（`tools/check-documents.py`）と同じで、Node.js の依存がまだ無いリポジトリでも動く。
  - ループは、ループ専用の作業ツリーで作業する。理由: ループは、何時間もブランチを切り替え、作業ツリーに変更が無い状態を要る。ユーザーが開いているチェックアウトを使うと、ユーザーの作業とぶつかる。
  - `claude` の権限は、`dontAsk` と、許可する操作を書いたファイル（実装・レビュー・仕分けで別）で決め、`--settings` で渡す。理由: 確認を待つと、誰も答えないのでループが止まる。ループの許可を、ユーザーのいる会話の許可（プロジェクトの `.claude/settings.json`）と分けて持てる。作業ディレクトリの信頼の状態によって、プロジェクトの設定の許可が効かないことがあっても、`--settings` で渡した許可は効く。`bypassPermissions` は、公式の資料が隔離した環境だけで使うものとしている。
  - コミット、push、ブランチの切り替え、pull request の操作は、`claude` に許可せず、スクリプトが行う。理由: `claude` が、決まりにない操作でリポジトリを変えることを防ぐ。
  - 保護するパス（`CLAUDE.md`、`.claude/`、`.github/`、`documents/conventions/`、検査の道具、ループのスクリプト）を決め、ループは、差分にそれらがあれば元に戻す。理由: ループが、自分の決まりと、確かめるための道具を、人が見ないうちに変えることを防ぐ。権限のファイルで書き込みを拒否しても、`npm` や `cargo` が実行するプログラムはファイルを書けるので、スクリプトが差分で確かめる。
  - ユーザーの判断が無いと進められないタスクは、判断を求める Issue の番号を、タスクの「前提」の行に足す。理由: その Issue が閉じれば、タスクが、また選ばれるようになる。ユーザーがラベルを外す手間が要らない。
  - ループが進められなかったタスクには `行き詰まり` を、マージした後に人が確かめることが残るタスクには `人の確認待ち` を付ける。理由: 一覧のための Issue を作らずに、ラベルで絞り込んで一覧できる（[ADR 0121](0121-no-tracking-issues-use-labels.md)）。
  - `claude`・`gh`・`git` の失敗（利用枠の上限、認証の失敗、時間切れを含む）では、タスクにラベルを付けずに、ループを止める。理由: 利用枠の上限に達したときに、残りのタスクが次々に行き詰まりになることを防ぐ。
  - 行き詰まりが 3 件続いたら、ループを止める。理由: 続けて行き詰まるときは、土台やチェックそのものが壊れていることがあり、続けるとトークンを無駄にする。
  - ループを始めるのはユーザーとし、AI エージェントは、自分からループを始めない。理由: ループは、ユーザーの承認を待たずにマージする（[ADR 0163](0163-loop-merges-pull-requests-by-itself.md)）。いつ回すかは、ユーザーが決める。

## 検討した他の案

- 案: GitHub Actions で `claude` を動かして回す
  - 採用しなかった理由: 「決定」に書いたとおり。ADR 0149 の、CI に作者のログインを置かない方針にも反する
- 案: クラウドの定期実行で回す
  - 採用しなかった理由: 新しく取得した環境で動き、作者の Mac でのチェックにならない
- 案: 1 つの会話の中で、サブエージェントを呼んで回す（`/loop` など）
  - 採用しなかった理由: 会話を開いたままにする必要がある。会話が長くなり、決まった手順にもトークンを使う。止まったときに、続きから始める仕組みを別に要る
- 案: 人が確かめることがあるタスクでは、確かめるまでマージしない
  - 採用しなかった理由: 画面のタスクのたびにループが止まり、ユーザーが選んだ「まとめて見る」にならない。後ろのタスクも進まない
- 案: 権限の確認をすべて省く（`bypassPermissions`）
  - 採用しなかった理由: 公式の資料が、隔離したコンテナや仮想マシンだけで使うものとしている。ループは、作者の Mac でそのまま動く

## 影響

- ユーザーが見ていない間に、実装が進む。ユーザーが確かめるのは、マイルストーンの区切りになるので、誤りに気づくのが遅れることがある。そのときは、マージ済みのタスクをさかのぼって直す。
- ループを回している間、作者の Mac でビルドとテストが動き続ける。ループ専用の作業ツリーの分、ディスクを使う。
- ループのスクリプトは、偽の `gh` と偽の `claude` を使うテストで確かめただけで、実物のタスクではまだ動かしていない。`M0 土台` で試運転する（[実装計画とタスクの Issue](../conventions/implementation-plan.md)「マイルストーン」）。
- `--bare` が `-p` の既定になると、claude.ai のログインで呼んでいるこのスクリプトも、動かなくなるおそれがある。アプリについての同じ問題は、Issue #44 にある。
- 利用枠の上限に達したときの `claude` の出力は、確かめていない。スクリプトは、`claude` のどの失敗でも止まるようにしてある。
- 保護するパスを変えるタスクは、ループでは進められない。ユーザーのいる会話で行う。
