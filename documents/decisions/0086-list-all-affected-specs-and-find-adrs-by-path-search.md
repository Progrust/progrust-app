- 置き換え: なし

## 背景

ユーザーが「現在のドキュメントの構成や作りはAIエージェントにとって検索しやすいですか？ドキュメントの数が多いので、必要な知識にすぐに辿れるのか気にしています。」と尋ねた。確かめるために、バンドルの中身を知らないエージェントに `documents/index.md` から 4 つの調べものをさせた。仕様を探す 2 問は 4〜5 ファイルで迷わずに届いた。質疑応答を変える前に確かめる ADR を洗い出す 1 問は、15 回の操作をしても、漏れがないと言い切れなかった。

原因は次の 3 つだった。

- ADR を探す手順が 2 つあり、結果が違った。`CLAUDE.md` は `decisions/index.md` で確かめると書き、運用ルールは `decisions/` を仕様のパスで検索すると書いていた（0082）。
- 索引は、ADR を関連仕様の先頭の仕様の見出し 1 か所にだけ載せる（0083）。質疑応答の見出しの下にあるのは 0025 と 0072 だけだが、パスで検索すると 0001 と 0046 も見つかった。ADR 85 件のうち 28 件は、関連仕様が複数の機能にまたがっていた。
- 関連仕様に何を載せるかの決まりが無く、判断が別の機能の仕様の内容を決めていても、その仕様へのリンクが無い ADR があった。0065 は質疑応答に渡す文を決めているが、関連仕様に質疑応答の仕様が無く、パスの検索でも見つからなかった。

Claude は改善案として、探す手順をそろえることと、ADR の関連仕様を補うことを提案した。関連仕様へのリンクの追加は、運用ルールが認める「リンク先の更新」に含まれるかが明記されていなかったので、あわせて判断を求めた。ユーザーは「改善案の1〜3すべて実施してください。」と承認した。

## 決定

- 仕様に関係する ADR は、ADR の「関連仕様」の行を、機能のディレクトリのパスで検索して探す。機能が他の機能の決まりに従うと定めているときは、参照先の機能のパスでも検索する。`decisions/index.md` の見出しだけを見て済ませない。手順は [参照とリンクの書き方](../conventions/links.md)「仕様に関係する ADR の探し方」に定め、`CLAUDE.md` もこの手順に合わせる。
- 関連仕様には、ADR の「決定」と「影響」が内容を決めている仕様の concept と、制約している仕様の concept を、他の機能のものも含めてすべて載せる。「背景」や理由の説明で触れているだけの仕様と、例として挙げただけの仕様は載せない。
- 採用した ADR にも、関連仕様へのリンクを足してよい。足すリンクは末尾に書き、先頭のリンクは入れ替えない。理由: 索引の見出しは先頭のリンクで決まるので、先頭を変えなければ索引は変わらない。
- 他の concept が定めた内容を言い直しているだけの concept、受け入れ条件、用語集、未決事項は、判断がそれ自体を対象にしているときを除いて載せない。理由: 見直しのときに、載せるかどうかで判断が分かれた。内容を定めている concept に絞れば、同じ判断で載せられる。
- この決まりに合わせて、0001〜0078 の関連仕様を見直し、抜けていたリンクを足す。「背景」「決定」「検討した他の案」は書き換えない。見直しでは、46 件の ADR に 85 本のリンクを足した。
- 変える範囲が機能のディレクトリより狭いときは、その内容を定めている concept のパスと、その concept があるディレクトリの `index.md` のパスで検索する。変える concept が他の機能の concept をリンクで参照しているときは、その concept のパスでも検索する。理由: 見直しのあとに、もう一度、バンドルの中身を知らないエージェントに新しい手順で調べものをさせた。質疑応答に関係する ADR は手順どおりの 6 回の操作で集まったが、字幕や動画の色のように機能の一部だけを調べるときは、ディレクトリのパスの検索が 28〜30 件を返し、絞り方の決まりが無かった。
- 検索の手順の細部と、載せない仕様の一覧は、Claude が決めた。
- 提案のときは、足す対象を「本文で触れている仕様」と説明していた。実施にあたって、Claude が「決定と影響が内容を決めている・制約している仕様」に絞った。理由: 触れているだけの仕様まで載せると、検索の結果に関係の薄い ADR が混じる（例: 0003 は、React を選ぶ理由としてチャットの UI に触れているだけである）。

## 検討した他の案

- 案: 仕様から ADR へのリンクも書く
  - 採用しなかった理由: 0082 が、同じ事実が 2 か所になる（SSOT）という理由で採用しなかった。関連仕様がそろっていれば、検索で足りる。
- 案: 索引で、1 つの ADR を関係する仕様の見出しすべてに載せる
  - 採用しなかった理由: `index.md` には同じものを 2 回載せない決まりで、検査（`index-coverage`）もそう確かめている。関係の全体は、関連仕様の行が持っている。
- 案: 判断が及ぶ機能ごとに、目印として何かの concept へのリンクを載せる（質疑応答のモデルの既定値を決めた 0023 に、質疑応答の仕様へのリンクを載せるなど）
  - 採用しなかった理由: その内容が書いてある concept が、その機能のディレクトリに無いことがある（質疑応答のモデルの既定値は Claude Code 連携の仕様にだけ書いてある）。内容の無い concept へリンクすると、リンクの意味がぼやける。代わりに、機能が従うと定めている参照先の機能も検索する手順にした。
- 案: ADR の本文の全体を、機能の名前で検索して探す
  - 採用しなかった理由: 例や背景で触れただけの ADR が混じり、機能の名前を使わずに書いた ADR は漏れる。広く探すときの補助の手順としては残した。

## 影響

- ある機能に関係する ADR の大半は、関連仕様の行の検索で集められる。見直しのあとの調べものでは、質疑応答の見出しの下の 2 件（0025・0072）に加えて、0001・0021・0046・0065 と、Claude Code 連携の ADR が、手順どおりの検索で見つかった。
- 検索で集まるのは、関連仕様に載っている ADR だけである。ADR の本文が別の ADR を理由に挙げているだけのとき（0048 が挙げる 0039 など）は、見つかった ADR の本文からたどる必要がある。
- 範囲の広い機能のディレクトリ（画面仕様、教材データ形式）は、パスの検索が 30 件近くを返す。concept のパスで絞る手間がかかる。
- ADR を書くときは、判断が内容を決めている仕様を、他の機能のものも含めて確かめて関連仕様に載せる必要がある。仕様を変えて、既存の ADR の判断が別の concept の内容も決めるようになったときは、その ADR の関連仕様にリンクを足す。
- 関連仕様に載せる仕様の範囲は、検査では確かめられない。載せ漏れは、ADR を書く人が運用ルールを読んで防ぐ。
- 関連仕様の行だけを検索するので、本文で仕様のパスを例に挙げただけの ADR（0081 など）は結果に入らない。
