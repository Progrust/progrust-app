## 背景

アプリのページには CSP を設定している（[ADR 0111](0111-bundle-monaco-and-set-csp.md)）。Issue #46 の技術検証で、次のことが分かった（[音声をアプリ同梱データから asset:// で読む再生の技術検証](../verification/issue-46-serve-narration-via-asset-protocol.md)「開発時の起動（`tauri dev`）でも読めるか」）。

- デスクトップの開発時の起動（`tauri dev`）では、ページは Vite の開発サーバーから配られ、応答に CSP のヘッダーが無く、CSP の違反は 1 件も出なかった。本番ビルドでは `connect-src` で拒否される `fetch(asset://…)` も、開発時は読めた。
- Tauri は CSP を、`tauri://` でページを配るときの応答ヘッダーとして付ける。デスクトップの開発時は、WebView が開発サーバーの URL を直接開く。開発時用の CSP（`app.security.devCsp`）も同じ経路で付くので、デスクトップの開発時には掛からないとみられる（試していない）。

このため、CSP に反するコードを書いても開発時には動き、本番ビルドで初めて拒否される。仕様には、開発時に CSP をどう扱うかの定めが無かった（Issue #58）。

この判断は、ユーザーが呼んだ Issue の仕分け（`/triage-issues`）で、Claude が決めた。CSP を仕様に定める判断は、ADR 0111 でユーザーが Claude に任せた。以下の理由は Claude が書いた。

## 決定

- デスクトップの開発時の起動では CSP が掛からないことを仕様に書き、CSP の下で動くかどうかは本番ビルドで確かめることにする（[セキュリティとプライバシー](../spec/non-functional/security-privacy.md)「アプリ自体」）。
  - 理由: 開発時に CSP が掛からないことは、検証で確かめた事実である。開発時に動いたことを、CSP の下で動いたことと取り違えないよう、確かめる場所を本番ビルドに決めておく。
- 本番ビルドで、動画を再生し、演習画面を操作したとき、CSP の違反が出ないことを、受け入れ条件にする（[非機能要件の受け入れ条件](../spec/non-functional/acceptance.md)）。
  - 理由: 動画の Player、音声、Monaco Editor は、どれも CSP の読み込み先に関わる部品である（ADR 0111 の「影響」）。完成の判断のときに、本番ビルドで違反が無いことを確かめる。
- 開発時の起動に CSP を掛ける方法は、この判断では決めない。

## 検討した他の案

- 案: 開発時も CSP が掛かるようにする（Vite の開発サーバーの応答に CSP のヘッダーを付ける、`app.security.devCsp` を設定する、など）
  - 採用しなかった理由: どの方法も確かめていない。`devCsp` は、デスクトップの開発時には掛からないとみられる。開発サーバーは、変更をすぐに画面に映す仕組みのために本番と違う読み込みをするので、本番と同じ CSP をそのまま付けられるかが分からない。本番と違う CSP を付けると、本番の CSP の下で動くことの確かめにならない。確かめるには技術検証が要る
- 案: 何も定めない
  - 採用しなかった理由: CSP に反するコードが、本番ビルドを動かすまで見つからない。どこで確かめるかが決まっていないと、確かめないまま進むおそれがある

## 影響

- 開発時の起動で動いても、本番ビルドで CSP に拒否されることは、これまでどおり起きうる。CSP の読み込み先に関わる変更（部品の追加・版上げ、読み込み先の追加）をしたときは、本番ビルドで確かめる手間が要る。
- 開発時にも CSP の違反を見つけたくなったときは、開発時に CSP を掛ける方法を技術検証で確かめてから、決め直す。
