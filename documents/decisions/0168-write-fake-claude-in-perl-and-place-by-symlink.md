## 背景

[テストの方針](../spec/non-functional/testing.md)「偽の claude と偽の cargo」は、偽の `claude` を「テスト用の実行ファイル（シェルスクリプトなど）」にし、受け取った引数・環境変数・標準入力をファイルに書き残すと定めていた。アプリが `claude` に渡す環境変数は 6 つだけである（[ADR 0124](0124-pass-only-six-env-vars-to-claude.md)）。後のタスクでは、アプリが 6 つだけを渡していることを、偽の `claude` が書き残した環境変数で確かめる。

Issue #76（偽の `claude` と偽の `cargo`・`rustc` を作るタスク）の実装で、作者の Mac（macOS 27.2.1）で次のことを確かめた。

- 環境変数を `HOME`・`USER`・`LOGNAME`・`PATH`・`SHELL`・`TMPDIR` の 6 つだけにして `#!/bin/sh` のスクリプトを起動し、その中で `/usr/bin/env` を実行すると、6 つのほかに `PWD`・`SHLVL`・`_` が出た。sh が子のプロセスに足すためである。
- 同じ 6 つで `#!/usr/bin/perl` のスクリプトを起動すると、`%ENV` は 6 つだけだった。`/usr/bin/perl` は perl 5.34.1 だった。

また、テストは `cargo test` で並べて実行される。実行ファイルをテストの中で書き出してすぐに起動すると、Linux では、別のスレッドが同時に起動した子のプロセスが書き込みのファイルを開いたままのことがあり、起動が「Text file busy」で失敗することが知られている（このプロジェクトでは試していない）。CI は ubuntu-latest で実行する（[テストの方針](../spec/non-functional/testing.md)「CI」）。

プロジェクトの方針（`CLAUDE.md`）で、アプリの操作感に関わらない技術の詳細は、Claude が最適と思う方法で決めることになっている。この判断は、ユーザーがスキル `implement-task` で Issue #76 の実装を頼んだ会話で、Claude が決めた。以下の決定と理由は、すべて Claude の判断である。

## 決定

- 偽の `claude` は、perl の組み込みの機能だけで書いたスクリプト（`/usr/bin/perl`）にする（[テストの方針](../spec/non-functional/testing.md)「偽の claude と偽の cargo」）。
  - 理由: sh で書くと、受け取った環境変数に sh が足したものが混ざり、アプリが渡した環境変数をそのまま書き残せない。足された変数を除いて書き残すと、アプリが誤って同じ名前の変数を渡したときに気づけない。perl は環境変数を足さず、子のプロセスを作らずに止まれる（応答しない失敗）。`/usr/bin/perl` は macOS に入っている。Ubuntu でも、必須のパッケージ（`perl-base`）が入れるものだが、CI の実行環境で偽の `claude` が動くことは、この判断の時点ではまだ確かめていない。モジュールを使わないのは、CI の実行環境に入っているモジュールを確かめていないからである。
- 偽の `cargo`・`rustc` は、sh のスクリプトにする。
  - 理由: 環境変数を書き残す必要が無く、版を返すだけで済む。
- テストでは、偽のツールの原本（`src-tauri/tests/` の下）を指すシンボリックリンクを、テストごとの一時ディレクトリに置き、返す出力をリンクの隣のファイルに書く。
  - 理由: 実行ファイルを写さないので、並べて実行したテストが「Text file busy」で失敗することが無い。リンクのあるディレクトリが、テストごとに分かれるので、テストを並べて実行しても、返す出力と書き残したものが混ざらない。

## 検討した他の案

- 案: 偽の `claude` を sh で書き、sh が足す `PWD`・`SHLVL`・`_` を除いて書き残す
  - 採用しなかった理由: アプリが誤って、同じ名前の変数を渡したときに気づけない。sh の実装によって足す変数が違うこともありうる
- 案: 偽の `claude` を Rust のプログラムにし、`Cargo.toml` の `[[bin]]` として作る
  - 採用しなかった理由: Tauri の本番ビルドは、パッケージの主なバイナリ以外のバイナリもアプリに入れうるので、偽のツールが同梱されるおそれがある（このプロジェクトでは試していない）。テストの前にビルドの手順も要る
- 案: 偽のツールを、テストの中で一時ディレクトリに写して使う
  - 採用しなかった理由: 並べて実行したテストが、Linux で「Text file busy」で失敗するおそれがある

## 影響

- 偽の `claude` を直すときは、perl の組み込みの機能だけで書く。
- macOS から `/usr/bin/perl` が無くなったときと、CI の実行環境で偽の `claude` が動かなかったときは、偽の `claude` の書き方を見直す（新しい ADR にする）。
- テストは、偽のツールのパスとして、一時ディレクトリのリンクのパスを使う。リンクを使うので、偽のツールのテストは macOS と Linux のように、シンボリックリンクを使える OS でだけ動く。
