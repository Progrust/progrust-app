## 背景

C の演習の提出では、メモリリークを、確保と解放を数えるライブラリを環境変数 `DYLD_INSERT_LIBRARIES` で検査なしの実行ファイルに差し込んで検査すると決めた（[ADR 0266](0266-build-c-exercises-with-clang-and-check-memory-on-submit.md)）。ライブラリの作り方と置き方と、検査の起動がふつうに終わらなかったときの扱いは、コード実行・判定の未決事項に残っていた。

Claude は、Issue #294 で技術検証をした（[確保と解放を数えるライブラリでメモリリークを検査できるかの技術検証](../verification/issue-294-leak-check-library.md)）。決め手になったことは次のとおりである。

- 呼び出し元のアドレスが学習者の実行ファイルの `__TEXT` セグメントの中にある確保だけを記録するライブラリで、C の章で想定する形の 52 本のプログラムの件数が正しかった。標準ライブラリが内部で確保する領域は数えず、差し込んでも標準出力と終了コードは変わらなかった。
- `strdup` の領域は、置き換えないと数えなかった。置き換えに足すと数えた。
- 差し込んだ学習者のプログラムが `fork` と `exec` で子プロセスを起動すると、子にもライブラリが入り、同じ結果のファイルに書いた。ライブラリが読み込まれたときに環境変数を消すと、入らなかった。
- 置き方は、2 つの案のどちらでも差し込めた。
  - アプリに同梱する案: quarantine 属性の値にかかわらず、本番ビルドの `.app` の写しの中のライブラリを差し込めた。ただし、ライブラリをアプリのビルドのときに作る必要があり、CI（ubuntu-latest）ではそのライブラリを作れない。
  - ソースを学習者の `clang` でビルドする案: ビルドは 0.08 秒で、環境変数が無くてもビルドできた。
- `_exit` で終わったプログラムは、終了コード 0 なのに結果のファイルを書かなかった。検査なしと検査つきで動きが変わるコード（初期化していない領域を読むコードなど）では、手順の 3 を通っても、手順の 4 の起動が異常終了しうる。

Claude は、画面に出るものが変わる点として、検査の起動がふつうに終わらなかったとき（終了コードが 0 以外、シグナルで終了、結果のファイルが無い）のテストケースの扱いをユーザーに尋ねた。案は、`runtime_error` にする（Claude が勧めた）、`pass` にする、提出をアプリの側の失敗にする、の 3 つである。ユーザーは、`runtime_error` にする案を選んだ。

## 決定

- メモリリークの検査の起動が、終了コード 0 以外かシグナルで終わったとき、結果のファイルができなかったとき・読めなかったとき・形に合わなかったとき、記録の上限を超えたときは、そのテストケースを `runtime_error` にする（[C のコードの提出（submit）](../spec/exercise-runner/c-submit.md)「手順」）。
  - 理由: ユーザーが選んだ。Claude が勧めた理由は、学習者のプログラムの動きが原因なので不正解として示すのがよく、`pass` にすると、検査できなかった解放し忘れを見逃すことである。
- 次の細部は Claude が決めた。
  - ライブラリのソースはバックエンドのクレートに埋め込み、提出のたびに、2 つのビルドの後で、作業領域の `leakcheck/` に書き出して、検出した `clang` でビルドする。教材チェックツールの判定も同じ手順で行う（[C のコードの提出（submit）](../spec/exercise-runner/c-submit.md)「メモリリークの検査」、[C の演習の作業領域とビルド](../spec/exercise-runner/c-project-assembly.md)「ビルド」）。理由: アプリ・開発時の起動・教材チェックツールで、ライブラリの場所を分けずに同じ手順にでき、ビルドスクリプトとリソースの設定と CI に手を入れずに済む。ライブラリが、学習者の実行ファイルと同じ `clang` で作られる。費用は、提出ごとに 1 回 0.08 秒ほどのビルドである。
  - ライブラリのビルドに失敗したときは、提出をアプリの側の失敗として終える（同上）。理由: 2 つのビルドが通った後なので、学習者のコードが原因ではない。
  - ライブラリのビルドにも、ビルド時間の制限を当てる（[実行・判定の制限値](../spec/exercise-runner/limits.md)「C の演習」）。
  - ライブラリは、`malloc`・`calloc`・`realloc`・`strdup` の確保を数え、記録できる領域を同時に 524,288 個までとし、読み込まれたときに環境変数 `DYLD_INSERT_LIBRARIES` と `PROGRUST_LEAK_REPORT` を消し、読み込まれたプロセスだけが結果のファイルを書く（[C のコードの提出（submit）](../spec/exercise-runner/c-submit.md)「メモリリークの検査」）。理由: 上の「背景」のとおり。`strdup` は C の章で扱わないが、数えると見逃しが無くなる。上限は、C の章の演習で同時に持つ領域の数より十分に大きい。
  - ライブラリのファイル名を `libprogrust_leakcheck.dylib`、結果のファイルのパスを渡す環境変数を `PROGRUST_LEAK_REPORT` とする（同上）。

## 検討した他の案

- 案: ビルド済みのライブラリをアプリに同梱する
  - 採用しなかった理由: アプリのビルドのときにライブラリを作るビルドスクリプトと、CI（Linux）でそれを飛ばす手当てが要る。教材チェックツールは `.app` に入らないので、ライブラリの場所を別に決める必要がある
- 案: ソースを同梱し、ビルドしたライブラリを作業領域の外に残して使い回す
  - 採用しなかった理由: `clang` やソースが変わったときに作り直す条件が要る。ビルドが 0.08 秒ほどなので、提出のたびに作るほうが簡単である
- 案: メモリリークの検査の起動がふつうに終わらなかったテストケースを `pass` にする
  - 採用しなかった理由: ユーザーが選ばなかった。Claude が示した難点は、検査できなかった解放し忘れを見逃すことである
- 案: メモリリークの検査の起動がふつうに終わらなかったときは、提出をアプリの側の失敗にする
  - 採用しなかった理由: ユーザーが選ばなかった。Claude が示した難点は、学習者のプログラムの動きが原因なのに、アプリの不具合のように見えることである
- 案: `strdup` を数えない
  - 採用しなかった理由: 上の「背景」のとおり、解放し忘れを見逃す

## 影響

- 提出のビルドが 3 回になる（検査なし、検査つき、メモリリークの検査のライブラリ）。
- メモリリークの検査は、macOS の dyld の interpose と `DYLD_INSERT_LIBRARIES` に頼る。CI（ubuntu-latest）では動かないので、CI で C の判定をどう動かすかは、非機能要件の未決事項に残る。
- `_exit` を使うプログラムは、出力が正しくても、メモリリークを検査できずに `runtime_error` になる。C の章では `_exit` を教えない。
