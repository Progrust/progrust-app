- 日付: 2026-11-21
- 関連仕様: [Issue の起票](../conventions/issues.md)
- 置き換え: なし

## 背景

AI エージェントは、作業中に見つけた問題を、確認せずに GitHub の Issue に起票する。対応するかどうかは、ユーザーが Issue ごとに決めることにしていた（[ADR 0088](0088-agents-file-found-problems-as-issues.md)）。AI エージェントは、自分から `未判断` を外したり、`保留` を付けたり、Issue を閉じたりしないことにしていた（ADR 0088、[ADR 0122](0122-hold-label-for-deferred-issues.md)）。ADR 0088 は「影響」で、Issue の数が増え、対応しない Issue も混じり、その分はユーザーが閉じる、としていた。

起票を始めた 2026-11-20 から 2026-11-21 までの2日で、`AI起票` の Issue は 21 件になった。ユーザーは次のように求めた。

- 「私が思っている以上に「AI起票」でIssueがどんどん作成されるので、私が1つ1つ見て処理するのは疲れるし時間がかかるので、この負担を軽減することが目的です。」
- 「作成されている「AI起票」 で「未判断」となっているものを対象に一括で処理するスキルにしたいです。私が直接確認、判断する必要があるもの以外はClaudeに判断させて処理させたいです。」

Claude は、スキルの案を示した。案の内容は、Issue を仕分ける種類、ユーザーに回す基準、判断を Issue のコメントに残して応答で一覧を報告すること、起票の決まりは変えないこと、スキルはユーザーが呼んだときだけ動くこと、直した変更をコミットしないこと、である。あわせて、ユーザーが決めることを2つ挙げ、どちらにも推奨を付けた。

- 仕分けるだけにするか、直すところまでするか。推奨は、直すところまで。大きな変更が要るものは直さず、`未判断` を外して報告に挙げるだけにする。理由: 仕分けるだけだと、対応すると決めた Issue が開いたまま溜まり、結局ユーザーが1件ずつ頼むことになる。
- 対応しない Issue を閉じることも、Claude に任せるか。推奨は、任せる。理由: 閉じるときに、また問題になる条件をコメントに書くので、状況が変われば、また起票される（[ADR 0123](0123-refile-closed-issue-when-situation-changed.md)）。閉じた Issue は開き直せる。

ユーザーは次のように答え、スキルの作成と決まりの修正を求めた。

- 「直すところまでお願いしたいです。「対応しない」で閉じるのも Claude に任せたいです。」

## 決定

- ユーザーがスキル `triage-issues` を呼んだときは、AI エージェントが、開いている Issue のうち `AI起票` と `未判断` の両方が付いたものを仕分ける。ユーザーの判断が要るもの以外は、AI エージェントが対応するかどうかを決め、直す・保留にする・閉じるところまで処理する。ユーザーの求めによる。決まりは [Issue の起票](../conventions/issues.md)「未判断の Issue の仕分け」に定める。
  - ADR 0088 の「対応するかどうかはユーザーが決める」を、ユーザーが決めるか、ユーザーが仕分けを頼んだときに AI エージェントが決める、に変える。
  - ADR 0122 の「`保留` を付ける・外すかどうかは、ユーザーが決める。AI エージェントは、自分から付けたり外したりしない」のうち、付けるほうを、仕分けのときは AI エージェントが決める、に変える。外すほうは変えない。
- 直すところまで行うことと、対応しない Issue を閉じることを AI エージェントに任せることは、ユーザーが選んだ（「背景」を参照）。
- 次の内容は、Claude が案として示し、ユーザーはそれを受けてスキルの作成を求めた。理由は Claude が挙げた。
  - ユーザーに回すのは、対応するかどうかや直し方によって、アプリの操作感や学習体験が変わるもの、アプリの範囲や方針が変わるもの、ユーザーが求めて決めたことを変えるもの、理由がユーザーにしか分からないもの、AI エージェントが迷ったものとする。理由: ユーザーは、操作感に関わらない技術的な判断を Claude に任せている（`CLAUDE.md`）。ADR は、理由を推測で書かない決まりである。迷ったものを AI エージェントが決めると、ユーザーが判断したかったものを、知らないうちに決めてしまう。
  - 判断は Issue ごとのコメントに残し、AI エージェントが判断したことを書く。応答の最後に、一覧を表で報告する。理由: ユーザーが後から判断を確かめ、変えられる。それまでのコメントには「ユーザーの判断」と書いているので、区別が要る。一覧のための Issue は作らない（[ADR 0121](0121-no-tracking-issues-use-labels.md)）。
  - 大きな変更が要る Issue は、直さずに `未判断` を外すだけにする。理由: 仕分けの中で大きな変更を始めると、仕分けが終わらず、ユーザーが確かめる変更も大きくなる。
  - 起票の決まり（迷ったら起票する）は変えない。理由: 起票を絞ると、見逃す問題が増える（ADR 0088、ADR 0123）。
  - 仕分けるのは、ユーザーがスキルを呼んだときだけにする。理由: 作業中に AI エージェントが自分から仕分けると、頼まれた作業から外れる（ADR 0088 の「本来の作業を脱線させない」）。ユーザーが知らないうちに、Issue が閉じられることにもなる。
  - 直した変更はコミットしない。理由: ユーザーが変更を確かめてからコミットできる。
- 次の細部は Claude が決めた。
  - 決まりは [Issue の起票](../conventions/issues.md) に書き、スキルには進め方だけを書いて、決まりは運用ルールを参照させる。理由: 同じ決まりを2か所に書かない。Issue の決まりは、`CLAUDE.md` が指す1つの文書にまとまる。
  - 起票のときと違い、仕分けでは調査をする。理由: 対応するかどうかを決めるには、問題がいまも残っているかと、関連する ADR を確かめる必要がある。ADR 0088 が調査をしないとしたのは、起票の手間を小さくするためで、仕分けには当てはまらない。
  - 問題がもう無い Issue と、前提が無くなった Issue は、「解消している」として閉じる。理由: 起票した後に、他の作業で直ったり、方針が変わったりしたものがある（Issue #33、#34）。
  - 対象は、仕分けを始めたときに開いていた Issue だけにする。理由: 直している途中で起票した Issue まで仕分けると、仕分けが終わらないことがある。
  - コメントの1行目に、したことと、日付と、誰の判断かを書く。理由: それまでのコメント（「保留にした（2026-11-21、ユーザーの判断）。」）と同じ形にすると、誰の判断かを同じ場所で読める。
  - ユーザーが答えなかった Issue は、`未判断` のままにする。理由: 判断が済んでいない。次に仕分けるときに、また対象になる。
  - Issue を閉じるときは、`未判断` を外す。仕分けに限らず、ユーザーに頼まれて閉じるときも同じにする。既に閉じた Issue に残っていた `未判断`（8件）も外す。理由: `未判断` は、対応するかどうかをまだ決めていないことを示す。閉じた Issue に残すと、`未判断` で絞り込んだ一覧に、判断の済んだ Issue が混じる。
  - スキルは、ユーザーだけが呼べるようにし、Issue を見る・コメントする・ラベルを変える・閉じる `gh` のコマンドを、スキルを呼んだ応答の中だけで、確認なしに実行できるようにする。理由: ユーザーが呼ぶことが、頼まれたことに当たる。リポジトリの設定で常に許可すると、スキルを呼んでいない作業でも、確認なしに Issue を閉じられるようになる。

## 検討した他の案

- 案: 起票を絞る（迷ったら起票しない、起票する前にユーザーに確認する、など）
  - 採用しなかった理由: 見つけた問題が、会話の中で流れて失われる（ADR 0088）。見逃した問題は、誰にも伝わらない（ADR 0123）
- 案: AI エージェントは仕分けるだけにして、直さない
  - 採用しなかった理由: ユーザーが、直すところまでを選んだ（「背景」を参照）
- 案: 対応しない Issue を閉じる前に、ユーザーに確認する
  - 採用しなかった理由: ユーザーが、閉じることも任せると選んだ（「背景」を参照）
- 案: スキルにせず、AI エージェントが作業中に自分から仕分ける
  - 採用しなかった理由: 「決定」に書いたとおり、頼まれた作業から外れ、ユーザーが知らないうちに Issue が閉じられる
- 案: 仕分けの決まりを、別の運用ルールの文書に分ける
  - 採用しなかった理由: [Issue の起票](../conventions/issues.md) は、起票した後の扱い（ラベルを変える者、保留と閉じるときのコメント）も定めていて、仕分けはその続きである。仕分けの決まりは、保留と閉じるときの決まりを参照する。足しても、分割の目安の約200行に収まる
- 案: AI エージェントが判断した Issue に、そのことを示すラベルを付ける
  - 採用しなかった理由: 判断はコメントに残していて（ADR 0121「影響」）、コメントの1行目の語で検索できる。ラベルを増やさずに済む

## 影響

- ユーザーは、`/triage-issues` を呼べば、`未判断` の Issue をまとめて処理できる。ユーザーが答えるのは、ユーザーに回された Issue の質問だけになる。
- 対応するかどうかを、ユーザーではなく AI エージェントが決めた Issue が生じる。ユーザーが判断したかった Issue を、AI エージェントが決めてしまうことがある。ユーザーは、コメントと報告を読んで、判断を変えられる。
- ユーザーに回すかどうかは、AI エージェントが読んで決めるので、決め方に幅がある。迷ったら回すので、ユーザーに回す Issue が多くなることがある。
- 閉じた Issue の中に、AI エージェントが判断して閉じたものが混じる。閉じた Issue と同じ問題を見つけたときの扱い（ADR 0123）は、誰が閉じたかによらず同じにする。
- 仕分けでは調査をし、直すところまで行うので、Issue が多いと、1回の仕分けに時間がかかる。
- 直した変更はコミットされないので、Issue を閉じた後に変更を捨てると、直していないのに閉じた Issue が残る。ユーザーは、報告を読んで変更を確かめ、コミットする。
- スキル（`.claude/skills/triage-issues/SKILL.md`）は `documents/` の外にあり、検査の対象にならない。決まりを変えたときは、スキルの進め方が合っているかを確かめる必要がある。
