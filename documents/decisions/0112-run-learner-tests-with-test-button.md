## 背景

実行は `cargo build` と実行だけを行い、学習者が書いたテストを動かす手段がなかった。ch11 テストの演習を作るには、学習者が自分のテストを `cargo test` で動かせる必要があり、画面での実行方法（テスト実行のボタンを別に置くか、実行ボタンの動作をレッスンで切り替えるか）が未決事項になっていた（Issue #28）。

ユーザーは「私は詳しい技術的な話はわからないので、あなたが推奨するやり方でお願いします。」と示し、判断と理由を Claude に任せた。以下の決定と理由は Claude が書いた。

## 決定

- 演習画面のコンソールに「テスト」ボタンを置き、どの演習でも表示する（[演習画面](../spec/screens/exercise-screen.md)）。押すと、学習者が書いたテストを `cargo test` で動かす（[コードの実行（run）](../spec/exercise-runner/run.md)「テスト実行」）。
  - 理由: テストの章（ch11）をモジュールの直後に置いたのは、以降の章で学習者が自分でテストを書いて確かめられるようにするためである（[ADR 0077](0077-curriculum-uses-trpl-as-coverage-guide.md)）。ボタンが ch11 の演習だけにあると、その後の章ではテストを動かせない。
- テスト実行では、cargo の出力（`Running ...`、`test {名前} ... ok`、`test result:` など）を、整形せずにそのままコンソールに表示する。ビルドだけは実行と同じく JSON の診断で行う。
  - 理由: ch11-01 では `cargo test` の結果の読み方を学ぶ。手元の Rust で書くときと同じ出力を見せる。ビルドを分けると、コンパイルエラーのエラーコードを実行と同じ方法で試行ログに残せる。
- `--no-fail-fast` を付ける。
  - 理由: 付けないと、単体テストが 1 件失敗した時点で止まり、統合テストとドキュメントテストが実行されない（2026-11-21 に rustc 1.99.1 で確かめた）。
- 結果の状態と制限値は、実行と同じものを使う。テストの失敗は `runtime_error` になる。
  - 理由: 結果の状態を増やすと、試行ログ・学習記録の入力・画面に影響が広がる。テストの成否は cargo の出力で分かる。
- 試行ログには `run` イベントとして記録し、`mode` で実行（`main`）とテスト実行（`test`）を区別する。
  - 理由: 新しいイベントの種類にすると、学習記録のジョブでの `run` / `submit` の扱い（[学習記録・分析の AI ジョブ](../spec/learning-record-and-analysis/ai-jobs.md)）を書き足す必要がある。区別できれば、分析で使える。

## 検討した他の案

- 案: 実行ボタンの動作を、レッスンごとに `cargo test` に切り替える
  - 採用しなかった理由: 切り替えた演習では、プログラムを実行できなくなる。切り替えない演習では、ch11 より後の章でテストを動かせない
- 案: 「テスト」ボタンを ch11-01 を学んだ後の演習だけに表示する
  - 採用しなかった理由: 表示の条件が、レッスンの演習と生成問題とで別に要る。学習者はプログラミングの経験がある前提で（[ADR 0002](0002-target-experienced-programmers.md)）、テストを学ぶ前にボタンが見えても困らない
- 案: cargo の出力を読み取り、テストごとの結果を表にして表示する
  - 採用しなかった理由: `cargo test` の出力の読み方を学ぶ妨げになる。読み取りの処理が増える

## 影響

- 演習画面のボタンが 1 つ増え、キーボードショートカット（Cmd+Shift+T）も 1 つ増える。
- テスト実行の出力には、cargo の `Running ...` などの行が入る。実行では、cargo 自身の進捗の表示を出さない。
- ドキュメントテストのコンパイルエラーはビルドの段階では見つからず、テストの失敗として出る。そのエラーコードは試行ログの `error_codes` に入らない。
