- 関連仕様: [試行ログ（attempts/*.json）](../spec/learning-record-and-analysis/attempt-log.md)「試行セッションのライフサイクル」、[実行・提出の試行ログへの記録](../spec/exercise-runner/attempt-log.md)、[進捗のコマンド](../spec/architecture/commands/progress.md)「end_session」
- 置き換え: なし

## 背景

Issue #155 で、試行ログを読み書きし、試行セッションを始める・続ける部品と、`run`・`submit` イベントを追記する部品を作った。仕様は、セッションの ID を `{開始日時 YYYYMMDDTHHMMSS}_{lesson_id}` とし、未完了のセッションがあれば続けるとしていたが、次のことを決めていなかった。

- 同じレッスンで、同じ秒に 2 つのセッションが始まったときの ID。ID は試行ログのファイル名なので、同じ ID にすると、前の試行ログを上書きする。試行ログは消さない決まりである（[ADR 0029](0029-keep-full-attempt-logs.md)）。
- 同じレッスンに未完了のセッションが複数あるときに、どれを続けるか。
- 実行・提出のイベントを、どのセッションに追記するか。`run_code`・`submit_code` の引数には、セッションの ID が無く、レッスン ID だけがある（[実行のコマンドとイベント](../spec/architecture/commands/run.md)）。
- 同じセッションで 2 回以上正解したときの `passed_at`。
- 正解の後に解説のモーダルを閉じて実行し、その途中で演習画面を離れたときの、セッションの終了と実行の停止の順。画面を離れると、セッションの終了（`end_session`）と実行の停止（`stop_run`）が両方起きる。止めた実行は `stopped` として試行ログに記録する（[ADR 0202](0202-stop-run-and-submit-when-leaving-exercise.md)。ユーザーが選んだ）が、終了が先に済むと、追記する先の未完了のセッションが無くなる。

## 決定

Claude が決めた。仕様の文は、関連仕様に書いた。

- 新しいセッションの ID が既にある試行ログと重なるときは、ID の開始日時を 1 秒ずつ進めて、まだ無い ID にする。`started_at` は、開いた日時のままにする。
  - 理由: 前の試行ログを上書きしない。ID の形（`{日時}_{lesson_id}`）を変えないので、ID からレッスン ID を取り出す処理と、ID の順が始めた順になることが、そのまま使える。重なるのは、同じ秒に前のセッションを終えて開き直したときだけで、ずれは数秒にとどまる。
- 未完了のセッションが複数あるときは、最後に始めたもの（ID の順で最後のもの）を続ける。
  - 理由: 部品は、未完了のセッションがあれば新しく始めないので、通常は複数にならない。複数あるのは、ファイルを手で置いたときなどで、そのときは最近の試行を続けるのが自然である。ほかの未完了のセッションは、起動時の救済（`passed_at` があるもの）の対象として残る。
- 画面の操作でセッションを終了するとき（`end_session`）は、そのレッスンの実行・テスト実行が動いていれば止め、`stopped` の `run` イベントを追記し終えてから終了する。
  - 理由: ADR 0202 のとおり、画面を離れて止めた実行を、終了する前のセッションに記録できる。フロントエンドが 2 つのコマンドを呼ぶ順に頼らない。止めるのは SIGKILL を送るだけで、追記はファイルを 1 つ書くだけなので、終了がほとんど遅れない。
- 実行・提出のイベントは、そのレッスンの未完了のセッションに追記する。未完了のセッションが無いときは、レッスンを開いたときと同じく新しいセッションを始めて追記する。終わったセッションには追記しない。
  - 理由: 実行・提出は演習画面を開いている間にだけ行い、演習画面を開いた時点でセッションは始まっている。上の終了の順を守れば、セッションが無いのは、試行ログが壊れて退避されたときなどに限られる。そのときも、実行・提出のたびに記録する決まり（[ADR 0029](0029-keep-full-attempt-logs.md)、ADR 0202）のとおり、学習者の試行を落とさない。終わったセッションに追記すると、`ended_at` の後のイベントになり、記録ジョブが読んだ後の試行ログが変わる。
- 同じセッションで再び正解しても、`passed_at` は最初に正解した日時を残す。
  - 理由: `passed_at` は、セッションが「正解」の段階に入った日時である。後の正解で書き換えると、正解するまでにかかった時間が分からなくなる。

## 検討した他の案

- 案: ID の重なりを、ID の末尾に `-2` などを付けて避ける
  - 採用しなかった理由: ID の形が `{日時}_{lesson_id}` でなくなり、`-2` がレッスン ID の一部と区別できない
- 案: 同じ秒の重なりは起こらないものとして扱う
  - 採用しなかった理由: 起きたときに、消さない決まりの試行ログを上書きする
- 案: 実行・提出のときに未完了のセッションが無ければ、記録しない
  - 採用しなかった理由: 正解の後に画面を離れて止めた実行が記録されず、ADR 0202 の決定（ユーザーが選んだ）と食い違う
- 案: セッションの終了と実行の停止の順を決めず、フロントエンドが `stop_run` を先に呼ぶことに頼る
  - 採用しなかった理由: `stop_run` は止めたら返り、記録は `run_finished` の前に行うので、呼ぶ順だけでは、記録が終了より先に済むとは限らない
- 案: 未完了のセッションが無ければ、そのレッスンで最後に終わったセッションに追記する
  - 採用しなかった理由: `ended_at` の後のイベントになり、記録ジョブが読んだ後の試行ログが変わる

## 影響

- `session_id` の日時が、`started_at` と数秒ずれることがある。開始日時は `started_at` を正とする。
- 実行・提出の部品は、レッスン ID とセッションの種類（`kind`）を渡せば、追記したセッションの ID を受け取れる。セッションの ID を画面から受け取る必要が無い。
- `end_session` を作るときは、動いている実行・テスト実行を止めて追記を待つ処理が要る。
- 試行ログが壊れて退避された後の実行・提出は、新しいセッションに記録される。壊れる前の試行は、退避したファイルに残る。
