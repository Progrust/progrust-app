## 背景

実装のループは、CI が失敗すると、指摘を付けて実装する側に直させ、また push して CI を待つ（[ADR 0162](0162-pick-model-by-difficulty-and-review-in-separate-session.md)、[ADR 0163](0163-loop-merges-pull-requests-by-itself.md)）。CI は push で走るので、直す側がファイルを変えず、新しいコミットが無いときは、push しても CI が走らない。ループは pull request のいまのチェックを読むので、前の回の失敗をそのまま読み、また「CI で失敗した」と判断していた。

2026-11-24 に、タスク #234 の 2 回目の CI が、タスクで変えていないフロントエンドのテストで失敗した。そのテストが、たまに失敗するものだったからである（#248。後に直った）。3 回目に直す側は、タスクと関係しない失敗と見て、ファイルを変えずに起票した。ループは CI を走らせずに 2 回目と同じ失敗を読み、#234 を行き詰まりにした（Issue #251）。タスクと関係しない失敗では、直す側が何をしても、その回は通る見込みが無かった。

## 決定

- ユーザーが Issue #251 への対応を求めた。直し方は Claude が技術的な判断で決めた。
- 直しの回で、push する前のコミットが、前の回に push したコミット（origin のタスクのブランチの先頭）と同じときは、空のコミットを足してから push する。決まりは [実装のループ](../conventions/implementation-loop.md)「直しと行き詰まり」に定める。
- 直しの回で、CI の失敗がタスクの変更と関係しないと、失敗の出力と差分から言えるときは、直す側はファイルを変えずに起票し、そのことを結果の報告に書く。決まりは [タスクの実装](../conventions/implementation-task.md) とスキル `implement-task` に定める。
- 次の細部も Claude が決めた。
  - 同じかどうかは、push の直前に、ローカルの HEAD と origin のブランチの先頭を比べて決める。直す側がファイルを変えたかどうかでは決めない。理由: ファイルが変わらなくても、origin の main を取り込んでコミットが増えれば CI は走る。また、前の回が機械のチェックやレビューで止まったときは、まだ push していないので、比べると違うことが分かる。
  - やり直したことは、pull request の本文の経過に書く。理由: 後から、どの回の CI がやり直しだったかを追える。
  - 直す側に、タスクと関係しない失敗ではファイルを変えなくてよいと示し、条件を「失敗の出力と差分から言えるとき」に絞る。理由: CI がやり直されると分かっていれば、関係しない失敗を通すために、タスクと関係しないファイルを変えずに済む。条件を絞るのは、直すべき失敗を関係しないとして見送る抜け道にしないためである。

## 検討した他の案

- 案: 前の回に失敗した CI の run を、`gh run rerun --failed` でやり直す。
  - 採用しなかった理由: やり直しが登録されるまで、pull request のチェックは前の回の失敗のままなので、待つ側が、やり直しが始まったことを確かめる仕組みを足す必要がある。push と pull request の 2 つの run を、両方やり直す必要もある。空のコミットなら、pull request の先頭のコミットが変わるので、前の回の結果を読むことが無く、CI を待つ処理を変えずに済む。空のコミットは squash でマージするので main には残らない。
- 案: 直す側がファイルを変えなかったときは、CI を待たずに行き詰まりにする。
  - 採用しなかった理由: たまに失敗するテストのように、やり直せば通る失敗でも、タスクが行き詰まりになる。

## 影響

- タスクと関係しない、たまに失敗するテストで CI が落ちても、直しの回で CI をやり直すので、タスクを行き詰まりにせずに通せることがある。
- タスクと関係せず、いつも失敗する CI（main が壊れているなど）では、やり直しの分だけ CI の時間を使ってから、行き詰まりになる。
- タスクのブランチに空のコミットが残る。マージは squash なので、main には残らない。
