## 背景

ドキュメントを OKF v0.3 のバンドルにした（0079）。OKF の適合条件はゆるく、frontmatter が YAML として読めることと、`index.md`・`log.md` の形を決めているだけである。ユーザーは「人間は極力ドキュメントの管理に手を出さずに済むようにする。」を前提にしている（0079）。そのため、リンク切れ、`index.md` の掲載漏れ、`description` の欠落などを機械的に見つけるしくみが要る。OKF の公式リポジトリには、適合チェック用のスクリプト（`validate.py`。PyYAML が必要）と、Claude Code 用のプラグイン（`okf-generate`・`okf-consume` のスキル）がある。どれを使い、どう実行するかを決める必要があった。

## 決定

- 公式のプラグインは入れない。公式 validator のスクリプトだけを、変更せずに `tools/okf/` へ取り込む。
- このプロジェクト独自の決まりと、このプロジェクトが使うキーの範囲の OKF の決まりは、独自の検査スクリプト `tools/check-documents.py` で検査する。このスクリプトは標準ライブラリだけで動く。
- 独自の検査は、Claude Code の Stop hook（`.claude/settings.json`）で、応答の終わりに自動で実行する。
- 公式 validator は hook に入れず、必要なとき（OKF の版を上げるときなど）に手動で実行する。
- プラグインを入れずスクリプトだけ取り込むこと、独自の検査を作って hook で自動実行することは、Claude の提案で、ユーザーが「すべて提案通りで大丈夫です。」「「決めてほしい点」もすべてあなたの推奨通りで問題ないので、この方針でドキュメントの整理をお願いします。」と承認した。
- 当初の提案は、公式 validator と独自の検査の両方を hook で実行するものだった。移行後に Claude が、公式 validator は手動にとどめる案を勧め、ユーザーが「手動にとどめるで問題ないです。」と承認した。

## 検討した他の案

- 案: 公式のプラグイン（`okf-generate`・`okf-consume`）を入れる
  - 採用しなかった理由: `okf-generate` は `log.md`・`generated`・`sources` を書く前提で、使わないと決めたもの（0080）と食い違う。
- 案: 公式 validator も hook で自動実行する（当初の提案）
  - 採用しなかった理由: hook に入れると `uv` と PyYAML が要り、無い環境では検査が走らない。独自の検査は、このプロジェクトが使うキーの範囲で、公式 validator と同じ項目を見ている。2026-11-20 に両方を実行し、どちらも指摘 0 件で一致した。

## 影響

- hook が働くのは Claude Code だけである。hook は、同じ応答の中で2回目以降は検査しない。
- 独自の検査は YAML のパーサーを使わない。frontmatter は、このプロジェクトの狭い書き方（1行に1キー、`title` と `description` は二重引用符）だけを通す。
- 独自の検査が見ない決まりがある（本文のリンクを相対パスで書くこと、ADR から仕様への片方向のリンクなど）。一覧は関連仕様にある。
- 公式 validator は 2026-11-20 に実行し、259 ファイルで error・warning とも 0 件だった。
