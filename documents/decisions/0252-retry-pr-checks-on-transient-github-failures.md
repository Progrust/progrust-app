## 背景

2026-11-25 に、実装のループが、タスク #239 の pull request（#259）の CI を待っている間に、`gh pr checks` が GitHub の側の一時的な失敗（`HTTP 504: 504 Gateway Timeout`）を返した。ループは、やり直さずに、仕組みの失敗として止まった。そのタスクは、実装、機械のチェック、レビュー、push まで済んでいて、止まった後に見ると、pull request の CI は通っていた。次にループを始めると、同じタスクを実装からやり直すことになる（Issue #269）。

前の仕分け（2026-11-25）で、Claude が対応すると決めた。変えるファイルが保護するパスなので、ユーザーのいる会話（2026-11-26 の仕分け）で直した。

## 決定

以下は、どれも Claude の技術的な判断である。

- CI を待つ間に `gh pr checks` が失敗したときは、CI を読み直す間隔（30 秒）だけ待ってから読み直す。5 回続けて失敗したときだけ、仕組みの失敗として止まる。読めたら、数え直す。決まりは [実装のループ](../conventions/implementation-loop.md)「止まるとき」に定める。
  - 理由: CI を待つのは、実装・チェック・レビュー・push まで済んだ後なので、ここで止まると、やり直しの損が大きい。GitHub の一時的な失敗は、数分の内に直ることが多い。5 回は、間隔と合わせて 2 分から 12 分ほど（`gh` の 1 回ごとの時間切れの 2 分を含む）待つことになり、一時的な失敗には足り、続く障害では長く待ちすぎない。
- 一時的な失敗かどうかを、エラーの文（HTTP の状態コードなど）では見分けず、どの失敗もやり直す。
  - 理由: ネットワークの失敗や時間切れは、文の形がさまざまで、見分け漏れると、やり直すべき失敗で止まる。認証の失敗のような、やり直しても直らない失敗でも、5 回で止まるので、損は数分で済む。
- チェックが 1 つも報告されないときと、出力を JSON として読めないときの扱いは、変えない。
  - 理由: どちらも、`gh` は成功していて、一時的な失敗ではない。
- やり直すのは、CI を待つ間の `gh pr checks` だけにする。ほかの `gh` の呼び出し（pull request を作る、マージするなど）は、これまでどおり、失敗したら止まる。
  - 理由: Issue #269 で起きたのは、CI を待つ間だけである。CI を待つ処理は、もともと何度も読み直すので、やり直しを足しても、処理の形が変わらない。ほかの呼び出しは、1 回だけ行う書き込みが多く、やり直すと、2 重に書くおそれを確かめる必要がある。

## 検討した他の案

- 案: HTTP 5xx とネットワークの失敗だけをやり直し、ほかの失敗ではすぐ止まる。
  - 採用しなかった理由: 上の理由。見分け漏れのほうが、損が大きい。
- 案: すべての `gh` の呼び出しに、やり直しを足す。
  - 採用しなかった理由: 上の理由。書き込みの呼び出しでは、やり直しで 2 重に書かないことを、呼び出しごとに確かめる必要がある。

## 影響

- CI を待つ間の GitHub の一時的な失敗では、ループが止まらず、済んだ作業を捨てずに済む。
- やり直しても直らない失敗では、止まるまでに数分かかる。
