## 背景

[ADR 0090](0090-support-only-authors-mac-until-completion.md) で、アプリの完成までは一般公開しない前提で開発することにした。ユーザーは理由として、「アプリ開発では他のバージョンやOSの確認、公開する際の懸念のために手を止めたくない。私が早く使えるようにアプリの完成を優先させたい。」と示した。

それまでの仕様は、学習者に教材とアプリを届けるために、配布物を GitHub Releases に置き、Tauri の自動更新で更新すること（ADR 0037）と、OS のコード署名を当面行わずに、警告を回避する手順を配布ページに記載すること（ADR 0038）を定めていた。

技術検証（[署名なしの macOS アプリの自動更新の技術検証](../verification/issue-19-updater-unsigned-macos.md)）では、自動更新を使うには決めることが残ると分かった。App Translocation されたアプリは更新に失敗する。private リポジトリの Releases は、認証なしでは更新ファイルを取れない。

Claude が「完成までは作らない（アプリは作者の Mac でビルドして使う。配布と自動更新は仕様から外し、一般公開をする場合に決める事項にする。ADR 0037 と ADR 0038 は新しい ADR で置き換える。教材をアプリに同梱する点は変えない）」と「自動更新は完成までに作る（配布と自動更新の仕様は macOS 向けだけ残す。技術検証で残った判断は完成までに必要になる）」を示し、ユーザーは前者を選んだ。

## 決定

- アプリの完成までは、配布物（インストーラー）、配布物の置き場所、更新の仕組み（自動更新、更新の確認）を作らない。配布のための OS のコード署名と公証も行わない。アプリは、作者の Mac でリポジトリからビルドして使う（[公開範囲と配布](../spec/non-functional/distribution.md)）。ユーザーの選択による。
- 教材はアプリに同梱する。ADR 0037 の判断のうち、この部分を引き継ぐ。理由は ADR 0037 と同じで、教材だけを配信するには、配信用のサーバーと、教材とアプリのバージョンの整合を管理する仕組みが必要になる。
- 配布と更新の方法と、OS のコード署名は、一般公開をする場合に決める未決事項として残す（[非機能要件の未決事項](../spec/non-functional/open-questions.md)）。
- 次の細部は Claude が決めた。どれも、更新の仕組みを持たないことに合わせたものである。
  - 設定画面の「バージョン情報」から、更新の確認ボタンを外す。
  - オフライン時の動作の表から「更新の確認」の行を外す。
  - 外部への通信の一覧から「更新の確認」を外す。
  - 非機能要件の受け入れ条件から、インストールと更新の条件を外し、対応環境の Mac でビルドして起動できることにする。

## 検討した他の案

- 案: 自動更新は完成までに作る（配布と自動更新の仕様を macOS 向けだけ残す）
  - 採用しなかった理由: ユーザーが選ばなかった。配布のための判断（App Translocation への対処、更新ファイルの置き場所）が完成までに必要になる。作者は、ビルドし直せば新しいバージョンを使える。
- 案: 教材だけをサーバーから配信する（ADR 0037 で検討した案）
  - 採用しなかった理由: 配信用のサーバーと、教材とアプリのバージョンの整合を管理する仕組みが必要になる。

## 影響

- 新しいバージョンや教材の修正を使うには、ビルドし直してアプリを入れ替える。
- 一般公開をする場合は、配布と更新の方法、コード署名を決めて、ADR を追加する。ADR 0037・ADR 0038 で採っていた方法（GitHub Releases、Tauri の自動更新、署名なし）と、技術検証の結果（[署名なしの macOS アプリの自動更新の技術検証](../verification/issue-19-updater-unsigned-macos.md)、[配布物と更新のサイズの技術検証](../verification/issue-20-distribution-size.md)）は、そのときの材料になる。
- 技術検証の Issue #19・#20 は、一般公開をする場合に扱う。
