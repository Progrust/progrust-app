- 関連仕様: [実装のループ](../conventions/implementation-loop.md)「ブランチ・コミット・pull request・マージ」
- 置き換え: なし

## 背景

これまで、AI エージェントは、ユーザーに頼まれたときだけコミットしていた。スキル `triage-issues` で直した変更も、コミットしない決まりである（[ADR 0130](0130-triage-undecided-issues-by-skill.md)。理由は、ユーザーが変更を確かめてからコミットできること）。

ユーザーは、人の介入をなるべく挟まずにループして実装する仕組みを求めた（[ADR 0160](0160-plan-implementation-as-task-issues-on-github.md)「背景」）。タスクは前提の順に積むので、前のタスクが main に入らないと、後ろのタスクを始められない。

Claude は、ユーザーに決めてほしいこととして、次のように尋ねた。「チェック、レビュー、CI が通った PR を、ループが自分でマージしてよいか。推奨は「よい」です。待つと、後ろのタスクが止まります。PR ごとに後から見て、取り消せます。」ユーザーは「「決めていただきたいこと」はすべて推奨通りでよいです。」と答えた。

2026-11-22 に GitHub の API で確かめたところ、このリポジトリ（GitHub Free の private）では、ブランチ保護が使えず、リポジトリの自動マージの設定も無効だった。CI は、push と pull request のたびに実行すると定めてあるが（[テストの方針](../spec/non-functional/testing.md)「CI」）、まだ作っていない。

## 決定

- ループは、機械のチェックが通り、レビューが合格で、CI が通ったタスクの pull request を、ユーザーの承認を待たずに、自分でマージする。ユーザーは、マージされた pull request を後から見て、取り消したいものを取り消す。ユーザーが選んだ（「背景」を参照）。決まりは [実装のループ](../conventions/implementation-loop.md)「ブランチ・コミット・pull request・マージ」に定める。
- ユーザーのいる会話での扱いは、変えない。AI エージェントは、ユーザーに頼まれたときだけコミットする。スキル `triage-issues` で直した変更をコミットしないこと（ADR 0130）も、変えない。
- 次の細部は Claude が決めた。
  - 1 タスクを、1 つのブランチと 1 つの pull request にし、squash でマージする。理由: main の 1 つのコミットが 1 つのタスクになり、取り消すときに、その 1 つを取り消せばよい。直しの途中のコミットが main に残らない。
  - pull request の本文に `Closes #{Issue の番号}` を書き、マージでタスクの Issue を閉じる。本文には、要約、起票せずに直した問題、追加で人が確かめること、レビューの `note` の指摘、直しの経過も書く。理由: ユーザーが後から見るときに、何が行われたかを 1 か所で読める。起票せずに直した問題を応答の最後に書く決まり（[Issue の起票](../conventions/issues.md)「起票する問題」）の、ループでの置き場になる。
  - マージは、スクリプトが CI の結果を見て行う。理由: このリポジトリでは、GitHub の自動マージが使えない。
  - CI のチェックが 1 つも報告されないときは、マージせずに、ループを止める。理由: CI が動いていない状態で、CI を通ったものとして扱わない。
  - コミットと push は、スクリプトが行い、`claude` には許可しない（[ADR 0161](0161-run-implementation-loop-locally-and-park-human-work.md)）。

## 検討した他の案

- 案: ループは pull request を作るところまでにし、ユーザーが承認してからマージする
  - 採用しなかった理由: 前のタスクがマージされるまで、後ろのタスクを始められず、ループが止まる。ユーザーが、待たないほうを選んだ（「背景」を参照）
- 案: pull request を作らずに、main に直接コミットする
  - 採用しなかった理由: マージの前に CI で確かめられない。タスクごとに、何が行われたかを残す場所がなくなる
- 案: 人が確かめることがあるタスクだけ、ユーザーの承認を待つ
  - 採用しなかった理由: 画面のタスクのたびに、ループが止まる（ADR 0161）

## 影響

- ユーザーが見ていない変更が、main に入る。確かめる手段は、機械のチェック、レビュー（[ADR 0162](0162-pick-model-by-difficulty-and-review-in-separate-session.md)）、CI と、マイルストーンの区切りでの人の確認になる。
- 取り消すときは、その pull request を取り消す。後ろのタスクがその変更を前提にしているときは、取り消すだけでは済まず、直すタスクが要る。
- pull request のたびに CI が動く。private のリポジトリの無料の枠は、Linux の実行環境で月に約 2,000 分である（[ADR 0149](0149-testing-policy.md)）。タスクが多い月に足りなくなるようなら、CI で実行するものか、実行するときを見直す（新しい ADR にする）。
- CI を作るまでは、ループはマージできない。CI は `M0 土台` で作る（ADR 0160）。
