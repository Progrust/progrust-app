## 方法

- 確保と解放を数える動的ライブラリ（下の「ライブラリの作り方」）を C で書き、`clang -dynamiclib -O2 -o libprogrust_leakcheck.dylib leakcheck.c` でビルドした。できたライブラリは `arm64` で、リンカの ad-hoc 署名（`adhoc,linker-signed`）が付いた。
- ライブラリを、空白と日本語を含むパス `…/Progrust テスト.app/Contents/Resources/leakcheck/` に置いた。
- C の章で想定する形のプログラムを、期待する件数とバイト数を決めて 52 本書いた。1 本ごとに次のことをした。
  - 作業領域 `…/Application Support/日本語 データ/workspace/c-project/` を作り直し、仕様の検査なしのビルド（`clang -std=c17 -g -O0 -Wall -Wextra -fcolor-diagnostics -o main main.c`）をした。
  - `./main` を、`c-project/` を作業ディレクトリとし、新しいプロセスグループで、差し込みなしで 1 回、差し込みありで 2 回起動した。差し込みありでは、`DYLD_INSERT_LIBRARIES` にライブラリの絶対パスを、`PROGRUST_LEAK_REPORT` に結果のファイルの相対パス `reports/leak-1` を渡した。環境変数は、Finder から起動したアプリに近いもの（`PATH=/usr/bin:/bin:/usr/sbin:/sbin`、`HOME`、`TMPDIR`、`USER` だけ）にした。標準入力を書き込んで閉じ、5 秒で止まらなければ SIGKILL を送った。
  - 差し込みありの 1 回目と 2 回目のそれぞれの後に、結果のファイルの中身を読み、期待する件数と比べた。差し込みなしの 1 回と差し込みありの 2 回で、標準出力のバイト列と終了コードを比べた。
- 本番ビルドの `.app` の写し（`Progrust 検証.app`）の `Contents/Resources/leakcheck/` にライブラリを置き、`com.apple.quarantine` を、なし・`0083`・`00c3`・`01c1`（値の意味は [署名なしの macOS アプリの自動更新の技術検証](issue-19-updater-unsigned-macos.md)）の 4 通りで、バンドルの中のすべてのファイルに付けて差し込んだ。
- 実行時に学習者の `clang` でライブラリをビルドする案の時間を測った。

## 結果

### ライブラリの作り方

- `malloc`・`calloc`・`realloc`・`free` を、ライブラリの `__DATA,__interpose` 節に置いた置き換えの表（dyld の interpose）で置き換える。置き換えた関数の中から呼ぶ `malloc` などは、本物が呼ばれる。
- 学習者の実行ファイルのコードから呼ばれた確保かどうかは、呼び出し元のアドレス（`__builtin_return_address(0)`）が、学習者の実行ファイルの `__TEXT` セグメントの中にあるかで決める。
  - `DYLD_INSERT_LIBRARIES` で差し込むと、`_dyld_get_image_header(0)`（0 番目のイメージ）は、学習者の実行ファイルではなく、差し込んだライブラリだった。0 番目を使った最初の試作は、すべてのプログラムで 0 件と報告した。ファイルの種類が `MH_EXECUTE` のイメージを探すと、正しく数えた。

```
image 0 …/dbg/dbg.dylib hdr=0x1002bc000
image 1 …/dbg/m hdr=0x1002a4000
image 2 /usr/lib/libSystem.B.dylib hdr=0x2df8a7000
```

- 記録は、確保した領域のアドレスと大きさを、ライブラリの中の固定の大きさの表（線形探査のハッシュ表。`2^20` 個の枠、16 MB の静的な領域）に入れる。解放は、どこから呼ばれたものでも、表にあれば消す。記録できる領域の数の上限は `2^19`（524,288）個にした。
- `realloc` は、成功したとき（または大きさ 0 のとき）に古い領域を表から消し、学習者のコードから呼ばれたときだけ新しい領域を記録する。失敗して `NULL` を返したときは、古い領域を残す。
- 初期化のとき（`__attribute__((constructor))`）に、結果のファイルのパスを読み、プロセス ID を覚え、`DYLD_INSERT_LIBRARIES` と `PROGRUST_LEAK_REPORT` を環境変数から消し、`atexit` で書き出しの関数を登録する。
- 書き出しは、`exit` のとき（`main` から戻ったときを含む）に、初期化のときと同じプロセスでだけ、`open`・`write` で行う（書き出しの中で確保しない）。中身は、件数とバイト数を 1 行ずつ。上限を超えたときは、件数の代わりに `overflow` の 1 行を書く。

中心の部分:

```c
static int from_learner(void *ret) {
    uintptr_t a = (uintptr_t)ret;
    return a >= text_start && a < text_end;   // 学習者の実行ファイルの __TEXT
}
static void *hook_malloc(size_t size) {
    void *p = malloc(size);
    if (from_learner(__builtin_return_address(0))) record(p, size);
    return p;
}
static void *hook_realloc(void *old, size_t size) {
    void *p = realloc(old, size);
    if (p != NULL || size == 0) forget(old);
    if (p != NULL && from_learner(__builtin_return_address(0))) record(p, size);
    return p;
}
static void hook_free(void *p) { forget(p); free(p); }
DYLD_INTERPOSE(hook_malloc, malloc)   // calloc・realloc・free も同じ
```

### C の章の形での件数

差し込みありの 1 回目と 2 回目のどちらでも、次のとおりになった。伸びる配列では、領域が移ったこと（`moved=yes`）を、`realloc` の前後のアドレスを比べて出力して確かめた。

| プログラムの形 | 期待 | 結果 |
|---|---|---|
| 確保して解放する | 0 件 | 0 件 |
| `main` の変数に残したまま終わる（100 バイト） | 1 件 100 バイト | 同じ |
| 関数の中で確保して、解放せずに戻る | 1 件 40 バイト | 同じ |
| ポインタを上書きして、最初の領域を失う | 1 件 16 バイト | 同じ |
| エラーで早く戻る経路で解放しない | 1 件 64 バイト | 同じ |
| 連結リスト 5 個をすべて解放 / どれも解放しない / 先頭だけ解放 | 0 件 / 5 件 80 バイト / 4 件 64 バイト | 同じ |
| 構造体と、そのメンバーが指す領域をすべて解放 | 0 件 | 0 件 |
| 構造体だけを解放し、メンバーが指す 2 つの領域を残す | 2 件 18 バイト | 同じ |
| 伸びる配列（`realloc` で領域が移る）を解放 / 解放しない | 0 件 / 1 件 524,288 バイト | 同じ |
| `realloc` で 1,000 バイトを 10 バイトに縮める（領域が移った）。解放 / 解放しない | 0 件 / 1 件 10 バイト | 同じ |
| `realloc` で 1,000 バイトを 1,008 バイトに伸ばす（同じ場所に残った）。解放 / 解放しない | 0 件 / 1 件 1,008 バイト | 同じ |
| `realloc(NULL, 40)` を解放 / 解放しない | 0 件 / 1 件 40 バイト | 同じ |
| `free(NULL)` | 0 件 | 0 件 |
| 確保に失敗した `malloc(SIZE_MAX / 2)`・`calloc(SIZE_MAX / 2, 8)`（差し込みの有無にかかわらず `NULL` が返り、`failed`・`null` を出力した） | 0 件 | 0 件 |
| 再帰の各段で確保して解放 / 解放しない（1,000 段） | 0 件 / 1,000 件 4,000 バイト | 同じ |
| 関数の中で `exit(0)` し、`main` の領域が残る | 1 件 50 バイト | 同じ |
| 解放してから `exit(0)` | 0 件 | 0 件 |
| グローバル変数に残したまま終わる | 1 件 32 バイト | 同じ |
| `atexit` で登録した関数で解放する | 0 件 | 0 件 |
| `qsort` で並べ替えて解放 | 0 件 | 0 件 |

- `realloc(p, 0)` は、この macOS では `NULL` でない領域を返した。それを解放しないと 1 件 0 バイトになり、解放すると 0 件になった。
- `exit` で終わったときも、終わるまでに解放されなかった領域を数えた（仕様の「プログラムが終わるまでに解放されなかった領域」のとおり）。グローバル変数から指している領域も数えた。

### 数えない領域

- 標準ライブラリが内部で確保する領域は数えなかった。`printf`・`fprintf(stderr, …)`・`fgets`・`sscanf`・`scanf` を多く使い、自分で確保した領域をすべて解放したプログラムは 0 件だった。
- `getline` に学習者が確保した領域を渡し、標準ライブラリが中で `realloc` して大きくしたプログラムも、最後に解放すれば 0 件だった。`getline` に `NULL` を渡して標準ライブラリに確保させ、学習者が解放したプログラムも 0 件だった。
- `strdup` の領域は、標準ライブラリの中の `malloc` が確保するので、数えなかった。解放しなくても 0 件になる（見逃す）。`strdup` も置き換えて、学習者のコードから呼ばれたときに記録する変種では、解放しないと 1 件 6 バイト、解放すると 0 件、`realloc` してから解放しても 0 件になった。

### 記録の上限と実行時間

| プログラム | 差し込みなし | 差し込みあり |
|---|---|---|
| `malloc` と `free` を 100 万回 | 0.03 秒 | 0.04〜0.05 秒 |
| 2,000 個の枠で、ランダムに確保と解放を 300 万回 | 0.08 秒 | 0.13〜0.35 秒 |
| 40 万個を同時に確保して解放する、を 3 回 | 0.03 秒 | 0.13〜0.16 秒 |
| 10 万個を同時に確保して解放する | — | 0.016〜0.025 秒 |
| 60 万個を同時に確保する（上限を超える） | — | 0.08 秒。結果のファイルは `overflow` |

- どれも 1 テストケースの制限（5 秒）に十分に収まった。ほかのプログラム（無限ループを除く）は、差し込みありで 0.004〜0.03 秒だった。差し込みなしの 1 回目（ビルドの直後）だけは、macOS が新しい実行ファイルを初めて起動するときの時間が加わり、0.19〜0.41 秒だった。
- 削除の印（墓石）を残す最初の試作を、印を残さずに後ろを詰める削除に変えた。確保と解放を長く繰り返しても、探す長さが伸びない。

### ふつうに終わらなかったとき

| 終わり方 | 結果のファイル | 終了コード |
|---|---|---|
| `main` から戻る、`exit(0)` | できる | 0 |
| `return 3;` | できる（1 件 8 バイト） | 3 |
| `_exit(0)` | できない | 0 |
| `abort()` | できない | SIGABRT |
| NULL への書き込み | できない | SIGSEGV |
| 無限ループを 5 秒で止めた | できない | SIGKILL |

- `_exit(0)` で終わったときは、終了コードが 0 なのに結果のファイルができない。

### 標準出力と終了コード

- 52 本すべてで、差し込みなしの 1 回と差し込みありの 2 回の、標準出力のバイト列と終了コードが同じだった。標準入力を読むプログラム（`fgets`・`scanf`・`getline`）、約 130 KB を出力するプログラム、標準エラー出力に書くプログラムを含む。
- ライブラリが初期化で環境変数を消すので、学習者のプログラムが `getenv("DYLD_INSERT_LIBRARIES")` を読んでも、差し込みなしと同じく `NULL` になった。

### 子プロセス

| プログラム | 環境変数を消すライブラリ | 環境変数を消さない変種 |
|---|---|---|
| `fork` して、子が `exit(0)` する（子にも未解放の領域がある） | 親の結果だけ（0 件）。子は、プロセス ID が違うので書かない | 同じ |
| `system("./main child")`（`/bin/sh` を通して自分を起動し、子は 1 件を残す） | 子にライブラリは入らない。結果は親の 0 件 | `/bin/sh` を通ると `DYLD_INSERT_LIBRARIES` は消えた（`PROGRUST_LEAK_REPORT` は残った） |
| `fork` と `execl("./main", …)` で自分を起動し、子は 1 件を残す | 子にライブラリは入らない。結果は親の 0 件 | 子にもライブラリが入り、子が同じ結果のファイルに書いた |

### 置き方: アプリに同梱する案

- quarantine 属性の値（なし・`0083`・`00c3`・`01c1`）にかかわらず、本番ビルドの `.app` の写しの `Contents/Resources/leakcheck/` に置いたライブラリを差し込めて、件数が正しかった。ライブラリにも、バンドルの他のファイルと同じ値の quarantine 属性が付いていた。
- ライブラリのパス（`…/Progrust 検証.app/Contents/Resources/leakcheck/libprogrust_leakcheck.dylib`）は、空白と日本語を含んでも差し込めた。`DYLD_INSERT_LIBRARIES` は `:` で区切るので、パスに `:` があると使えない。
- 開発時の起動（`tauri dev`）では、`tauri.conf.json` の `bundle.resources` のディレクトリが、実行ファイルの隣（`src-tauri/target/debug/` の `content/`・`runner/`・`prompts/`）に写されていた。同じ形で足したライブラリも、開発時と本番の両方で `resource_dir()` の下から読めるはずである。ただし、ライブラリを `build.rs` でビルドしてリソースに足すことは試していない。
- 教材チェックツールの判定のプログラム（`progrust-judge`）は、`.app` に入らず、同梱の許可クレートの定義を `concat!(env!("CARGO_MANIFEST_DIR"), "/../runner")` で読んでいる。ライブラリも、同じようにリポジトリの中のパスで読める。
- 同梱するライブラリは、作者の Mac で、アプリのビルドのときに作ることになる。CI（ubuntu-latest）では、Mach-O のライブラリも dyld の interpose も作れない。

### 置き方: 同梱したソースを学習者の clang でビルドする案

- ライブラリのソース（約 170 行）のビルドは、`/usr/bin/clang` で 0.08 秒だった。Finder から起動したアプリに近い環境変数でも、環境変数を何も渡さない `env -i` でもビルドできた。ビルドに `PATH` は要らなかった。
- 作業領域の下の、空白と日本語を含むディレクトリ（`…/workspace/c-leakcheck/`）にビルドしたライブラリも、差し込めた。
- ソースは、Rust のコードに `include_str!` で埋め込めば、アプリ・開発時の起動・`progrust-judge` で同じものを使え、リソースのパスを決める必要がない（試していない）。
- この案では、`clang` の版が変わっても、ライブラリが学習者の実行ファイルと同じ `clang` で作られる。CI にも影響しない（ソースは文字列なので、ビルドできない環境でもアプリのビルドは変わらない）。

### CI

- ubuntu-latest には `DYLD_INSERT_LIBRARIES` と dyld の interpose が無いので、このライブラリは動かない。Linux で同じことをするには、`LD_PRELOAD` と `dlsym(RTLD_NEXT, …)` を使う別の実装が要る（試していない）。CI で C の判定を動かすなら、macOS の実行環境を使うか、メモリリークの検査を飛ばすことになる。

### 検証のあとの判断

検証のあと、ユーザーは、画面に出るものが変わる 1 点で Claude の推奨を選び、ほかを Claude の推奨に任せた。次のように決め、仕様に書いた（[ADR 0273](../decisions/0273-build-leak-check-library-from-embedded-source.md)）。

- メモリリークの検査の起動が、終了コード 0 以外・シグナルで終わったとき、結果のファイルができなかったとき・読めなかったとき、`overflow` だったときは、そのテストケースを `runtime_error` にする（ユーザーの選択）。
- 置き方は、実行時にビルドする案にする。ソースをバックエンドのクレートに埋め込み、提出のたびに `c-project/leakcheck/` でビルドする。ビルドに失敗したときは、提出をアプリの側の失敗として終える。
- `strdup` も数える。上限は同時に 524,288 個とする。名前は試作のもの（`libprogrust_leakcheck.dylib`、`PROGRUST_LEAK_REPORT`）とする。

決めた後の構成（`strdup` も置き換えるソースを `c-project/leakcheck/leakcheck.c` に置き、`c-project/` を作業ディレクトリとして `clang -dynamiclib -O2 -o leakcheck/libprogrust_leakcheck.dylib leakcheck/leakcheck.c` でビルドしたライブラリ）で、52 本を動かし直した。ビルドは警告なしで通った。`strdup` を解放しないプログラムが 1 件 6 バイトになったほかは、件数・標準出力・終了コードは前と同じで、52 本すべてが期待どおりだった。差し込みありの 1 回目は、ビルドした直後のライブラリを初めて読み込むので、0.035〜0.22 秒だった（2 回目は前と同じ）。

## 判定

基準を満たした。

- C の章の演習で想定する形（上の表）で、解放し忘れが 1 件でもあれば見つかり、すべて解放したプログラムを不正解にしなかった。例外は、学習者のコードが `strdup` で確保した領域で、置き換えに `strdup` を足さない限り見逃す（C の章では扱わない）。
- ライブラリの作り方は、上の「ライブラリの作り方」のとおりに、仕様に書ける形で定められる。置き方は、2 つの案のどちらでも、アプリ（本番と開発時の起動）と教材チェックツールのそれぞれについて、ライブラリのパスの決め方を仕様に書ける。ただし、実際のアプリと `progrust-judge` から差し込むことは確かめていない（下の「残った事項」）。どちらの案にするかも「残った事項」に書く。

## 残った事項

- 決めること（仕様の変更が要る）と、Claude の推奨（検証のあとに決まった。上の「検証のあとの判断」）:
  - 置き方: 同梱する案と、実行時にビルドする案のどちらにするか。Claude は、実行時にビルドする案（ソースを Rust のコードに埋め込み、提出のたびに作業領域の下でビルドする）を勧める。理由は、アプリ・開発時の起動・`progrust-judge` で同じ手順になり、`build.rs` とリソースの設定と CI に手を入れずに済み、学習者の実行ファイルと同じ `clang` で作られることである。費用は、提出ごとに 1 回 0.08 秒のビルドである。同梱する案は、`build.rs` で作者の Mac の `clang` を使ってビルドし、CI（Linux）では作らないようにする必要がある。
  - 実行時にビルドする案にしたときの、ビルドに失敗したときの扱い。2 つのビルド（検査なし・検査つき）が通った後なので、失敗するのは `clang` が途中で壊れたときくらいである。提出をアプリの側の失敗として終えることを勧める。
  - ライブラリのファイル名と、結果のファイルのパスを渡す環境変数の名前。試作のもの（`libprogrust_leakcheck.dylib`、`PROGRUST_LEAK_REPORT`）を勧める。
  - 記録できる領域の数の上限と、超えたときの扱い。試作の上限（同時に 524,288 個）を勧める。C の章の演習で、同時にこれだけの領域を持つことは無い。超えたときは、試作のとおり件数の代わりに `overflow` と書き、アプリは検査ができなかったものとして扱う（次の次の項目）。
  - `strdup` を数えるかどうか。C の章では扱わないが、置き換えに足すのは小さな変更で、足すと見逃しが無くなるので、数えることを勧める。
  - メモリリークの検査の起動（手順の 4）が、終了コード 0 以外・シグナルで終わったとき、結果のファイルができなかったとき（`_exit(0)` のときなど）・読めなかったとき、`overflow` だったときの、テストケースの結果と画面の見せ方（ユーザーの判断が要る）。手順の 3 を通った後なので、起きるのは、検査なしと検査つきで動きが変わるコード（初期化していない領域を読むと、検査つきでは毎回 `0xBEBEBEBE` を読む。[C の演習のメモリの検査の報告から誤りの種類と行を取り出せるかの技術検証](issue-293-parse-sanitizer-reports.md)）と、`_exit` を使うコードくらいである。
- 確かめられなかった項目:
  - ライブラリを、実際の `build.rs` とリソースの設定で `.app` に入れ、`tauri dev` と `tauri build` のアプリから差し込むこと。写しの `.app` の中に手で置いて確かめただけである。
  - App Translocation されたアプリ（quarantine 属性が付いたまま、移動せずに開いたアプリ）の、読み取り専用の場所に置かれたライブラリを差し込むこと。
  - Rust のプロセス（アプリ）から起動したときの差し込み。Python から起動して確かめた。差し込みは起動される側（学習者の実行ファイル）の制限で決まり、学習者の実行ファイルは `clang` が作った制限の無い実行ファイルなので、変わらないと考えている。
  - CI（ubuntu-latest）での代わりの方法。CI で C の判定をどう動かすか（[非機能要件の未決事項](../spec/non-functional/open-questions.md)）を決める材料は、上の「CI」の節に書いた。
