- アプリの実装は、実装計画のタスクごとに進める。実装計画は、ユーザーがスキル `plan-implementation` を呼んだときに、AI エージェントが作る。
- 実装計画は、上位のモデル（Opus）の会話で作る。安いモデルで実装できるかどうかは、タスクの Issue の書き方で決まるからである。
- ここには、計画とタスクの Issue の決まりを書く。進め方は、スキル（リポジトリのルートの `.claude/skills/plan-implementation/SKILL.md`）に書く。
- タスクを実装するときの決まりは [タスクの実装](implementation-task.md)、レビューの決まりは [実装のレビュー](implementation-review.md)、タスクを続けて進める仕組みは [実装のループ](implementation-loop.md) にある。

## 対象

- 実装計画が扱うのは、アプリ本体（`src/`・`src-tauri/`・`prompts/`・`runner/`）、開発用ツール（`tools/`）、CI（`.github/workflows/`）である。それぞれの役割は [リポジトリ構成](../spec/architecture/repository.md) にある。
- 教材（`content/` のレッスン、動画、音声）を作ることは、実装計画の対象にしない。
- アプリと教材チェックツールを動かして確かめるのに要る見本の教材は、タスクにしてよい。そのうち、作者の環境の VOICEPEAK が要る作業は、`ループ対象外` のタスクにする。

## 計画の持ち方

- 実装は、1 タスクを 1 つの Issue にし、1 つの pull request でマージする。
- 計画と進み具合は、GitHub の Issue、ラベル、マイルストーンで持つ。計画やタスクの一覧を、リポジトリのファイルに書かない。
- 一覧のための Issue は作らない（[Issue の起票](issues.md)「Issue の一覧」）。タスクの前提は各 Issue の本文に、マイルストーンの目的は GitHub のマイルストーンの説明に書く。
- タスクの一覧は、ラベルとマイルストーンで絞り込んで見る（`gh issue list --label "実装タスク" --milestone "（マイルストーンのタイトル）"`）。

## マイルストーン

- マイルストーンは、作者がアプリを操作して確かめられる区切りにする。画面からバックエンドまでを通して動くまとまりで切り、層ごと（バックエンドを全部作ってから画面を全部作る、など）には切らない。
- タイトルは `M{番号} {名前}` の形にする（例: `M0 土台`）。番号は、進める順に付ける。
- 説明には、そのマイルストーンが済んだときに、作者がアプリで何をできるようになるかを書く。
- マイルストーンは、計画を最初に作るときに、最後のものまで作る（タイトルと説明だけ）。タスクの Issue は、次に進めるマイルストーンの分だけ作る。先のマイルストーンのタスクは、そのマイルストーンに進むときに作る。
- 最初のマイルストーンは `M0 土台` にする。次のものを作る。
  - 起動できる空のアプリと、開発で使うコマンド（[開発環境と依存の版](../spec/architecture/development-environment.md)「開発で使うコマンド」）
  - CI（[テストの方針](../spec/non-functional/testing.md)「CI」）
  - 偽の `claude` と偽の `cargo`（[テストの方針](../spec/non-functional/testing.md)「偽の claude と偽の cargo」）
  - ループの試運転（[実装のループ](implementation-loop.md)）
- `M0 土台` のタスクは、`ループ対象外` にして、ユーザーのいる会話で進める。ループは、機械のチェックと CI が動くようになってから回す。

## 未決事項を先に決める

- マイルストーンのタスクを作る前に、そのマイルストーンで扱う機能の未決事項（各機能の `open-questions.md`）をすべて読む。
- そのマイルストーンの実装に要る事項は、タスクを作る前に決める。
  - AI エージェントが決められる事項は、決めて仕様に反映し、ADR を追加する（[ADR の運用ルール](decision-records.md)「仕様の「未決事項」との関係」）。
  - ユーザーの判断が要る事項（[Issue の起票](issues.md)「ユーザーに回す Issue」と同じ基準）は、まとめてユーザーに尋ねる。
- そのマイルストーンの実装に要らない事項は、残してよい。

## タスクの切り方

- 1 つのタスクは、それだけでマージできるものにする。マージした後の main で、機械のチェック（[実装のループ](implementation-loop.md)「機械のチェック」）が通るようにする。
- 1 つのタスクが扱う範囲は、1 つの機能の中の 1 つのまとまりにする。差分が数百行まで、読む仕様の concept が 5 つ程度までを目安にし、超えそうなら分ける。
- タスクが済んだことを、自動テストで確かめられるように切る。画面の見た目のように人が確かめるものは、自動テストで確かめられる部分（部品の計算や状態の扱い）と合わせて 1 つのタスクにする。
- そのマイルストーンで作る範囲に当たる受け入れ条件（各機能の `acceptance.md`）は、どれかのタスクの「受け入れ条件と確かめ方」に載せる。最後のマイルストーンのタスクを作るときに、どのタスクにも載っていない受け入れ条件が無いことを確かめる。
- Issue は、前提になるタスクから先に作る。前提は、要るものだけにする。
- 保護するパス（[実装のループ](implementation-loop.md)「保護するパス」）を変えるタスクは、`ループ対象外` にする。

## タスクの Issue

- タイトルは、何を作るかを日本語の 1 文で書く。
- 本文は、Issue だけを読んで実装を始められるように書く。会話の中のやり取りや、一時作業用ディレクトリ（`CLAUDE.md` の「その他」にあるもの）のファイルを前提にしない。
- 仕様の内容は書き写さず、文書のパスで指す。
- 本文は、次の形で書く。見出しの名前と「前提」の行の形は、ループが読むので変えない。

```markdown
## 目的

（このタスクで、何ができるようになるか）

## 読む仕様

- （リポジトリのルートからの文書のパス。小見出しが分かるときは「小見出し」を続ける）

## 作るもの

- （作るもの・変えるものと、その置き場所）

## 受け入れ条件と確かめ方

- （条件。受け入れ条件の文書にある条件は、その文のまま書く） — （確かめ方の区分の案）

## 人が確かめること

- （マージした後に、作者がアプリを操作して確かめること。無ければ「なし」）

## 前提

- 前提: （先に閉じている必要がある Issue の番号を `#12, #13` の形で。無ければ「なし」）

## 範囲の外

- （このタスクでしないこと。無ければ「なし」）
```

- 確かめ方の区分は、[テストの方針](../spec/non-functional/testing.md)「受け入れ条件の確かめ方」の区分で書く。計画で書くのは案で、区分は実装するときに決める（[タスクの実装](implementation-task.md)「テストと確かめ方」）。
- Issue には、`実装タスク` と、難易度のラベルを 1 つ付け、マイルストーンを設定する。
- タスクの Issue には、`AI起票` と `未判断` を付けない。`AI起票` は、AI エージェントが作業中に見つけた問題の Issue のものである（[Issue の起票](issues.md)「ラベル」）。

## ラベル

| ラベル | 意味 | 付ける者・外す者 |
| --- | --- | --- |
| `実装タスク` | 実装計画のタスク。ループが選ぶ対象になる | 計画を作るときに付ける |
| `難易度:小`・`難易度:中`・`難易度:大` | タスクの難易度（下の「難易度」）。どれか 1 つ | 計画を作るときに付ける |
| `ループ対象外` | ループが選ばない。ユーザーのいる会話で進める | 計画を作るときに付ける |
| `行き詰まり` | ループが進められなかった。経過はコメントにある | ループが付け、ユーザーが外す |
| `人の確認待ち` | マージは済み、作者がアプリを操作して確かめることが残っている | ループが付け、ユーザーが外す |

- ループが直すと決めた `AI起票` の Issue にも、`実装タスク` と難易度のラベルが付く（[実装のループ](implementation-loop.md)「Issue の仕分け」）。
- `行き詰まり` と `人の確認待ち` を外すときは、[実装のループ](implementation-loop.md)「行き詰まり」「人の確認」に従う。

## 難易度

| 難易度 | 当てはまるタスク |
| --- | --- |
| 小 | 仕様が形をそのまま決めていて、作り方を選ぶところが無い（型の定義、定数、設定、文言、定型の部品など） |
| 中 | 小にも大にも当てはまらない |
| 大 | 次のどれかを扱う。プロセスの起動と停止、並行する処理、時間切れ。ジョブキュー。ファイルの書き込みの規則と、データの形式の変換。安全に関わる処理（パスの検証、CSP、`claude` に渡す引数と環境変数）。複数の機能にまたがる作り。技術検証の結果に、注意が要ると書かれたもの |

- 難易度は、差分の量ではなく、誤りやすさで決める。
- 迷ったら、上の難易度にする。
- 難易度とモデルの対応は、[実装のループ](implementation-loop.md)「モデル」にある。

## 計画を作り直すとき

- マイルストーンの区切り（[実装のループ](implementation-loop.md)「マイルストーンの区切り」）で、次のマイルストーンのタスクを作る。済んだマイルストーンで分かったことによって、先のマイルストーンの切り方が変わるときは、先に、マイルストーンのタイトルと説明を直す。
- 開いているタスクの Issue の内容が、仕様の変更で合わなくなったときは、本文を直し、何を変えたかをコメントに書く。
- タスクを分け直すときは、新しい Issue を作り、元の Issue を `not planned` で閉じて、新しい Issue の番号をコメントに書く。元の Issue を前提にしていた Issue の「前提」の行も直す。
