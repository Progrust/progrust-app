- AI エージェントは、作業中に不具合・問題点・課題を見つけたら、その作業の中で直すか、GitHub の Issue に起票する。どちらにするかは、下の「起票する問題」で決める。対象は、ソースコード、設定、ツール、教材、`documents/` の文書など、リポジトリの中のもの全部。
- 問題かどうかを迷ったら、問題として扱う。直す前にも、起票する前にも、ユーザーに確認しない。
- Issue を対応するかどうかは、ユーザーが決める。ユーザーが仕分けを頼んだときは、ユーザーの判断が要るもの以外を、AI エージェントが決める（下の「未判断の Issue の仕分け」）。

## 起票する問題

- 見つけた問題が、いましている作業と関係するときは、起票する前に、その作業の中で直せるかどうかを確かめる。直せるときは、直して、起票しない。
- 次のどれかに当てはまる問題は、いましている作業と関係する。
  - 作業で変えるファイルにある。または、作業の対象と同じ機能（仕様では、同じ機能のディレクトリ）にある。
  - 作業でした変更と食い違う。または、作業でした変更によって生じた。
  - 作業で扱っている問題と、原因が同じである。
- 関係する問題でも、次のどれかに当てはまるときは、直さずに起票する。
  - 直すには大きな変更が要る（機能の実装、技術検証、複数の機能にまたがる仕様の書き換えなど）。
  - 直すかどうか、または、どう直すかに、ユーザーの判断が要る（下の「ユーザーに回す Issue」の、「仕分けを迷った」以外のどれかに当てはまる）。ユーザーの判断が要るかどうかを迷ったときも、起票する。
- いましている作業と関係しない問題は、直さずに起票する。
- 直せるかどうかは、問題の場所と関連する ADR を読んで確かめる。関係するかどうかを迷ったら、関係するとして確かめる。大きな変更が要るかどうかを迷ったら、直し始める。直し始めてから大きな変更が要ると分かったときと、直そうとして直せなかったときは、その問題のためにした編集だけを元に戻して、起票する。
- 起票せずに直した問題は、応答の最後に、何が問題だったかと、どう直したかを書く。
- 1つの Issue には、1つの問題だけを書く。

## Issue の一覧

- Issue の一覧のための Issue（他の Issue を並べて、まとめたり進み具合を追ったりする Issue）は作らない。ユーザーに頼まれて、技術検証などの Issue をまとめて起票するときも同じ。
- Issue のまとまりはラベルで表し、一覧はラベルで絞り込んで見る（`gh issue list --label "（ラベル）"`）。一覧とラベルの2重管理を避けるためである。

## 書く内容

- 何が問題なのかと、それがどこにあるかだけを書く。
- Issue に書くための原因の調査や改善案の検討はしない。作業中に既に分かったことがあれば、書き添えてよい。いましている作業と関係する問題を直さずに起票するときは、直さなかった理由を「問題」に書く。
- Issue だけを読んで分かるように書く。会話の中のやり取りや、一時作業用ディレクトリ（`CLAUDE.md` の「その他」にあるもの）のファイルを前提にしない。
- タイトルは、何が問題なのかを日本語の1文で書く。
- 本文は、次の形で書く。

```markdown
## 問題

（何が問題なのか。見た事実を書く）

## 場所

- （リポジトリのルートからのパス。行が分かるときは `パス:行`）
- 確認したコミット: （`git rev-parse --short HEAD` の値）
```

## ラベル

- 起票する Issue には、`AI起票` と `未判断` と、下の種類のラベルを1つ付ける。
- `AI起票` を付けるのは、AI エージェントが起票した Issue だけ。

| ラベル | 意味 |
| --- | --- |
| `AI起票` | AI エージェントが作業中に見つけて起票した |
| `未判断` | 対応するかどうかを、まだ決めていない |
| `保留` | 対応するが今は対応しないと決めた。起票するときには付けない（下の「起票した後」） |

種類のラベル:

| ラベル | 付ける問題 |
| --- | --- |
| `不具合` | プログラム（ソースコード、設定、ツール）が仕様どおりに動かない、または壊れている |
| `仕様` | 仕様の内容の問題（矛盾、抜け、曖昧なところ、ADR との食い違い）。実装と仕様が食い違っていて、どちらが正しいか分からないときもこれにする |
| `ドキュメント` | 文書の書き方の問題（誤記、リンク切れ、運用ルールへの違反、実態と合わなくなった説明） |
| `改善` | 不具合ではないが、良くしたほうがよい点（重複、保守しにくい作り、性能、使い勝手、運用ルールそのものの問題） |

- どの種類か迷ったら、近いものを1つ選ぶ。
- ラベル `技術検証` と `確認事項` は、ユーザーが管理する Issue のもの。AI エージェントの起票には使わない。
- ラベル `実装タスク`・`難易度:小`・`難易度:中`・`難易度:大`・`ループ対象外`・`行き詰まり`・`人の確認待ち` は、実装計画とループのもの（[実装計画とタスクの Issue](implementation-plan.md)「ラベル」）。起票するときには付けない。

## 手順

1. 同じ問題の Issue が既にあるか、問題を表す語で、閉じた Issue も含めて検索する。

   ```bash
   gh issue list --state all --search "（問題を表す語）"
   ```

   - 開いている Issue があれば、起票しない。その Issue に `保留` が付いているときは、下の「保留の Issue」に従う。
   - 閉じた Issue があるときは、下の「閉じた Issue と同じ問題」に従って、起票するかどうかを決める。

2. Issue を起票する。

   ```bash
   gh issue create --title "（タイトル）" --label "AI起票,未判断,（種類のラベル）" --body-file - <<'EOF'
   ## 問題

   …

   ## 場所

   - …
   - 確認したコミット: …
   EOF
   ```

3. 頼まれた作業に戻る。

- `gh` が使えないときや起票に失敗したときは、起票しようとした内容を、応答でユーザーに伝える。

## 閉じた Issue と同じ問題

閉じた Issue と同じ問題を見つけたときは、閉じたときから状況が変わっていれば起票し、変わっていなければ起票しない。

- 閉じた Issue の本文とコメント（閉じた理由、また問題になる条件）を読み、いま見ている事実と比べる。読んで分かる範囲で比べ、調査はしない。
- 次のどれかに当てはまるときは、状況が変わったとして起票する。
  - コメントに書かれた「また問題になる条件」が起きている。
  - 閉じた理由の前提が、成り立たなくなっている。
  - 閉じたときは起きるかもしれないとされていた問題が、実際に起きている。または、影響が、閉じたときに書かれていたものより大きい。
  - 直したと書かれた問題が、また起きている。
- どれにも当てはまらないときは、起票しない。対応するかどうかの判断が、既に済んでいるからである。
- 閉じた Issue の元になった文書の記述（技術検証の結果の「残った事項」など）を読み直しただけでは、状況が変わったとしない。
- 状況が変わったかどうかを迷ったら、起票する。
- 起票するときは、本文の「問題」に、閉じた Issue の番号と、閉じたときから変わったことを書く。閉じた Issue は開き直さない。

## 起票した後

- 起票した問題は、ユーザーに頼まれるまで直さない。ただし、実装のループは、タスクの切れ目に Issue を仕分け、直すと決めたものを直す（[実装のループ](implementation-loop.md)「Issue の仕分け」）。
- 応答の最後に、その作業で起票した Issue の番号とタイトルを書く。
- ユーザーは、Issue ごとに次のどれかをする。自分でする代わりに、AI エージェントに仕分けを頼んでもよい（下の「未判断の Issue の仕分け」）。
  - 対応すると決めた Issue から、`未判断` を外す。
  - 対応するが今は対応しないと決めた Issue から、`未判断` を外し、`保留` を付ける。
  - 対応しないと決めた Issue を閉じる。
- AI エージェントは、自分から `未判断` を外したり、`保留` を付けたり外したり、Issue を閉じたりしない。ユーザーに頼まれたとき（仕分けを頼まれたときを含む）と、実装のループの仕分けでは行い、下のとおりコメントを書く。
- Issue を閉じるときは、`未判断` が付いていれば外す。

### 保留の Issue

- `保留` を付けるときは、保留の理由と、対応するきっかけ（どうなったら対応するか）を、その Issue のコメントに書く。
- 作業中に、保留の Issue の「対応するきっかけ」が来たことに気づいたら、その Issue にそのことをコメントし、応答でユーザーに伝える。新しい Issue は起票しない。
- 保留の Issue の一覧は、`gh issue list --label "保留"` で見る。

### 対応しない Issue を閉じるとき

- `gh issue close （番号） --reason "not planned"` で閉じる。
- 閉じた理由と、また問題になる条件（どうなったら、また問題になるか）を、その Issue のコメントに書く。条件が分からないときは、閉じた理由だけを書く。後で同じ問題を見つけたときに、状況が変わったかどうかを比べるためである（上の「閉じた Issue と同じ問題」）。

## 未判断の Issue の仕分け

- ユーザーがスキル `triage-issues` を呼んだとき（`/triage-issues`）、AI エージェントは、開いている Issue のうち、`AI起票` が付き、`保留` も `実装タスク` も付いていないものを仕分けて処理する。`未判断` の Issue と、対応すると決めて開いたままの Issue（`未判断` も `保留` も付いていないもの。下の「対応すると決めた Issue」）の両方が対象になる。ユーザーの判断が要る Issue だけを、ユーザーに尋ねる。
- スキルが呼ばれていないときは、仕分けない（上の「起票した後」）。ただし、実装のループは、ユーザーがループを始めたことを仕分けの依頼として、タスクの切れ目に仕分ける。ループの仕分けがここの決まりと違う点（ユーザーに尋ねないこと、その場で直さずにループのタスクにすること）は、[実装のループ](implementation-loop.md)「Issue の仕分け」にある。
- `実装タスク` が付いた `AI起票` の Issue は、ループが直すと決めたものである。ループが直すので、仕分けの対象にしない。
- ここには、仕分けと処理の決まりを書く。進め方は、スキル（リポジトリのルートの `.claude/skills/triage-issues/SKILL.md`）に書く。
- 仕分ける前に、Issue の本文とコメント、「場所」にあるファイルのいまの内容、関連する ADR を読む。起票のときと違い、仕分けに要る調査はする。
- 対象は、仕分けを始めたときに開いていた Issue だけにする。仕分けの途中で起票した Issue は、その回では仕分けない。

### 仕分けの種類

| 仕分け | 当てはまる Issue | 処理 |
| --- | --- | --- |
| 解消している | 問題が、いまのリポジトリにはもう無い。または、問題の前提が無くなった | 閉じる。直っていたときは `completed`、前提が無くなったときは `not planned` |
| 直す | 対応する。直し方を AI エージェントが決められ、その場で直せる | 直して、`completed` で閉じる |
| 対応するが、この仕分けでは直さない | 対応する。直すには大きな変更が要る（機能の実装、技術検証、複数の機能にまたがる仕様の書き換えなど） | `未判断` を外す。開いたままにする |
| 保留 | 対応するが、今は対応しなくてよい | `未判断` を外し、`保留` を付ける |
| 対応しない | 対応しなくてよい | `not planned` で閉じる |
| ユーザーの判断が要る | 下の「ユーザーに回す Issue」に当てはまる | `未判断` のままにして、ユーザーに尋ねる |

### ユーザーに回す Issue

対応するかどうか、または、どう直すかによって、次のどれかに当てはまる Issue は、AI エージェントが決めずに、ユーザーに尋ねる。

- アプリの操作感や学習体験が変わる。
- アプリの範囲や方針が変わる。
- ユーザーが求めて決めたこと（ADR の「決定」に、ユーザーの求めや選択によると書かれたもの）を変える。
- 理由が、ユーザーにしか分からない。ADR の理由を推測で書かないためである。
- AI エージェントが、仕分けを迷った。

尋ねるときは、技術的な詳細を省いて、何を決めてほしいかを書き、推奨する答えを先頭にした選択肢を示す。ユーザーが答えた Issue は、その答えのとおりに処理する。答えなかった Issue は、`未判断` のままにする（`未判断` が付いていない Issue は、何もしない）。

### 対応すると決めた Issue

`未判断` も `保留` も付いていない Issue は、前に、ユーザーか AI エージェントが対応すると決め、まだ直していないものである（上の「起票した後」、「仕分けの種類」の「対応するが、この仕分けでは直さない」）。

- 対応するかどうかは、決め直さない。保留にすることも、対応しないで閉じることもしない。
- 次のどれかにする。
  - 解消している: 問題がもう無い、または前提が無くなったときは、「仕分けの種類」の「解消している」のとおりに閉じる。
  - 直す: 前に要るとした大きな変更が、他の作業で済んだなどして、その場で直せるようになったときは、「仕分けの種類」の「直す」のとおりに直して閉じる。
  - 開いたまま残す: まだ大きな変更が要るときは、何もしない。コメントも書かず、ラベルも変えない。報告で、開いたまま残した Issue として挙げる（下の「コメントと報告」）。
- 直し方が、上の「ユーザーに回す Issue」に当てはまるときは、ユーザーに尋ねる。

### 直すとき

- `CLAUDE.md` と運用ルールに従う（関連する ADR の確認、ADR の追加、検査）。
- ADR に書く理由が、AI エージェント自身の技術的な判断でないときは、直さずにユーザーに回す。
- 直した変更は、コミットしない。ユーザーが確かめてからコミットする。
- 直している途中で別の問題を見つけたら、上の「起票する問題」のとおりにする。「いましている作業」は、直している Issue の対応とする。起票せずに直した問題は、直している Issue のコメントと報告に書く。

### コメントと報告

- 処理した Issue には、必ずコメントを書く。1行目に、したことと、日付と、誰の判断かを書く（例: `保留にした（2026-11-21、Claude の判断）。`）。ユーザーが答えた Issue は「ユーザーの判断」と書く。
- コメントの続きには、仕分けによって次のことを書く。
  - 解消している: 何を読んで確かめたか。
  - 直す: 決めたことと理由、直したファイル、追加した ADR、確認したコミット。直している途中で見つけて、起票せずに直した問題があれば、それも書く。
  - 対応するが、この仕分けでは直さない: 対応すると決めた理由と、直すのに要る変更。
  - 保留: 上の「保留の Issue」のとおり。
  - 対応しない: 上の「対応しない Issue を閉じるとき」のとおり。
- 応答の最後に、仕分けた Issue の番号、タイトル、仕分け、理由を、表で報告する。直した変更がコミットされていないことと、起票せずに直した問題も書く。
- 対応すると決めた Issue のうち、開いたまま残したものは、番号、タイトル、直すのに要る変更を報告する。どれを進めるかは、ユーザーが選んで頼む。報告のための Issue は作らない（上の「Issue の一覧」）。
- ユーザーは、AI エージェントの判断を変えてよい。AI エージェントは、ユーザーに頼まれたら、Issue を開き直す、ラベルを付け直すなどして処理をやり直し、そのことをコメントに書く。
