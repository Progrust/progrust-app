- 技術検証（GitHub の Issue でラベル `技術検証` が付いたもの）の結果は、`documents/verification/` に置く。1つの技術検証の Issue につき1文書にする。
- 技術検証の結果には、検証した時点の事実（使った版、試した方法、観測した出力）を書く。仕様ではない。仕様は `spec/` に、仕様の理由は ADR に書く。

## ファイル

- ファイル名は `issue-<Issue の番号>-<英語の短い説明>.md`（例: `issue-12-reuse-prepared-crates.md`）とする。
- 作成したら、`verification/index.md` に1行追加する（[index.md の書き方と更新](index-files.md)）。

## frontmatter

- `type` は `Verification Report`。
- `title` は「〈確かめたこと〉の技術検証」の形にする（例: `"許可クレートのビルド結果の共有の技術検証"`）。
- `description` は「〈確かめたこと〉を Issue #番号 で検証した結果（〈項目の要約〉）を記す。」の形にする。

## 本文

- 本文の先頭に「日付」「Issue」「確かめた OS」「関連仕様」の4行を書く。
  - 「Issue」は、Issue へのリンク（`[#12](https://github.com/Progrust/progrust-app/issues/12)`）で書く。
  - 「確かめた OS」には、実際に確かめた OS と版を書く。対応環境（[対応環境](../spec/non-functional/environments.md)）と違う環境で確かめたときは、そのことも書く。
  - 「関連仕様」には、検証の対象になった仕様と ADR へのリンクを、「、」で区切って書く。
- 続けて、次の見出しを書く。
  - 「環境」: OS と、使ったツール・ライブラリの版
  - 「方法」: 何を作って、どう試したか
  - 「結果」: Issue の「確かめること」の項目ごとの結果（確かめた・確かめられなかった）と、根拠になった出力
  - 「判定」: Issue の「基準」を満たしたか
  - 「残った事項」: 確かめられなかった項目、ユーザーの判断が要る点、仕様の変更が要りそうな点。無ければ「なし」と書く
- 試作のコードはリポジトリに残さないので、本文だけを読んで分かるように書く。判断の決め手になった最小のコード・コマンド・出力は、本文に書き写す。一時作業用ディレクトリ（`CLAUDE.md` の「その他」にあるもの）のファイルを参照しない。

## 仕様・ADR との関係

- 技術検証の結果を、仕様に書き写さない。検証で仕様を変えることにしたときは、仕様を直し、ADR を追加する。ADR の「背景」から技術検証の結果へリンクしてよい。
- リンクの向きは [参照とリンクの書き方](links.md) に従う。

## 検証し直したとき

- 同じ Issue の検証をやり直したときは、同じ文書を新しい結果に書き換え、「日付」を直す。古い結果は git の履歴に残る。
