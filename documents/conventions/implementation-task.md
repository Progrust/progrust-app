- タスクを実装するのは、ループ（[実装のループ](implementation-loop.md)）か、ユーザーがスキル `implement-task` を呼んだ会話である。どちらも、ここの決まりに従う。
- ここには決まりを書く。進め方は、スキル（リポジトリのルートの `.claude/skills/implement-task/SKILL.md`）に書く。
- 対象は、実装計画のタスクの Issue（[実装計画とタスクの Issue](implementation-plan.md)）と、ループが直すと決めた `AI起票` の Issue（[実装のループ](implementation-loop.md)「Issue の仕分け」）である。

## 始める前

- Issue の本文とコメントを、すべて読む。
- タスクの Issue では、「読む仕様」の文書、その機能の受け入れ条件（`acceptance.md`）、関連する ADR（[参照とリンクの書き方](links.md)「仕様に関係する ADR の探し方」）を読む。その機能の技術検証の結果があれば、それも読む。
- `AI起票` の Issue では、「場所」にあるファイルのいまの内容と、仕分けのコメント（決めたことと理由）を読み、[Issue の起票](issues.md)「直すとき」にも従う。

## 作るとき

- 仕様どおりに作る。仕様に書いていない細部は、技術的な判断で決まるものなら、自分で決める。その判断が ADR に記録する判断（[ADR の運用ルール](decision-records.md)「書く対象」）に当たるときは、ADR を追加する。
- ファイルの置き場所は [リポジトリ構成](../spec/architecture/repository.md)、コマンドと依存の版は [開発環境と依存の版](../spec/architecture/development-environment.md)、画面の見た目は [デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md) に従う。
- 画面を作るタスクでは、画面のレイアウトを [画面の見た目とテーマ](../spec/screens/appearance.md)「画面デザイン」に従って決める。画面デザインのファイル（`design-system/ui-design/`）は、[画面デザインのファイルと変更の手順](../spec/screens/ui-design-files.md)「読み方」に従って読む。
- Issue の「範囲の外」にあるものと、Issue に書かれていない機能は作らない。後のタスクのための作り込みもしない。

## テストと確かめ方

- 「受け入れ条件と確かめ方」の条件ごとに、確かめ方の区分を決める（[テストの方針](../spec/non-functional/testing.md)「受け入れ条件の確かめ方」）。Issue に書かれた区分は案で、変えてよい。変えたときは、結果の報告に書く。
- 自動テストで確かめられる条件には、自動テストを書く。
- 人が操作して確かめる区分にした条件が、Issue の「人が確かめること」に無いときは、結果の報告の「追加で人が確かめること」に書く。
- 終える前に、機械のチェック（[実装のループ](implementation-loop.md)「機械のチェック」）を自分で実行し、すべて通す。
- チェックを通すために、次のことをしない。
  - テストを消す、実行されないようにする、期待する値を実装の結果に合わせて書き換える。
  - lint や型検査の規則を、無効にしたり弱めたりする。
  - 仕様や受け入れ条件を、実装に合わせて書き換える。
- テストが誤っていたときは、仕様と照らして直し、結果の報告に書く。
- 作者の Mac では通り、CI の実行環境でだけ失敗するときは、[テストの方針](../spec/non-functional/testing.md)「CI」に従う。アプリのコードを Linux に合わせて直さない。
- 直しの回で、CI の失敗がタスクの変更と関係しない（タスクで変えていないテストが、たまに失敗するなど）と、失敗の出力と差分から言えるときは、ファイルを変えずに、その失敗を起票し（[Issue の起票](issues.md)）、そのことを結果の報告の要約に書く。ループは、ファイルが変わらなくても CI をやり直す（[実装のループ](implementation-loop.md)「直しと行き詰まり」）。

## 仕様を変える必要が出たとき

仕様の誤り・抜け・矛盾のために、そのままでは実装できないときは、次のようにする。

- 技術的な判断で決められるとき（[Issue の起票](issues.md)「ユーザーに回す Issue」のどれにも当てはまらないとき）は、仕様を直し、ADR を追加して、実装を続ける。`CLAUDE.md` の「必ず守ること」に従う。
- ユーザーの判断が要るときは、決めずに、Issue に起票する（[Issue の起票](issues.md)）。
  - その判断が無くても、タスクの残りを作れるときは、判断が要る部分を除いて作り、除いたことを結果の報告に書く。
  - その判断が無いと進められないときは、実装をやめ、判断待ちとして報告する（下の「結果の報告」）。
- ADR の理由を、推測で書かない。理由が AI エージェント自身の技術的な判断でないときは、ユーザーの判断が要るものとして扱う。

## 見つけた問題

- 実装の途中で見つけた問題は、[Issue の起票](issues.md)「起票する問題」のとおりにする。「いましている作業」は、そのタスクとする。
- 起票せずに直した問題は、結果の報告に書く。

## ループの中で変えないもの

- ループの中では、保護するパス（[実装のループ](implementation-loop.md)「保護するパス」）のファイルを変えない。変える必要があるときは、変えずに Issue に起票する。
- ループの中では、コミット、push、ブランチの切り替えをしない。ループのスクリプトが行う。
- ユーザーのいる会話では、ユーザーに頼まれたときだけ、コミットする。

## 結果の報告

- ループの中では、ループが決めた形で、次のことを返す。

| 項目 | 内容 |
| --- | --- |
| 状態 | 済んだか、判断待ちで進められないか |
| pull request のタイトル | 変更の種類（`feat`・`fix`・`docs` など）と、変更の内容の 1 文 |
| 要約 | 作ったものと、決めた確かめ方の区分 |
| 起票せずに直した問題 | 何が問題だったかと、どう直したか |
| 追加で人が確かめること | Issue の「人が確かめること」に無い、作者がアプリを操作して確かめること |
| 進められない理由と、待っている Issue | 判断待ちのときだけ。起票した Issue の番号 |

- 報告は、どの項目も日本語で書く。ループは、報告を pull request の本文や Issue のコメントにそのまま載せ、ユーザーが読むからである。コードの名前、コマンド、エラーの文の引用、pull request のタイトルの変更の種類（`feat` など）は、元の言葉のまま書いてよい。
- ユーザーのいる会話では、応答の最後に、同じことと、起票した Issue の番号とタイトルを書く。
