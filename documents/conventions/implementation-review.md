- タスクの実装は、マージする前に、実装したのとは別の会話の AI エージェントがレビューする。ループの中ではループが呼び（[実装のループ](implementation-loop.md)）、ユーザーのいる会話ではユーザーがスキル `review-task` を呼ぶ。
- ここには決まりを書く。進め方は、スキル（リポジトリのルートの `.claude/skills/review-task/SKILL.md`）に書く。

## 渡すもの

- レビューする側は、Issue の番号だけを受け取り、Issue、仕様、差分を自分で読む。
- 実装した側の説明（要約、判断の理由の言い分）は、レビューする側に渡さない。差分と仕様だけで判断させるためである。

## 読むもの

- Issue の本文とコメント。
- 差分（main と、タスクのブランチの違い）。
- タスクの Issue では、「読む仕様」の文書、その機能の受け入れ条件、関連する ADR（[参照とリンクの書き方](links.md)「仕様に関係する ADR の探し方」）。
- `AI起票` の Issue では、「場所」にあるファイルと、仕分けのコメント。
- 差分が `documents/` を変えているときは、当てはまる運用ルール。

## 観点

| 観点 | 確かめること |
| --- | --- |
| 仕様 | 実装が、「読む仕様」の文書と関連する ADR のとおりになっている |
| 受け入れ条件 | 「受け入れ条件と確かめ方」の条件が、どれも、自動テストで確かめられているか、人が確かめることとして扱われている。テストが、その条件を実際に確かめている（どんな実装でも通るテストになっていない） |
| 弱めていないこと | テスト、lint や型検査の規則、仕様、受け入れ条件を、チェックを通すために弱めていない（[タスクの実装](implementation-task.md)「テストと確かめ方」） |
| 範囲 | Issue の「範囲の外」のものや、Issue に書かれていない機能を作っていない。タスクと関係のない変更が混じっていない |
| 誤り | 境界の値、エラーの扱い、ファイルの書き込み、パスの扱い、プロセスの扱いなどに、誤動作するところが無い |
| 文書 | 仕様を変えたときに、ADR を追加している。ADR の理由を推測で書いていない。ユーザーの判断が要ること（[Issue の起票](issues.md)「ユーザーに回す Issue」）を、決めてしまっていない。運用ルールに従っている |
| 画面 | 見た目の値を、デザインシステム（[デザインシステムのファイルと変更の手順](../spec/screens/design-system-files.md)）から使っている |

- `AI起票` の Issue では、「受け入れ条件」の代わりに、Issue の「問題」が解消していることを確かめる。

## 指摘の重さと判定

| 重さ | 当てはまる指摘 | 扱い |
| --- | --- | --- |
| `must` | 仕様・受け入れ条件・ADR・運用ルールに反する。誤動作する。テストが条件を確かめていない。チェックを通すために弱めた。ユーザーの判断が要ることを決めた | 直すまでマージしない |
| `note` | 上のどれでもない、良くできる点 | 直さなくてよい。pull request に記録する |

- `must` が 1 件でもあれば、不合格にする。`must` が無ければ、合格にする。
- 好みや書き方の違いは、`must` にしない。
- 指摘には、場所（ファイルと行）、何が誤っているか、どの仕様・受け入れ条件・ADR・運用ルールに反するかを書く。直し方の案は、分かるときだけ書く。
- 迷ったときは、仕様か受け入れ条件のどの文に反するかを言えるものだけを、`must` にする。

## レビューする側がしないこと

- ファイルを変えない。直すのは、実装する側である。
- 機械のチェックを、通ったかどうかを確かめるために実行し直さない。ループでは、レビューの前に、ループが実行して通している（[実装のループ](implementation-loop.md)「1 周の流れ」）。

## 見つけた問題

- タスクと関係しない問題を見つけたときは、指摘にせず、[Issue の起票](issues.md) のとおりに起票する。
