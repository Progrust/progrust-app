- **ch11 テストの演習の判定方法**: 今の仕様では、実行（[コードの実行（run）](../exercise-runner/run.md)）は `cargo build` と実行だけを行い、提出の判定（[コードの提出（submit）](../exercise-runner/submit.md)「test 方式」）は学習者が書いたテストを含めない。学習者が自分で書いたテストを `cargo test` で実行できるようにする方針だが、次のことが決まっておらず、仕様書にもまだ反映していない。決まるまで ch11 の演習は作れない。
  - 画面での実行方法（テスト実行のボタンを別に置くか、実行ボタンの動作をレッスンで切り替えるか）
  - 判定方法（例: 学習者が書いた `#[test]` が N 件以上あり、すべて通ること。学習者のテストが実装の誤りを検出できるかまで判定するか）
  - 統合テスト（`tests/` ディレクトリ）を書けるようにするか。今はエディタから受け取るパスを `src/` 以下に限っている（[実行・提出時のプロジェクトの組み立て](../exercise-runner/project-assembly.md)）
  - ドキュメントテストを実行するか（`src/lib.rs` がある演習でのみ動く）
  - 決め方によっては、統合テスト（ch11-05）とドキュメントテスト（ch11-06）のレッスンを外す。
- **許可クレートの追加**: レッスンで使う外部クレートはすべて許可クレート（[許可クレートと作業領域](../exercise-runner/crates-and-workspace.md)「許可クレート」）に入れる方針だが、ch19・ch21 で使う次のクレートはまだ一覧になく、固定するバージョンも決まっていない。`tokio` を加えると、初回準備の時間とディスク使用量が増える。

  | クレート | 使う章 | 用途 |
  | --- | --- | --- |
  | `thiserror` | ch19-05 | 独自のエラー型の定義 |
  | `anyhow` | ch19-06 | アプリケーションのエラー処理 |
  | `tokio` | ch21 | 非同期ランタイム |
  | `futures` | ch21-03・ch21-07 | `join_all`、ストリーム |
  | `tokio-stream` | ch21-07 | ストリーム（紹介程度） |

- **Rust の最低バージョン**: ch07-08 の let チェーンは Rust 1.88 以降の機能で、今の最低バージョン（rustc 1.85 以上: [対応環境](../non-functional/environments.md)、[外部ツール（cargo・claude）への依存](../architecture/external-tools.md)「検出」）では使えない。最低バージョンをアプリのリリースごとにその時点の最新の stable に上げる方針だが、仕様書には未反映である。バージョンが足りないときの案内（`rustup update stable` を案内するか）も決まっていない。
- **ch01〜ch02 のテストケースの件数**: [レッスンの演習を作るときの注意](exercise-constraints.md) のとおり出力が固定の演習になるため、テストケースを 1 件でよい例外にする方針だが、例外を章（ch01〜ch02）で決めるか、「関数が未習のレッスン」のような条件で決めるかが決まっておらず、[演習の作成ルール](../content-guidelines/exercise.md)「テストケース」・[教材チェックツール](../content-guidelines/check-tool.md)（3 件以上）には未反映である。
- **標準入力のおまじないの定型**: ch03〜ch08 で `stdout` 方式の演習に入力が要る場合に決める（ch01〜ch02 では使わない）。
