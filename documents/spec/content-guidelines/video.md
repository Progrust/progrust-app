## 構成と長さ

- 構成は「表紙 → 導入 → 本編 → まとめ」を基本とする。
- 長さは 1〜5 分を目安とする。目安であり、超えてよい。
- 最初のシーンは表紙にする。表紙にはレッスン名（`lesson.json` の `title`）を出す（[動画のシーンの書き方](../content-format/video/scenes.md)）。
- 最後のシーンはまとめにする。まとめには、このレッスンで分かったことを書き、感想にしない。
- 演習の答えに直結する完成コードは動画に載せない。
- 動画だけでは伝えにくい背景知識は台本の `ai_note` に書いておくと、質疑応答の精度が上がる。
- Rust のレッスンでは、実務での使われ方も伝える（[実務での書き方を伝える](practice.md)）。

## 台本

- ナレーションは「です・ます」調とする。
- 1 文（`text`）は 60 字までを目安とする。目安であり、超えてよい。
- `say` は 140 字までとする。これは上限であり、超えられない（[動画の台本（script.json）](../content-format/video/script-json.md)）。
- `text` は、「画面の文章」 の文章の決まり（和文と英数字の間の半角スペースなど）に従って書く。
- `say` には、VOICEPEAK に読ませる形を書く。
  - 読み間違えやすい語は、読みの対応表（`content/readings.json`。[動画の音声](../content-format/video/voice.md)）に従って、かなで書く（Rust → ラスト、値 → あたい）。
  - 変数名などの英字も、読みで書く（s1 → エスワン）。
  - 間を置きたいところに「、」を入れる。「、」の位置は `text` と違ってよい。
  - 音声を作るツールは、文の途中の句読点の数と、音声の中の間の数が合わない文の音声を作らない（[動画の音声](../content-format/video/voice.md)「音声を作るツール」）。そのエラーが出たときは、`say` の句読点を直す。
  - 対応表にない語を読み間違えたときは、`say` をかなで書き、その語を対応表に足す。
  - コードの記号・キーワード・型名などの読み方は、[ナレーションでのコードの読み方](readings.md) に従う。
- 語は、[教材で使う訳語](terms.md) に従う（例: `&T` は「共有参照」と呼ぶ）。

## ナレーションと画面

音声を聞きながら、その内容と関係ない文字を読むのは、人には難しい。そのため、画面はナレーションに合わせて見せ、ナレーションだけでも話が分かるようにする。

- 音声だけで話の筋が分かるようにする。`say` を順に読み上げただけで、画面を見なくても、何を説明しているのかが分かるように書く。
- 画面に出すもの（見出し・本文・callout・図のラベル・コード）は、どれもナレーションで触れる。ナレーションで触れないものは、画面に出さない。ただし、どの画面にも決まって出る表示（レッスンの番号とタイトルの表示、コードブロックの行番号とファイル名のラベル）は除く。
- 画面の要素は、ナレーションで触れるときに出す。先に全部を出しておかず、話す順に出していく。要素を出す合図は、その要素に触れる言葉の位置に合わせる（「動きと画面の量」）。一度触れた要素は、そのあと画面に残してよい。
- 画面の文に触れるときは、読み上げるだけで済ませない。画面には要点を短く書き、ナレーションでは、その要点を、理由・例・前後とのつながりを添えて説明する。
  - 画面の文と同じ内容を話してよいのは、正確な言葉で覚えてほしい定義や規則（例: 「可変参照は、同時に 1 つだけ」）と、コンパイラの出力の一部を引くときである。このときも、前後の文で、その意味や理由を説明する。画面の文と同じ内容の文だけが続かないようにする。
  - まとめの項目は、項目と同じ内容を話すだけでよい。まとめの項目は、本編で説明を済ませているからである。表紙のレッスン名も同じとする。
  - 画面の文と同じ内容を話すときも、口調はナレーションの「です・ます」調のままにする。画面の文（常体・体言止め）を、そのまま読み上げない（例: 画面の「所有権は新しい変数に移る（ムーブ）」は、「代入すると、所有権は新しい変数に移ります。これがムーブです」と話す）。
- コードが初めて画面に出たら、行を指す前に、そのコードが何をするものかを言う（例: 「これは、2 つの整数を足して返す関数 add と、それを呼ぶ main です」）。そのあとで、注目する行を説明する。左右に並べたコードは、それぞれが何のコードかを言う。
- 画面の上のものを、「ここ」「これ」「この部分」のような指示語だけで指さない。「6 行目の add の呼び出し」「右の図のヒープの箱」のように、名前か位置で指す。名前で言った直後に、指示語で受けるのはよい（上の例の「これは、…関数 add と、…main です」もよい）。

## 画面の文章

- 画面の見出しは、そのとき伝えていることを言い切る文にする（例: 「代入すると、所有権が移る」。「ムーブ」のような名詞だけの見出しにしない）。ただし、表紙の見出しはレッスン名、まとめの見出しは「このレッスンのまとめ」のような見出しでよい。
- 見出しは、ナレーションの進みに合わせて切り替えてよい。
- 画面の本文と callout の文は「です・ます」調とする。見出し・小見出し・箇条書き・表・図の中の語句は、言い切りの常体（「〜が移る」）か体言止めでもよい。
- 和文と英数字の間に半角スペースを入れる（「String を代入」「15 行まで」）。
- 表紙のサブタイトルと箇条書きの項目には句点を付けない。1 つの箇条書きの中では、項目の文末（常体・体言止めなど）をそろえる。
- callout の文に「注意:」「ポイント:」のような前置きを書かない（種類はアイコンと色で示される）。
- 表を載せるときは、表から何を読み取ってほしいのかを、ナレーションで伝える（画面の文・callout に書き添えてもよい）。
- 文中でインラインコード（コードの書体）にするのはコード片だけとする。コード片は、記号・括弧・`::` を含むもの（`&s`、`clone()`、`String::from`、`"hello"`）と、キーワード（`let`、`mut`、`fn`）である。変数名・型名・クレート名だけ（s1、String、i32）はインラインコードにしない。見出しではインラインコードを使わない。表で型や式を並べる列は、そろえるためにすべてインラインコードにする。

## コード

- 画面に出すコードとコンパイラの出力は、台本の `code_blocks` に書く（[動画でのコードの表示](../content-format/video/code-display.md)）。
- 注目させたい字句はマーカー（`CodeBlock` の `marks`）で強調する。行全体に色を付けて強調しない。読み上げている行に目を向けさせるときは、ほかの行を淡くしてよい。
- 他の言語との違いを見せるときは、左右に並べる（左に他の言語、右に Rust）。C と対比するときも、左に C、右に Rust を並べる。
- コードブロックには行番号が表示される（[動画でのコードの表示](../content-format/video/code-display.md)）。ナレーションと画面の文で、コードの行を「6 行目」のように行番号で指してよい。コード片（「`println!` の行」）や、マーカー・枠のラベル（「r の枠」）で指してもよい。マーカーや枠で指すときは、指している字句や範囲（行番号）を台本の `ai_note` に書く。
  - 行番号は、表示される番号（ファイルの行番号）で書く。
  - ファイルの途中から載せるときは `start_line` を書き、ファイルの行番号やコンパイラの出力の行番号とそろえる。`label` にファイル名を書く。関数の途中から載せてもよい。
  - Diff の行は変更後の行番号で指す。削除行には行番号がないので、コード片（「`let s2 = s1;` を消す」）で指す。
  - 行を差し込む動きの途中では、表示される行番号が `code_blocks` の行番号と違うことがある（[動画でのコードの表示](../content-format/video/code-display.md)）。行番号で指すのは、両方が同じになるところだけにする。違うところでは、コード片で指す。
- Diff では、置き換える行は削除行を先に、追加行を後に書く。

## エラー

- コンパイルエラーを説明するときは、コードブロックの中のエラーの箇所を波線（`CodeBlock` の `errors`）で示す。そのエラーをレッスンで初めて説明するところでは、実際のコンパイラの出力も、`language` が `text` のコードブロックで示す。同じエラーに再び触れるところでは、出力を省き、波線と言葉の説明だけでもよい。
- コンパイラの出力には、実際に rustc でコンパイルして得た出力を使う。説明に使わない行は省いてよい。載せる行は書き換えない。C のレッスンの出力の決まりは [C の章の教材の作成ルール](c-lessons.md)「動画」に定める。
- エラーをエラーコードだけで説明しない。ナレーション・画面の本文・callout・見出し・図・コードのコメント・画像の `alt` でエラーを指すときは、何が起きたのかを言葉で書く（例: 「ムーブ済みの値を使ったエラー」「借用している値が先に破棄されるエラー」）。エラーコードは、言葉の説明に括弧書きで添えるときだけ使う（例: 「ムーブ済みの値を使ったエラー（E0382）」）。コンパイラの出力の中のエラーコードは、そのままでよい。

## C との対比

- Rust のレッスンで、[章とレッスンの一覧](../curriculum/chapters/index.md) の「主に扱う内容」が C のレッスンの ID を添えている内容は、C と対比して説明する。
- 対比では、C ではどう書き、何が起きたか（C の章で体験した誤りや書き方）を先に示してから、Rust ではどうなるかを説明する。
- 対比に使う C のコードは、添えられた C のレッスンで扱った内容の範囲にする（[未登場の要素を使わない](no-unseen-elements.md)）。
- Rust が防ぐ範囲を、実際より広く言わない。コンパイル時に防ぐもの（解放後の使用、二重解放、指す先より長く生きる参照、データ競合など）と、実行時に止めるもの（配列の範囲外アクセスなど）と、防がないもの（メモリリークなど）を区別して説明する。

## 図

- 所有権の移動・参照・メモリ配置など目に見えない仕組みは、図で示す。
- コード（文や式）は図（SVG）の中に書かず、コードブロックに書く。図の中に書くのは、変数名・型名・値と、`&s`・`'a` のような 1 語の短いラベルだけにする。図の説明は図の外の文なので、「画面の文章」 に従ってコード片をインラインコードにして書いてよい。図とコードを 1 つの画面に並べるときは、左右に並べ、片方にコードブロック、もう片方に図を置く。
- 変数が生きている範囲・スコープは図にせず、コードブロックに枠（`CodeBlock` の `scopes`）を重ねて示す。
- 図の色は、色クラス（[動画の色の指定](../content-format/video/colors.md)）で指定する。

## 動きと画面の量

- 1 つの画面の上で、ナレーションの進みに合わせてコードと図を変えていく（所有者の印が動く、行を差し込む、読み上げている行以外を淡くする など）。
- 内容のある範囲へ寄せて、文字と図を大きく見せる。
- 寄せ方、文字の最小サイズ、動きの種類と速さ、1 画面に載せる量は、動画のデザインシステム（[画面の見た目とテーマ](../screens/appearance.md)「デザインシステム」）の README「動画の原則」に従う。
- 合図（[動画のタイムラインと合図](../content-format/video/timeline-and-cues.md)）は言葉に合わせる。絵が動く位置を、そのことを読み上げる位置にそろえる。
- 台本や声の設定を変えて音声を作り直したら、合図が言葉に合っていることを確かめ直す。
